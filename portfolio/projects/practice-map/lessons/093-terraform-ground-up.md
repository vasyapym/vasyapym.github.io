# Terraform, Explained From the Ground Up

## The problem before the tool

Terraform is a tool for *infrastructure as code*, the practice of describing servers, networks, databases, DNS records, and anything else a cloud API can create, in text files that are versioned and reviewed like software. The problem it addresses is older than the cloud: when infrastructure is created by clicking in consoles or running ad-hoc scripts, nobody can say with confidence what exists, why, or how to recreate it. The specific wager Terraform makes, which distinguishes it from a shell script that calls cloud APIs, is that infrastructure should be *declarative*. A declarative description says what the end result should be, and leaves to the tool the question of which operations get there. An *imperative* script, by contrast, lists the operations themselves. The appeal of declaration is that the same description works whether you are starting from nothing, from a half-built system, or from a system that has drifted since last week; the tool computes the difference and acts on it.

This single idea, that the tool reconciles a *desired state* (what the files say) against an *actual state* (what the cloud reports), is the load-bearing concept in Terraform. Almost everything else is a consequence of it, or a patch over the places where it breaks down.

## The three things Terraform actually manages

Terraform juggles three artifacts, and most confusion comes from blurring them. The first is *configuration*: the files you write, in a language called *HCL* (HashiCorp Configuration Language), conventionally with a `.tf` extension. The second is *state*: a record Terraform keeps of which real-world objects it has created and what their attributes were the last time it looked. The third is the set of *providers*: plugins that translate Terraform's generic notion of "create, read, update, delete this thing" into calls against a specific API, such as AWS, Azure, Kubernetes, GitHub, or Datadog.

The workflow that binds these is *plan* and *apply*. During plan, Terraform reads your configuration, reads the state, optionally asks providers to *refresh* the state by re-reading the real objects, and then computes a *diff*: a proposed set of creations, updates, replacements, and deletions that would bring reality into line with the configuration. During apply, it executes that plan and writes the result back to state. The plan is the product that makes Terraform safe to use on things that matter; you read it the way you read a pull request, and you can save it to a file so that what gets applied is exactly what was reviewed, not a fresh computation against a world that may have changed in between.

The problem the plan abstraction solves is irreversibility. Cloud operations are often destructive and slow, and "describe what you'll do before doing it" is the only general defense. Where it leaks is in *unknown values*: many attributes, such as the ID a database will be assigned, cannot be known until the object exists. Terraform represents these in a plan as "known after apply," and any configuration that depends on them, including the decision of whether some other resource should exist at all, can force a cascade of uncertainty that makes a plan less informative than it looks. A senior engineer learns to read a plan not just for what it says but for how much of it is deferred.

## Resources and the dependency graph

The atomic unit of configuration is the *resource block*, which declares a single managed object. A resource has a *type*, such as `aws_instance`, which is defined by a provider, and a *local name* you choose, which together form an *address* like `aws_instance.web`. Inside the block you set *arguments*, the inputs the provider accepts, and after creation the resource exposes *attributes*, which include the arguments plus whatever the API reported back, like IP addresses or ARNs. Resources reference each other's attributes through expressions such as `aws_instance.web.id`, and this is not merely a convenience: every such reference is an edge in a *dependency graph* that Terraform constructs before doing anything. The graph determines ordering during apply, parallelism (independent resources are created concurrently), and reverse ordering during destruction.

The graph is load-bearing. It is why you rarely have to say "do this first" explicitly, and why Terraform can safely apply changes to a thousand-resource configuration without a human sequencing them. It leaks in two directions. First, dependencies that exist in reality but are not expressed as references in configuration, for example an IAM policy that must propagate before an instance can use it, are invisible to the graph, and the `depends_on` *meta-argument* exists to declare them by hand. Meta-arguments are a small set of arguments Terraform itself interprets rather than passing to the provider; `depends_on`, `count`, `for_each`, `provider`, and `lifecycle` are the full list, and they are worth memorizing because they are the seams where Terraform's own semantics show through. Second, the graph is built from static references, so Terraform cannot know a dependency that only becomes apparent from runtime data. These are the cases where applies fail with eventual-consistency errors and succeed on retry, and the honest answer is that Terraform's model does not fully capture time.

A *data source*, declared with a `data` block, is the read-only counterpart to a resource: it looks something up, such as the current account ID or the newest AMI matching a filter, and exposes it as attributes without claiming to manage it. Data sources solve the problem of importing facts from outside the configuration. They leak when the thing they read is itself managed by Terraform in the same run, because they are read during plan and may see a stale or nonexistent object; the usual advice to reference the resource directly rather than query for it is really advice to keep the dependency in the graph.

## Multiplicity: count and for_each

Declaring one resource at a time does not scale, and Terraform offers two ways to stamp out several from one block. `count` takes a number and produces instances addressed by integer index, like `aws_subnet.private[0]`. `for_each` takes a map or set of strings and produces instances addressed by key, like `aws_subnet.private["eu-west-1a"]`. The distinction is incidental in syntax but load-bearing in behavior. Because state tracks each instance by its address, removing the first element of a `count`-based list renumbers every subsequent instance, and Terraform will propose destroying and recreating all of them. `for_each` instances keep their keys, so adding or removing one touches only that one. The rule of thumb that `count` is for "zero or one, conditionally" and `for_each` is for "several distinct things" is not style; it is a consequence of how state identity works. Both share a hard limitation: the number or set of keys must be known at plan time, which means you cannot `for_each` over a list of IDs that will only exist after apply. This is one of the most common walls people hit, and it is the unknown-values problem from earlier wearing a different hat.

## Variables, locals, outputs, and the expression language

A configuration is parameterized with *input variables*, declared in `variable` blocks and supplied from files, environment variables, or command-line flags, each with an optional *type constraint* drawn from a type system that includes strings, numbers, booleans, lists, maps, sets, objects, and tuples. *Local values*, declared in a `locals` block, are named intermediate expressions, roughly what `let` bindings are in a functional language. *Output values*, declared in `output` blocks, expose results to whoever is using the configuration, whether a human reading the CLI or a parent module.

Underneath these is an expression language with conditionals, `for` expressions that transform collections, splat syntax for extracting one attribute from many instances, string templates, and a library of built-in functions for manipulating strings, collections, encodings, and files. The language is deliberately not Turing-complete; there are no user-defined functions in the core language (providers can define functions as of Terraform 1.8, but you cannot write one in HCL), no loops outside of collection comprehensions, and no mutable state. This restriction is load-bearing because it keeps evaluation predictable and keeps plans computable, and it leaks precisely when people want it to, which is why Terraform configurations sometimes contain heroic nested `for` expressions that would be three lines in Python. The *dynamic block*, which generates repeated nested blocks inside a resource from a collection, is the most-used pressure valve here and the most-abused.

Since Terraform 1.x, variables and outputs can be marked *sensitive*, which redacts them from CLI output. This is cosmetic rather than security: sensitive values are still written to state in plaintext, and anyone who can read state can read them. Treating state as a secret store with the same access controls as the secrets themselves is a consequence, not an option.

## State, the uncomfortable center

State deserves its own treatment because it is the abstraction most people underestimate. It is a JSON document, by default a local file named `terraform.tfstate`, that maps every resource address in your configuration to the identifier and attributes of a real object. It exists to solve a problem that providers cannot solve alone: cloud APIs generally do not let you ask "which of these objects did Terraform create and which configuration block does each correspond to." Tags are unreliable, naming is inconsistent, and some objects have no stable name at all. State is the binding between declaration and reality, and without it Terraform would have to guess.

Because it is the binding, it is also the thing that goes wrong. If a resource is deleted outside Terraform, state still claims it exists, and the next refresh will discover the discrepancy and plan to recreate it, which is correct. If a resource is modified outside Terraform, this is called *drift*, and refresh will detect it and plan to revert it, which may or may not be what you want; the `ignore_changes` lifecycle setting exists to declare that certain attributes are owned by something else. If an object is created outside Terraform but you want Terraform to own it, you must *import* it, which writes a state entry for an existing object; this was historically a CLI command and since Terraform 1.5 can be declared in configuration with an `import` block, which is a meaningful improvement because it makes adoption reviewable in a plan. If you rename a resource in configuration, Terraform sees one address disappear and another appear and will plan a destroy and a create; the `moved` block, added in 1.1, lets you tell it that these are the same object, and the `removed` block, added in 1.7, lets you tell it to forget an object without destroying it. These three blocks exist because the fundamental model, "address equals identity," has no other way to express refactoring.

State must also be shared and protected. A *backend* is where state lives and how it is accessed; the common ones are object stores such as S3, Azure Blob, and GCS, and HashiCorp's own hosted service. *State locking*, which prevents two concurrent applies from corrupting the file, is a backend feature and not all backends support it. State can be read by other configurations through the `terraform_remote_state` data source, which is a tempting way to connect stacks and a well-known source of coupling, since it exposes every output of one configuration as a dependency of another. Note one area of recent churn here: the S3 backend historically used a separate DynamoDB table for locking, and since Terraform 1.10 it supports native locking via S3 conditional writes, so guidance that insists on DynamoDB is now dated though not wrong.

The deepest leak in state is that it is a cache that can be lied to. A state file can be edited by hand, surgically moved between configurations with `terraform state mv`, or rebuilt from scratch. All of these are sometimes necessary and all of them break the guarantee that a plan is trustworthy. Experienced practitioners treat state operations the way database administrators treat direct table edits.

## Lifecycle and the places where "declarative" needs help

The `lifecycle` meta-argument is a grab bag of knobs that modify how Terraform handles a specific resource, and each knob is a confession about a case the default model handles poorly. `create_before_destroy` inverts the default replacement order so that a new object exists before the old one is removed, which matters for anything serving traffic; it is not the default because many resources have unique names that prevent two from coexisting. `prevent_destroy` makes a plan fail rather than delete a resource, a guard rail for databases. `ignore_changes` cedes ownership of specific attributes. `replace_triggered_by` forces replacement when some other resource changes, for cases where the dependency is real but no attribute carries it. *Preconditions* and *postconditions*, added in 1.2, let you assert facts about inputs and results and fail with a readable message. None of these is load-bearing in the sense of being unavoidable; a configuration can be written without any of them. They are load-bearing in the sense that production configurations always end up using some, because the gap between "reconcile desired and actual" and "do so without an outage" is exactly the gap they fill.

*Provisioners* are the older and blunter escape hatch: blocks that run scripts on the local machine or over SSH on a created instance. They are explicitly discouraged in the documentation, because they are imperative steps bolted onto a declarative model, they run only at creation, and their failure leaves a resource half-configured in a way state cannot describe. The `null_resource`, and its modern replacement `terraform_data`, exist largely as somewhere to hang a provisioner. If a problem seems to need a provisioner, the usual better answers are cloud-init, a configuration management tool, or a provider that models the thing directly.

## Modules: composition and its costs

A *module* is a directory of configuration files. The directory you run Terraform in is the *root module*; any other module it calls, through a `module` block with a `source` pointing at a local path, a Git repository, or a *registry* such as the public Terraform Registry, is a *child module*. Modules take input variables and produce outputs, and a child's resources are addressed under its module path, like `module.vpc.aws_subnet.private["a"]`. Modules solve the problem of reuse and of hiding complexity behind an interface, and they are the only unit of abstraction Terraform offers, so they carry a lot of weight.

They leak in characteristic ways. Everything a module needs must be passed in explicitly, and everything it produces must be declared as an output, so deep module trees acquire long chains of pass-through plumbing. Provider configurations are inherited implicitly from the parent unless overridden, which is convenient and surprising in equal measure; a module cannot easily declare that it requires a specifically configured provider without the parent cooperating. Modules can use `count` and `for_each` since 0.13, but the same plan-time knowability constraints apply. Module versioning, through a `version` argument against registry sources, is essential for stability, and pinning to a Git commit for non-registry sources is the equivalent discipline. The broader design question, how large a module should be and how many should compose into one root, has no settled answer; the community has oscillated between monolithic roots and many small ones, and the honest trade-off is between blast radius on one side and cross-stack coupling through remote state on the other.

## Providers, the plugin boundary

Providers are separate executables that Terraform launches and talks to over a gRPC protocol. Each is versioned independently of Terraform, has its own release cadence and its own bugs, and defines the schema of every resource type and data source it offers. The `required_providers` block declares which providers a configuration uses and with what version constraints, and the *dependency lock file*, `.terraform.lock.hcl`, records the exact versions and checksums selected, which should be committed so that colleagues and CI resolve the same plugins. Provider configurations can be *aliased* so that one configuration can, for example, operate in two AWS regions or two accounts simultaneously, with resources selecting an alias through the `provider` meta-argument.

The provider boundary is load-bearing because it is what makes Terraform generic; the core knows nothing about any cloud. It is also where the abstraction leaks most visibly. Whether an attribute change is an in-place update or forces replacement is decided by the provider's schema, and the plan will tell you with a "forces replacement" annotation, but the decision is sometimes surprising and occasionally wrong. Whether a plan shows a spurious diff every run, the phenomenon called *perpetual drift*, is almost always a provider bug in normalizing what the API returns. Whether an object can be imported, and with what identifier, is provider-specific. The quality of your Terraform experience is largely the quality of your providers, and the major cloud providers are mature while long-tail ones vary widely.

## Workspaces, and a naming collision

The word *workspace* means two different things, and this is incidental API surface that nonetheless trips people up. In the CLI, a workspace is a named state file within one backend, so one configuration can be applied several times with separate state, which some teams use for environments like staging and production. In HashiCorp's hosted product, a workspace is a unit of organization that bundles a configuration, variables, state, and run history, which is a broader concept. CLI workspaces are a thin feature, and the common criticism that they encourage configurations where environment differences are expressed as conditionals on the workspace name rather than as explicit inputs is fair. Many teams prefer separate root directories or separate variable files per environment and ignore CLI workspaces entirely.

## Newer surface, and where to hold opinions loosely

Several features are recent enough that documentation and folklore have not caught up, and it is worth saying which ones are settling and which are still moving. The native *test framework*, with `.tftest.hcl` files that run plans or applies against a configuration and assert on results, arrived in 1.6 and is now reasonable to adopt; earlier testing approaches using external Go frameworks remain in use but are no longer the only option. *Check blocks*, from 1.5, let a configuration assert ongoing conditions, such as that an endpoint responds, without those assertions blocking apply. *Ephemeral values*, introduced in 1.10, and *write-only arguments*, in 1.11, are an attempt to fix the long-standing problem that secrets fetched during a run end up in state; an ephemeral resource is read during a run and never persisted, and a write-only argument accepts a value without storing it. This is a genuine architectural change and provider support for it is still being built out, so expectations should be calibrated per provider. *Stacks*, a higher-level construct for orchestrating multiple configurations with shared provider setup and deferred changes, has been available in HashiCorp's hosted platform and its exact shape in the open CLI is something I would verify against current documentation rather than rely on from memory. *Deferred actions*, which let a plan proceed when parts of it cannot yet be known, address the unknown-values problem directly and are similarly new enough that their maturity should be checked.

The largest churn is not technical. In 2023 HashiCorp changed Terraform's license from the Mozilla Public License to the Business Source License, which restricts use by competitors offering it as a service. In response, a community fork named *OpenTofu* was created from the last MPL release and is governed under the Linux Foundation. OpenTofu tracks Terraform's language closely but has begun to diverge, adding features such as client-side state encryption and early evaluation of variables in backend and module source blocks that Terraform does not have, while Terraform has added features OpenTofu has not yet mirrored. Separately, HashiCorp's hosted product was renamed from Terraform Cloud to HCP Terraform, and IBM's acquisition of HashiCorp closed in 2025. Anything written about licensing, feature parity between the two projects, or the commercial platform has a short shelf life, and I would treat specific claims in either direction as needing a date attached. Policy-as-code enforcement, through HashiCorp's Sentinel or the open-source Open Policy Agent, sits in this commercial and ecosystem layer rather than in the core language, and which one a team uses is more a function of platform choice than of Terraform itself.

## What to actually hold onto

If the vocabulary above is compressed to what a practitioner cannot do without, it is this. Terraform reconciles a declared desired state against a stored record of actual state, by way of a plan that should be read before it is applied. Resources are the units of declaration, their references form a graph that governs ordering, and their addresses are their identities in state, which is why renaming and renumbering are dangerous and why `moved`, `import`, and `removed` exist. Providers are where the generic model meets specific APIs and where most surprises originate. Modules are the only abstraction mechanism and pay for reuse with plumbing. State is a shared, sensitive, corruptible cache that must be locked, protected, and treated with the caution of a database. The expression language is intentionally weak and will frustrate you in exactly the places that weakness is doing its job. And the single recurring limitation under all of it is that Terraform must decide what to do before it knows everything it would like to know, so anything that cannot be known at plan time, whether a count, a key, or an ID, is where the clean model gives way to workarounds. Everything else, the exact flags, the lifecycle knobs, the names of built-in functions, the shape of the test syntax, is surface that can be looked up when needed and that has changed enough times to make looking it up the right habit.
