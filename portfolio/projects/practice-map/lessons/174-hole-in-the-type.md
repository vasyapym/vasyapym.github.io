# The Hole in the Type
On the thirtieth of July 2003, in his office at Microsoft in Redmond, Anders Hejlsberg explained to two visitors what was wrong with throwing generics away.

He had designed Turbo Pascal, Delphi and C#, whose generics were two years from shipping. A generic, he said, is a type with a type parameter: a List that can say what it is a List of. Java was getting them too, under a goal he found revealing: they had to run on an unmodified virtual machine. So Java's compiler checked that a List<Customer> held only customers, then deleted the <Customer>, compiled a plain List, and inserted the casts you had not written. He had two objections; the first was speed. The second, "probably an even bigger issue," was that "when you get to runtime, you don't actually have a faithful representation of what you had at compile time." In C#, by contrast, "anything you can do at compile time you can also do at runtime."

On the eighteenth of June 2013, eight months after its first release, Hejlsberg's TypeScript shipped version 0.9. The headline feature was generics, "the most highly requested feature by 0.8 users," and every one of them was erased. Not even Java's casts; there was nothing to insert them for. The compiler checked the <T> and then wrote out JavaScript in which no T had ever been. He had not changed his mind. The machine was not his to modify. It was every JavaScript engine in every browser, running a language that since 1995 could only be added to; TypeScript's founding decision was that its types would add nothing to it.

So what is a T, if nothing that runs is ever one? A generic is a type with a hole in it — a promise that whatever relationship goes in comes out intact — and you rarely fill the hole yourself, because the compiler infers it; the best TypeScript is mostly inferred, annotated only at the edges.

function first<T>(xs: T[]): T {
  return xs[0];
}
T is the hole. It is not a type but the place a type will go — named in the angle brackets, then used twice, and that is the whole declaration: whatever kind of thing the array holds, that is the kind of thing that comes out. The 0.9 announcement said it plainly: generics capture "relationships between inputs and outputs."

Who fills the hole? Mostly nobody. Given a playlist of type Track[], write const nowPlaying = first(playlist). Nobody wrote <Track>; first does not know what a Track is and never will. The compiler looked at the argument, laid Track[] against T[], and T was Track; so nowPlaying is a Track, nowPlaying.seconds is a number, and nowPlaying.second is an error. Nothing was annotated between the signature and the mistake; the signature is the edge. A shuffle declared <T>(xs: T[]): T[] gives a playlist back as a Track[], which is the whole promise of a shuffle: the same things, reordered. You may fill the hole by hand, first<Track>(playlist), and almost never need to. The handbook describes inference in five words: the compiler "just looked at the value."

A hole can be given a shape: <T extends { length: number }> accepts only things with a length — strings, arrays — so .length may be used inside, and a number is refused.

At run time there is one function. Not a copy per type, the way a C++ template works — "really just like macros, except they look like classes," Hejlsberg said that day — and not a first of Track manufactured on demand, as in C#. One function for every call there will ever be, because a JavaScript function had always taken what it was given. <T> is the compiler's name for whatever it was given, so it can say that the same whatever comes out.

The promise is made by reading, and reaches as far as reading can see. first(playlist) is a Track; when the playlist is empty it is undefined, typed Track, and the type travels. The compiler could call every xs[0] a T | undefined. It would be right, and would demand a check at every index in every loop ever written. In 2003 Hejlsberg had called typing "a dial," and warned that "you can turn that dial too far in either direction." TypeScript left xs[0] at T, and in November 2020 added noUncheckedIndexedAccess, the other notch; it is not part of strict, the release notes say, because "it might be noisy for a lot of code." Turn it on and first will not compile until its return type says T | undefined.

What the compiler wrote out for first is function first(xs) { return xs[0]; }. The September 1995 beta of Navigator 2.0 would have run it, and returned the first of whatever it was given.
