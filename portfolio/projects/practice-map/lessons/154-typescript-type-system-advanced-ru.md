# Продвинутая система типов TypeScript

## Часть 0. Главная ментальная модель

Самая полезная перестройка мышления звучит так: **в TypeScript два языка**.

Первый — JavaScript с аннотациями. Он выполняется в рантайме.

Второй — язык типов. Это отдельный чистый функциональный язык. Он «выполняется» компилятором во время проверки и полностью стирается перед запуском. У этого языка есть всё, что нужно для программирования:

- **функции** — дженерик-алиасы: `type F<T> = ...`;
- **ветвление** — conditional types: `T extends U ? X : Y`;
- **паттерн-матчинг** — `infer`;
- **циклы** — рекурсия и mapped types;
- **строки** — template literal types;
- **данные** — кортежи, объекты, union'ы.

Переменных и мутаций в нём нет, только выражения. Когда опытный разработчик пишет сложный тип, он мысленно пишет маленькую программу на Haskell-подобном языке со странным синтаксисом.

Вторая опорная модель: **тип — это множество значений**.

- `string` — множество всех строк.
- `"a"` — множество из одного элемента.
- `"a" | "b"` — объединение множеств.
- `never` — пустое множество.
- `unknown` — множество всех значений, универсум.

Отношение «A assignable to B» (A можно присвоить в B) означает «A — подмножество B». Почти всё странное поведение становится логичным, если думать в этих терминах:

- `never` присваивается куда угодно: пустое множество — подмножество любого.
- Всё присваивается в `unknown`.
- `A | never` — это просто `A`.
- `A & never` — это `never`.
- `{ a: string } & { b: number }` — это объекты, у которых есть *и* `a`, *и* `b`. Пересечение множеств значений даёт объединение требований. Новички часто путаются, почему `&` «добавляет поля»: дело именно в этом.

Особняком стоит `any`. Это не множество, а выключатель проверки: он одновременно и подтип, и супертип всего. Поэтому `any` ломает рассуждения, и в конструкциях на уровне типов он ведёт себя непредсказуемо (подробнее ниже).

Третья модель: **типизация структурная**. Тип определяется формой, а не именем. Два интерфейса с одинаковыми полями взаимозаменяемы. Это важно для branded types: они существуют ровно для того, чтобы локально обойти структурность.

## Часть 1. Дженерики как функции и `extends` как контракт

```ts
type Box<T> = { value: T };
type Pair<A, B = A> = [A, B];             // параметр по умолчанию
type Keys<T extends object> = keyof T;    // constraint
```

Дженерик-алиас — это функция на уровне типов. `T extends object` в объявлении параметра — это типизация аргумента такой функции: «принимаю только то, что присваивается в `object`».

У слова `extends` в TypeScript **два разных смысла**, и их полезно различать вслух:

1. В объявлении параметра (`<T extends X>`) это **constraint**, ограничение.
2. В условном типе (`T extends X ? A : B`) это **проверка assignability**, вопрос «является ли T подмножеством X?».

Оба смысла не имеют отношения к наследованию классов. Это проверка подмножества.

## Часть 2. Conditional types

### Базовая форма

```ts
type IsString<T> = T extends string ? true : false;

type A = IsString<"hi">;    // true
type B = IsString<42>;      // false
```

Это тернарник над множествами: «если T — подмножество string, то true, иначе false».

### Дистрибутивность — главное, что нужно понять

```ts
type ToArray<T> = T extends unknown ? T[] : never;

type C = ToArray<string | number>;  // string[] | number[], а НЕ (string | number)[]
```

Если проверяемый тип — это **«голый» параметр типа** (naked type parameter: именно `T`, не `T[]` и не `[T]`), а в него подставили union, то conditional type **распределяется** по членам union. Он применяется к каждому члену отдельно, а результаты объединяются. По сути это `map` по union'у.

На этом построены встроенные утилиты:

```ts
type Exclude<T, U> = T extends U ? never : T;   // фильтр
type Extract<T, U> = T extends U ? T : never;

type D = Exclude<"a" | "b" | "c", "a">;  // "b" | "c"
```

Фильтрация работает потому, что `never` в union исчезает, ведь это пустое множество. Идиома «вернуть `never`, чтобы выкинуть элемент» встречается в коде постоянно.

**Как отключить дистрибутивность.** Оберните обе стороны в кортеж:

```ts
type ToArrayND<T> = [T] extends [unknown] ? T[] : never;
type E = ToArrayND<string | number>;  // (string | number)[]
```

### Ловушки дистрибутивности

**Первая ловушка: `never`.** `never` — это пустой union. Распределение по пустому union даёт пустой результат, то есть `never`, и ни одна ветка не выполнится.

```ts
type IsNever<T> = T extends never ? true : false;
type F = IsNever<never>;  // never (!), а не true

type IsNeverFixed<T> = [T] extends [never] ? true : false;  // правильно
```

Это классический вопрос на собеседовании и классический баг в самописных утилитах.

**Вторая ловушка: `boolean`.** `boolean` — это `true | false`, поэтому любой дистрибутивный тип на `boolean` даст union из двух результатов. Это неожиданно, если вы мысленно считали `boolean` атомарным.

**Третья ловушка: `any`.** `any extends X ? A : B` даёт `A | B`, то есть обе ветки. Компилятор не может решить, и поэтому объединяет.

### Отложенные (deferred) conditional types — слой ниже

Пока `T` — неизвестный дженерик-параметр (например, внутри тела функции), компилятор **не может** вычислить `T extends string ? ... : ...`. Тип остаётся невычисленным и «висит» в отложенной форме. Отсюда давняя боль:

```ts
function f<T extends boolean>(x: T): T extends true ? string : number {
  return x ? "yes" : 0;
  // Ошибка: "yes" не присваивается в T extends true ? string : number
}
```

Компилятор не сужает `T` по проверке `x` в рантайме: control flow narrowing работает со значениями, а не с параметрами типов. Обычные решения: перегрузки (overloads) или каст `as any` / `as never` внутри реализации при честной сигнатуре снаружи.

Это норма индустрии, а не позор. Библиотечный код полон таких кастов в реализации, а сложность типов живёт в публичной сигнатуре. Принцип формулируется так: **типы — для потребителя API, а реализация может быть доказана вами, а не компилятором**.

## Часть 3. `infer` — паттерн-матчинг по типам

`infer X` можно использовать только в правой части `extends` у conditional type. Он означает: «сопоставь форму и захвати, что окажется на этом месте».

```ts
type ElementOf<T> = T extends (infer E)[] ? E : never;
type G = ElementOf<string[]>;   // string

type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
type MyParameters<T> = T extends (...args: infer P) => any ? P : never;

type First<T extends readonly unknown[]> = T extends readonly [infer H, ...unknown[]] ? H : never;
```

Встроенные `ReturnType`, `Parameters`, `ConstructorParameters`, `InstanceType`, `Awaited` устроены именно так. `Awaited` ещё и рекурсивна: она разворачивает вложенные промисы и thenable-объекты.

Заметьте `any[]` в constraint функции. Обычный совет «никогда не используй any» здесь не работает. Из-за контравариантности параметров `(...args: unknown[]) => unknown` *не* примет функцию `(x: string) => void`: функция, требующая строку, не может принять произвольный unknown. Поэтому в позиции ограничения «любая функция» пишут `(...args: any[]) => any` или `(...args: never[]) => unknown`. Это осознанная идиома, а не небрежность.

### `infer ... extends` (TS 4.7+)

```ts
type FirstString<T> = T extends [infer S extends string, ...unknown[]] ? S : never;
```

Конструкция одновременно захватывает тип и проверяет его. Раньше для этого требовался вложенный conditional type.

### Вариантность и `infer` в нескольких позициях

Если одна и та же переменная `infer X` встречается в нескольких местах, результат зависит от позиции:

- в **ковариантных** позициях (возвращаемые значения, поля) кандидаты объединяются в **union**;
- в **контравариантных** позициях (параметры функций) — в **intersection**.

На этом построен знаменитый трюк:

```ts
type UnionToIntersection<U> =
  (U extends unknown ? (x: U) => void : never) extends (x: infer I) => void
    ? I
    : never;

type H = UnionToIntersection<{ a: 1 } | { b: 2 }>;  // { a: 1 } & { b: 2 }
```

Разберём по шагам:

1. Дистрибутивный conditional type превращает union в union функций: `((x: A) => void) | ((x: B) => void)`.
2. Затем `infer I` в позиции параметра собирает кандидатов как пересечение.

Если вы умеете объяснить этот трюк, вы понимаете вариантность лучше большинства.

**Словарь вариантности.** Ковариантность — тип «едет в ту же сторону», что и подтипирование: `Array<Dog>` ≤ `Array<Animal>` при чтении. Контравариантность — в обратную сторону, это параметры функций. Инвариантность — ни туда, ни туда. Бивариантность — в обе стороны. Методы, объявленные синтаксисом метода `m(x: T): void`, а не свойства-функции `m: (x: T) => void`, проверяются бивариантно даже при `strictFunctionTypes`. Это сознательная дыра ради совместимости, например с DOM-событиями.

С TS 4.7 можно явно аннотировать вариантность: `interface Producer<out T>`, `interface Consumer<in T>`. Это нужно в основном для производительности и документирования в библиотеках, в прикладном коде такое встречается редко.

## Часть 4. Mapped types

### Основа

```ts
type MyPartial<T>  = { [K in keyof T]?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
type Mutable<T>    = { -readonly [K in keyof T]: T[K] };   // снять модификатор
type MyRequired<T> = { [K in keyof T]-?: T[K] };
```

`[K in ...]` — это цикл по union ключей. `T[K]` — **indexed access type**, обращение к типу поля. Модификаторы `+`/`-` добавляют или снимают `readonly` и `?`. Плюс подразумевается по умолчанию.

`keyof T` возвращает union ключей. Нюанс: для типа с индексной сигнатурой `{ [k: string]: X }` выражение `keyof` даёт `string | number`, потому что числовые ключи в JS — это строки. При генерации строк из ключей поэтому часто пишут `K & string` или `Extract<keyof T, string>`. Иначе `symbol` и `number` не пролезут в template literal.

### Гомоморфные mapped types — слой ниже

Mapped type вида `{ [K in keyof T]: ... }`, где `T` — параметр типа, называется **гомоморфным**. У него есть особые свойства, которые компилятор реализует специально:

1. **Сохраняет модификаторы** исходного типа: `readonly` и `?` переносятся.
2. **На массивах и кортежах даёт массивы и кортежи**, а не объект со всеми методами Array: `MyPartial<[string, number]>` превращается в `[string?, number?]`.
3. **Распределяется по union**: `MyPartial<A | B>` равно `MyPartial<A> | MyPartial<B>`.
4. На примитивах возвращает сам примитив.

Если написать `{ [K in "a" | "b"]: ... }` с конкретным union, гомоморфности нет. Получится просто `Record`.

### Key remapping через `as` (TS 4.1+)

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<K & string>}`]: () => T[K]
};
type P = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }

// Фильтрация ключей: вернуть never, и ключ исчезнет
type OmitFunctions<T> = {
  [K in keyof T as T[K] extends (...a: any[]) => any ? never : K]: T[K]
};
```

Footgun: `as`-клауза сохраняет модификаторы, но **ломает поведение на массивах и кортежах**. Применив такой тип к кортежу, вы получите объект с `length`, `push` и так далее. Если тип должен работать и с массивами, обрабатывайте их отдельной веткой conditional type.

### `Record`, `Pick`, `Omit` и тонкости

```ts
type Record<K extends keyof any, V> = { [P in K]: V };
```

`Record<"a" | "b", number>` и `Record<string, number>` — это разные вещи. Первый тип — объект с ровно этими ключами. Второй — индексная сигнатура.

Обращение `obj["anything"]` по индексной сигнатуре возвращает `number`, а не `number | undefined`, если не включён `noUncheckedIndexedAccess`. Этот флаг стоит включать в новых проектах: он честнее, хотя и шумнее.

`Omit<T, K>` **не дистрибутивен** и разрушает discriminated union. `Omit<A | B, "x">` работает с `keyof (A | B)`, то есть только с *общими* ключами, и результат сплющивается. Это частый реальный баг. Решение — дистрибутивная обёртка:

```ts
type DistributiveOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;
```

Ещё одна особенность: `Omit` не проверяет, что `K` существует в `T`. Ключ задан как `K extends keyof any`. Это осознанное решение команды TS, и о нём много спорили.

### Prettify — бытовая мелочь, которую знают все

Пересечения и вложенные утилиты в подсказках IDE выглядят ужасно: `Omit<Pick<A, "x">, "y"> & B`. Чтобы «развернуть» тип для чтения, используют такую обёртку:

```ts
type Prettify<T> = { [K in keyof T]: T[K] } & {};
```

Mapped type заставляет компилятор вычислить форму, а `& {}` — распространённый приём, чтобы подсказка точно показала развёрнутый объект. На семантику обёртка не влияет.

## Часть 5. Template literal types

### Основа (TS 4.1+)

```ts
type EventName<T extends string> = `on${Capitalize<T>}`;
type Q = EventName<"click">;  // "onClick"

type Size  = "sm" | "md" | "lg";
type Color = "red" | "blue";
type Cls   = `${Size}-${Color}`;  // 6 вариантов: декартово произведение
```

Подстановка union в шаблон даёт **декартово произведение**. Встроенные **intrinsic**-типы `Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize` реализованы прямо в компиляторе, а не на языке типов.

Можно использовать и широкие типы как «паттерны»:

```ts
type CssVar = `--${string}`;
const ok: CssVar = "--main-color";
type Px = `${number}px`;
```

### Парсинг строк через `infer`

Это то, что делает TanStack Router, Hono и подобные библиотеки:

```ts
type RouteParams<S extends string> =
  S extends `${string}:${infer Param}/${infer Rest}`
    ? Param | RouteParams<`/${Rest}`>
    : S extends `${string}:${infer Param}`
      ? Param
      : never;

type R = RouteParams<"/users/:id/posts/:postId">;  // "id" | "postId"
```

Как сопоставляются шаблоны:

- `infer`-переменная, за которой идёт литерал, захватывает минимальную подстроку до первого вхождения этого литерала;
- последняя переменная забирает остаток.

Знать это нужно, чтобы предсказывать, как разберётся строка с несколькими разделителями.

### Ограничения

У union'ов есть потолок — около 100 000 членов. Произведение пары union'ов по 500 элементов даёт ошибку «Expression produces a union type that is too complex to represent». Задолго до этого предела тормозит редактор.

Template literal types — мощный инструмент для DSL, но генерировать ими «все возможные CSS-классы Tailwind» — плохая идея.

## Часть 6. Рекурсивные типы

### Рекурсивные структуры данных

```ts
type Json =
  | string | number | boolean | null
  | Json[]
  | { [key: string]: Json };
```

Рекурсивные алиасы в такой форме работают давно. Ограничения постепенно снимались, и с TS 3.7 такая запись в целом допустима.

### Рекурсивные conditional types (TS 4.1+)

```ts
type DeepReadonly<T> =
  T extends (...args: any[]) => any ? T :
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;

type Flatten<T> = T extends readonly (infer U)[] ? Flatten<U> : T;
```

Обратите внимание на ветку для функций. Без неё функции превратятся в объект без сигнатуры вызова: функция — это `object`, а mapped type по её ключам теряет callable-часть. Это footgun во всех самописных Deep-утилитах. Ещё одна частая проблема — `Date`, `Map` и `Set`, которые тоже стоит обрабатывать отдельно.

### Пути к полям — популярная задача

```ts
type Paths<T> = T extends object
  ? { [K in keyof T & string]:
        T[K] extends object ? K | `${K}.${Paths<T[K]>}` : K
    }[keyof T & string]
  : never;

type S = Paths<{ user: { name: string; address: { city: string } } }>;
// "user" | "user.name" | "user.address" | "user.address.city"
```

Здесь виден ещё один важный паттерн: **mapped type + немедленный indexed access** `{...}[keyof T]`. Он превращает объект «ключ → результат» в union результатов. Это идиома «map по ключам, затем собрать значения».

### Лимиты глубины и хвостовая рекурсия — слой ниже

Компилятор защищается от бесконечной рекурсии. Ошибка **TS2589: «Type instantiation is excessively deep and possibly infinite»** знакома каждому, кто писал библиотечные типы.

- Обычная рекурсия упирается в глубину порядка нескольких десятков уровней (условно 50–100).
- С TS 4.5 есть **оптимизация хвостовой рекурсии**: если рекурсивный вызов стоит непосредственно в ветке conditional type, без обёртки вроде `Param | Recurse<...>` или `[...]`, компилятор раскручивает рекурсию в цикл. Лимит при этом поднимается примерно до 1000.

Поэтому применяют **паттерн аккумулятора**, как в функциональном программировании:

```ts
// Не хвостовая: результат оборачивается
type Reverse<T extends unknown[]> =
  T extends [infer H, ...infer R] ? [...Reverse<R>, H] : [];

// Хвостовая: результат копится в параметре
type ReverseAcc<T extends unknown[], Acc extends unknown[] = []> =
  T extends [infer H, ...infer R] ? ReverseAcc<R, [H, ...Acc]> : Acc;
```

Сюда же относится «арифметика на типах». Числа представляют длиной кортежа: `[unknown, unknown, unknown]["length"]` даёт `3`. Сложение — конкатенация кортежей. Это весело и полезно для тренировки, но в продакшене обычно оказывается признаком того, что вы зашли слишком далеко.

## Часть 7. Branded (nominal, opaque) types

### Проблема

```ts
type UserId = string;
type OrderId = string;
function getUser(id: UserId) {}
const orderId: OrderId = "o-1";
getUser(orderId);  // Компилируется. Структурно это одно и то же.
```

Алиас — это просто другое имя, а не новый тип.

### Решение: бренд

```ts
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };

type UserId  = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

getUser("u-1");                 // Ошибка: у строки нет бренда
getUser(orderId as OrderId);    // Ошибка: бренды разные
```

Пересечение примитива с объектным типом в рантайме не существует: не бывает строки со свойством-символом. Поэтому значение получить честно нельзя, только через утверждение. В этом и смысл: бренд — **фантомный тип**, метка, живущая только в системе типов.

`unique symbol` вместо строкового ключа `__brand` нужен по двум причинам:

- ключ не появится в автодополнении;
- его невозможно случайно подделать литералом объекта.

Вариант с `__brand: "UserId"` — более старый и проще, он по-прежнему широко распространён.

### Как значения получают бренд

Только через контролируемые точки, так называемые **smart constructors**:

```ts
function toUserId(s: string): UserId {
  if (!/^u-\d+$/.test(s)) throw new Error("bad id");
  return s as UserId;
}

// или type guard
function isEmail(s: string): s is Email { return s.includes("@"); }

// или assertion function
function assertPositive(n: number): asserts n is Positive {
  if (n <= 0) throw new Error();
}
```

На практике бренды обычно ставят на границе системы, вместе с валидацией. В Zod это `z.string().uuid().brand<"UserId">()`. В Effect есть модуль `Brand`, в Valibot — `v.brand`. Главная идея: **parse, don't validate**. Проверили один раз на границе, закодировали факт проверки в типе и дальше в доменном коде больше не проверяете.

### Footguns брендов

- **Арифметика стирает бренд.** `(a: Cents) + (b: Cents)` даёт `number`, а не `Cents`, потому что операторы работают с базовым типом. Нужны функции-помощники.
- **Рантайм ничего не знает.** После `JSON.parse`, в ответах API, в данных из базы брендов нет. Если просто написать `as UserId` над внешними данными, вы получите ложное чувство безопасности.
- **Каст как спасательный люк.** `as UserId` в любом месте кодовой базы обесценивает идею. В хороших командах это ловят на ревью или линтером.
- **Совместимость в обратную сторону.** `UserId` *присваивается* в `string`, ведь это подмножество. Бренд защищает в одну сторону, и обычно именно это и нужно.

## Часть 8. Что происходит под капотом и почему это важно

**Инстанцирование и кэширование.** Каждый `F<X>` компилятор инстанцирует: подставляет аргументы и вычисляет результат. Результаты кэшируются по идентичности аргументов. Интерфейсы имеют имя и кэшируются эффективнее. Пересечения (`A & B & C`) компилятор каждый раз вынужден «сплющивать» и проверять заново. Поэтому официальный гайд команды TS по производительности советует **предпочитать `interface extends` пересечениям** для больших объектных типов.

**Проверка вариантности.** Проверяя `Foo<A>` против `Foo<B>`, компилятор не сравнивает структуры целиком. Он один раз вычисляет вариантность параметра через маркерные типы и дальше сравнивает только аргументы. Отсюда редкие ошибки, когда вычисленная вариантность неточна. Как раз для этого и появились аннотации `in`/`out`.

**Выведение и контекст.** Вывод дженерик-аргументов идёт по кандидатам с приоритетами. Если нужно повлиять на вывод, пригодятся современные инструменты:

- `const T` (TS 5.0): `function f<const T>(x: T)` выводит литеральные и readonly-типы, как будто вызывающий написал `as const`;
- `NoInfer<T>` (TS 5.4): помечает позицию, из которой не нужно выводить `T`. Классический пример — `createFSM<S extends string>(states: S[], initial: NoInfer<S>)`;
- `satisfies` (TS 4.9): проверяет соответствие типу без расширения выведенного типа. Это стало стандартом для конфигов и словарей.

**Диагностика производительности.** Когда сложные типы тормозят IDE, используют:

- `tsc --extendedDiagnostics` — счётчики инстанцирований и время;
- `tsc --generateTrace ./trace` плюс `@typescript/analyze-trace` или просмотр в Perfetto — какие именно типы горячие.

Без этих инструментов разговор о производительности типов — гадание.

**Горизонт.** Microsoft переписывает компилятор на Go: Project Corsa, будущий TypeScript 7, `tsgo`, обещано ускорение порядка 10×. Язык типов от этого не меняется, но «это слишком медленно, не делай так» будет звучать реже. На момент знакомства с этим уроком сверьтесь со статусом: переход идёт поэтапно.

## Часть 9. Как это выглядит в реальной работе

### Где живёт сложная типизация

Почти вся она живёт в **библиотеках**:

- **tRPC** выводит типы клиента из роутера сервера;
- **Zod**, **Valibot**, **ArkType** выводят TS-тип из схемы (`z.infer<typeof schema>`); ArkType вообще парсит строковые определения типов template literal'ами;
- **Prisma**, **Drizzle**, **Kysely** типизируют результаты запросов по выбранным полям;
- **TanStack Router** и **Hono** парсят пути;
- **ts-pattern** реализует exhaustive pattern matching;
- **type-fest** — актуальная коллекция утилит (`SetRequired`, `Simplify`, `PartialDeep`, `Paths` и другие).

В **прикладном коде** хорошая практика — сдержанность: discriminated unions, `satisfies`, умеренные mapped types, бренды для идентификаторов и денег. Если в продуктовом коде тип занимает 30 строк рекурсии, на ревью обычно спросят: «а кто это будет поддерживать?»

### Тестирование типов

Сложные типы — это код, и его тестируют:

```ts
// В Vitest
import { expectTypeOf } from "vitest";
expectTypeOf<RouteParams<"/a/:id">>().toEqualTypeOf<"id">();

// Без библиотек
// @ts-expect-error — строка ДОЛЖНА давать ошибку
getUser("raw-string");
```

Знаменитый трюк строгого равенства из сообщества type-challenges:

```ts
type Equal<X, Y> =
  (<T>() => T extends X ? 1 : 2) extends (<T>() => T extends Y ? 1 : 2) ? true : false;
```

Наивное `X extends Y ? Y extends X ? ...` даёт ложные срабатывания с `any` и с пересечениями. Этот трюк опирается на внутреннее сравнение отложенных conditional types на идентичность.

Инструменты: `expect-type` (на нём построен `expectTypeOf` в Vitest) и `tsd`, более старый, но живой.

Лучшая тренировка — репозиторий **type-challenges** (уровни easy/medium/hard/extreme). Medium-уровень — нормальная планка для мидл+. Hard — уровень авторов библиотек.

### Конвенции, которые стоит знать

- Однобуквенные параметры для простых случаев (`T`, `K`, `V`), осмысленные имена для сложных (`TInput`, `TContext`). Префикс `T` популярен в экосистеме TanStack и tRPC.
- Внутренние вспомогательные типы не экспортируют или помечают как internal.
- Нормально писать перегрузки или каст в реализации и честный сложный тип в сигнатуре.
- С `isolatedDeclarations` (TS 5.5) экспортируемые функции требуют явных типов возврата. Это ещё одна причина давать сложным выведенным типам имена.

## Часть 10. Спорные места («it depends»)

**Сколько магии на уровне типов допустимо?** В библиотеке, где типы и есть продукт, допустимо много. В приложении — мало. Аргументы против глубокой магии:

- непонятные сообщения об ошибках у потребителя (ошибка в 40 строк про `Paths<...>`);
- медленная IDE;
- высокий порог входа для команды.

Хорошие авторы библиотек тратят на *качество ошибок* столько же сил, сколько на сами типы.

**Branded types или классы-обёртки?** Бренды ничего не стоят в рантайме, но не защищают от кастов и внешних данных. Классы вроде `class UserId { constructor(readonly value: string) {} }` дают настоящую номинальность через private-поля и рантайм-проверку `instanceof`. Платить за это приходится аллокациями и неудобной сериализацией. В TS-мире чаще выбирают бренды плюс валидацию на границе.

**`interface` или `type`?** Многолетний спор. Позиция, с которой трудно спорить:

- `interface` — для объектных форм, особенно публичных и расширяемых. Его можно дополнять через declaration merging, он быстрее кэшируется, и ошибки с ним читаются лучше;
- `type` — для union'ов, mapped и conditional types, кортежей, всего вычисляемого.

Многие команды просто выбирают одно для объектов и фиксируют выбор в линтере (`@typescript-eslint/consistent-type-definitions`). Важнее консистентность, чем выбор.

**`enum` или union литералов?** Тренд однозначно в пользу union'ов (`type Role = "admin" | "user"`) или объектов `as const`:

```ts
const Role = { Admin: "admin", User: "user" } as const;
type Role = typeof Role[keyof typeof Role];
```

Причины:

- `enum` генерирует рантайм-код;
- числовые enum'ы небезопасны (в старых версиях в них присваивалось любое число);
- enum'ы несовместимы с режимом «просто стереть типы». Нативный type stripping в Node и флаг `erasableSyntaxOnly` (TS 5.8) запрещают enum, namespace и parameter properties.

Защитники enum'ов говорят о читаемости и рефакторинге, и это легитимная позиция в старых кодовых базах.

**`any` или `unknown`?** В значениях — `unknown`, почти всегда. В constraint'ах дженериков `any` иногда *корректнее*: см. пример с функциями выше. Знать это различие — признак зрелости. Догматичное «any запрещён везде» ведёт к неработающим constraint'ам.

## Часть 11. Актуальное и устаревшее

**Современное (используйте):**

- `satisfies` (4.9);
- `const` type parameters (5.0);
- `NoInfer` (5.4);
- inferred type predicates (5.5): `arr.filter(x => x !== null)` наконец сужает тип;
- `infer X extends C` (4.7);
- key remapping через `as` (4.1);
- хвостовая рекурсия (4.5);
- `Awaited` (4.5);
- `unique symbol`-бренды;
- `noUncheckedIndexedAccess`;
- `expectTypeOf`;
- type-fest;
- `erasableSyntaxOnly` и `verbatimModuleSyntax`.

**Устаревшее или осторожно:**

- самописные `ReturnType`-подобные утилиты, когда есть встроенные;
- `ts-toolbelt` — огромный и мощный, но развивается заметно медленнее, в новых проектах чаще берут type-fest;
- старые трюки обхода лимитов рекурсии вроде вложенных объектов-«лестниц» до 4.1/4.5;
- `namespace` для организации кода;
- числовые `enum`;
- типы `Function`, `Object`, `{}` как «любой объект»: используйте `(...args: any[]) => unknown`, `object` или `Record<string, unknown>`. Помните, что `{}` означает «всё, кроме null и undefined», включая строки;
- `as Type` на внешних данных вместо парсинга схемой.

## Часть 12. Сводка footguns

1. `T extends never` в дистрибутивном типе на `never` даёт `never`. Пишите `[T] extends [never]`.
2. Дистрибутивность по `boolean` и по union'ам, которых вы не ждали. Обёртка в кортеж её отключает.
3. `any` в conditional type даёт объединение обеих веток.
4. `Omit` и `keyof` на union'е работают только с общими ключами. Используйте дистрибутивный Omit.
5. `as`-клауза в mapped type ломает обработку массивов и кортежей.
6. Deep-утилиты, не обрабатывающие функции, `Date`, `Map` и `Set`.
7. `keyof` включает `number` и `symbol`. В template literal пишите `K & string`.
8. Conditional type в возвращаемом типе не сужается по рантайм-проверке. Нужны перегрузки или каст в реализации.
9. Бренд теряется при арифметике и отсутствует в данных извне.
10. Методы проверяются бивариантно, свойства-функции — контравариантно.
11. Декартово произведение template literal'ов взрывается.
12. TS2589. Перепишите рекурсию в хвостовую с аккумулятором или упростите тип.
13. Пересечение несовместимых примитивов (`string & number`) молча даёт `never`. Пересечение объектов с конфликтующим полем даёт `never` в этом поле, а иногда и весь объект схлопывается в `never`, если поле — дискриминант.

## Часть 13. Рабочий словарь

| Термин | Что значит и как употребляют |
|---|---|
| **assignability** | «A assignable to B» — A подмножество B; основное отношение системы |
| **conditional type** | `T extends U ? X : Y` |
| **distributive conditional type** | распределяющийся по union'у; говорят «дистрибутивный» |
| **naked type parameter** | голый `T` в проверке; условие дистрибутивности |
| **deferred** | отложенный, невычисленный из-за неизвестного дженерика |
| **mapped type** | `{ [K in ...]: ... }`; по-русски часто так и говорят — «мапнутый тип» |
| **homomorphic mapped type** | mapped type по `keyof T`; сохраняет модификаторы и кортежи |
| **key remapping** | `as` в mapped type |
| **indexed access type** | `T[K]` |
| **template literal type** | строковый шаблон на уровне типов |
| **intrinsic** | встроенный в компилятор тип вроде `Uppercase` |
| **infer** | захват подтипа при сопоставлении |
| **variance** (co-/contra-/in-/bi-) | направление подтипирования параметров |
| **brand / opaque / nominal / phantom type** | близкие понятия: метка, делающая структурно одинаковые типы различимыми; «phantom» подчёркивает, что метки нет в рантайме |
| **smart constructor** | функция, валидирующая значение и выдающая бренд |
| **discriminated (tagged) union** | union объектов с общим литеральным полем-тегом |
| **narrowing** | сужение типа по проверкам в потоке управления |
| **exhaustiveness check** | проверка полноты через присваивание в `never` в `default` |
| **widening** | расширение литерала `"a"` до `string`; против него — `as const` и `const T` |
| **type-level programming** | программирование на языке типов; ироничное «type gymnastics» — когда перебор |

## Как двигаться дальше

1. Пройдите type-challenges уровня easy полностью и medium хотя бы наполовину. После этого синтаксис станет «родным».
2. Прочитайте исходники типов одной знакомой библиотеки. `z.infer` в Zod или `RouteParams` в Hono — хорошие кандидаты. Вы увидите все паттерны из этого урока в боевом виде, вместе с компромиссами ради читаемых ошибок.
3. Внедрите в рабочий проект бренды для идентификаторов вместе со схемой на границе и `noUncheckedIndexedAccess`. Это даёт наибольшую практическую пользу на единицу сложности.
4. Научитесь пользоваться `--generateTrace`. Умение ответить на вопрос «почему у нас тормозит IDE» конкретно, а не на ощущениях — один из самых убедительных сигналов senior-уровня в этой области.

Последняя мысль, которая отличает зрелого специалиста: владеть системой типов на этом уровне нужно не для того, чтобы применять её везде. Нужно понимать, *когда* сложный тип окупается: в библиотеках, на границах систем, в местах частых ошибок. И когда честная перегрузка или простой union лучше элегантной рекурсии.
