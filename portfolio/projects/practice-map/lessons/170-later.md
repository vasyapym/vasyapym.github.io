# Later
The departures page for a small station shows the next six trains and has a Refresh button. The button's handler is an async function. Its first line dims the list already on the screen, and its second is the one that matters:

const response = await fetch('/departures');

At 18:41 on a Tuesday someone presses Refresh. The browser writes the click down — which button, where, when — at the end of a queue it keeps, and when the thread that runs the page's JavaScript has nothing in hand, it reads the note, finds the handler, and calls it.

The handler dims the list and calls fetch. fetch is not JavaScript. Neither is the button, nor setTimeout, nor console.log. The language has no network, no screen, and no clock that can call it back later; everything of that kind belongs to the program it lives inside — the host: here the browser, on a server usually Node. So the request goes to the browser's network code, which runs on threads of its own, and what fetch hands back, at once, is a promise: an object with nothing in it yet, standing in for a response that does not exist.

await, given an object like that, does two things, and neither is waiting. It attaches the rest of the function — the assignment and everything below it — to the promise, as what to do once the promise is settled. Then it returns. The handler is over, as far as the thread is concerned, and the thread goes back to the queue. JavaScript does one thing at a time and never waits: anything slow is handed to the host it lives in, and the answer comes back as a note in a queue, read when the current work is finished — a promise is simply the object that stands in for the answer until it arrives.

For the next two hundred milliseconds the thread does what the queue says. It repaints the page, which is when the dimmed list is seen to dim. It handles a scroll. It handles nothing from the departures function, because there is nothing of it to handle: the rest of that function is pinned to a promise, not to the thread. Nothing froze. There was nothing on the thread to freeze.

The response arrives on the network thread, which leaves a note. The thread reads it, settles the promise, and the rest of the function falls due. Follow-ups to promises have a short queue of their own, read to the end before the thread returns to the long one, so the rest of the handler runs ahead of any click that arrived meanwhile. It runs as far as response.json(), which hands the body to the browser to parse — another promise, another await, another return — and the third piece writes six trains into the page. One function, three pieces, one thread, free in between.

In 2015 the same thing was written fetch('/departures').then(response => …), with the rest of the function inside the parentheses and a function inside that for each further step. await, two years later, attaches the same rest to the same promise. The difference is where the rest is written: underneath instead of inside.

The board also refreshes itself. setTimeout(refresh, 60000) asks the browser to leave a note in a minute, and in a minute at the soonest: the note goes to the end of the queue when it is written, behind whatever is already there, and is read when the thread gets to it. Asked for zero milliseconds, the browser writes the note at once, and it still goes to the end of the queue. Zero means later, and later means after whatever is already there.

The other side of never waiting is that the thread is never interrupted. If a handler sorts a million rows itself, no note is read until it is done; the clicks made during the sort are not lost but written down, and each is handled, in order, afterwards. The browser's standard describes this loop — one note, to completion, then the next — and calls it the event loop. The language's standard has no loop in it; it requires only that the host run promise follow-ups, in order, when nothing else is running. The loop is the host's. Node has one too, in a C library called libuv.

There is no way to wait a second in JavaScript, and the line everyone copies for it is await new Promise(r => setTimeout(r, 1000)). It asks the host for a note in a second, makes a promise that will be settled when the note is read, and leaves. The thread is free for the whole second. The waiting is done by the browser's clock, which is not JavaScript.
