# Multi-Tenancy в Laravel: один урок

Если вы думаете, что multi-tenancy — это «добавить `tenant_id` в таблицы», вы мыслите на уровне junior/middle. На уровне senior multi-tenancy — это не фича, а **архитектурный режим всего приложения**: почти каждый запрос, job, команда, кэш, файл, лог и миграция начинают зависеть от неявного вопроса — *в контексте какого тенанта мы сейчас работаем?*

Хорошая ментальная модель такая:

> **Tenant context — это ambient state, глобальная переменная окружения на стероидах. Как `auth()->user()` или локаль, только опаснее: она переключает базу, кэш, файловую систему, очереди и права доступа.**

Отсюда всё остальное.

---

## 1. Базовая ментальная модель: control plane и data plane

Опытные люди делят систему на две плоскости.

**Central / landlord context** — «центральный» контекст. Control plane. Здесь живут:
- реестр тенантов: таблица `tenants`, `domains`;
- биллинг, тарифы, подписки, инвойсы Stripe/Paddle;
- супер-админка платформы;
- provisioning: создание тенанта, его базы/схемы, первичный seed;
- вебхуки платёжных систем.

**Tenant context** — data plane. Обычная бизнес-логика конкретного клиента: его пользователи, заказы, документы, настройки, файлы.

Ключевая фраза, которую senior скажет на ревью: **«Эта таблица центральная, тенантная или глобально-справочная?»** Классификация каждой таблицы — первое действие при проектировании:

| Тип таблицы | Примеры | Где живёт |
|---|---|---|
| Central-only | `tenants`, `domains`, `plans`, `subscriptions` | только центральная БД |
| Tenant-owned | `orders`, `projects`, `invoices` внутри продукта | тенантная БД или с `tenant_id` |
| Global shared reference | `countries`, `currencies`, `timezones` | справочники; в DB-per-tenant их приходится реплицировать |

Жизненный цикл любого входа в систему senior видит так:

```
Identify → Resolve → Initialize → Bootstrap resources → Execute → End/Teardown
```

Определить идентификатор (поддомен, юзер, header) → найти тенанта → инициализировать контекст → переключить DB/cache/filesystem/queue → выполнить код → **обязательно сбросить контекст**.

Последний шаг критичен в long-lived процессах: queue-воркеры, Laravel Octane, FrankenPHP, Horizon. В классическом PHP-FPM процесс умирает после запроса и «прощает» забывчивость. В Octane и очередях забытый teardown = **утечка данных чужого тенанта в следующий job**. Это самый страшный класс багов в этой области.

## 2. Рабочий словарь и его нюансы

- **Tenant** — арендатор: компания/клиент, чьи данные изолируются. Не «пользователь». Один тенант — много пользователей.
- **Tenancy** — механизм/режим мультитенантности в целом.
- **Tenant identification** — *как* мы поняли, кто тенант (поддомен `acme.app.com`, кастомный домен, юзер). **Resolution** — *нашли запись* тенанта по идентификатору. **Initialization** — *переключили* приложение в его контекст. Новички смешивают три шага; senior разделяет, потому что падают они по-разному.
- **Tenant-aware** — код/компонент, который знает о контексте (job, команда, listener). **Tenant-agnostic** — код, который работает вне контекста осознанно (вебхук биллинга, центральная админка). Опасен код, который *думает*, что он aware, а на деле нет.
- **Central database** (у spatie — `landlord`, термин уходит в legacy) — центральная БД.
- **Tenant scope / scoping** — автоматическая фильтрация запросов по текущему тенанту.
- **Provisioning** — процесс создания тенанта: запись, база, миграции, seed, первый админ, домен.
- **Cross-tenant query** — запрос поперёк тенантов (аналитика платформы). В одних архитектурах тривиален, в других — боль.
- **Noisy neighbor** — шумный сосед: один тяжёлый тенант кладёт производительность всем, потому что сервер/БД общие, даже если базы разные.

---

## 3. Спектр изоляции: три главные модели

Это центральное «it depends» всей темы. Изоляция — спектр, а не бинарный выбор.

### 3.1. Single database, shared schema (row-level, discriminator column)

Одна БД, у каждой тенантной таблицы `tenant_id`, все запросы фильтруются.

**Плюсы:** простейшая эксплуатация, одна миграция, тривиальная cross-tenant аналитика, быстрые тесты, дёшево масштабируется до тысяч мелких тенантов.
**Минусы:** изоляция — только дисциплина кода. Забыли scope в одном запросе — утечка. Бэкап/восстановление одного тенанта — хирургия. GDPR-удаление одного клиента — `DELETE` по всем таблицам.

### 3.2. Database per tenant

У каждого тенанта своя БД (`tenant_acme`, `tenant_umbra`), центральная хранит только реестр. Дефолтная модель stancl/tenancy.

**Плюсы:** изоляция на уровне инфраструктуры: даже кривой запрос физически не достанет чужие данные. Удалить тенанта = `DROP DATABASE`. Восстановить одного = восстановить одну базу. Можно вынести жирного тенанта на отдельный сервер. Для регулируемых отраслей (финтех, мед) это часто не выбор, а требование.
**Минусы:** миграции выполняются N раз (на 5 000 тенантов деплой превращается в фоновую операцию с *schema version skew* — часть баз уже на новой схеме, код должен быть обратно-совместим: expand/contract миграции обязательны). Cross-tenant аналитика = агрегировать извне (ETL в отдельное хранилище). Пул соединений, мониторинг, бэкапы — всё ×N.

### 3.3. Schema per tenant (в основном PostgreSQL)

Одна БД, у тенанта своя схема, переключается `search_path`. Промежуточный вариант: изоляция сильнее row-level, эксплуатация легче DB-per-tenant. В MySQL «схема» ≈ база, поэтому модель почти не встречается. В Laravel поддерживается хуже, чаще вручную или через stancl с кастомным bootstrapper-ом.

### 3.4. Гибрид: шардирование по группам

Senior-уровень: тенанты группируются по `shard_id`, внутри шарда — row-level, шардов несколько БД. Так живут большие SaaS. Ещё вариант: 95% тенантов в shared-БД, enterprise-клиенты — на выделенных базах. Вопрос «какая у нас стратегия для тенанта, который вырастет в 100 раз?» отличает senior-дизайн от middle.

**Эвристика выбора:** нет жёстких требований к изоляции и тенантов много/мелкие → row-level. Контрактные/регуляторные требования, тяжёлые или неравномерные тенанты, дорого стоит утечка → DB per tenant. «Нам нужна максимальная изоляция, потому что так солиднее» при 30 мелких клиентах — классический over-engineering, за который платят эксплуатацией годами.

## 4. Что происходит слоем ниже абстракции

Пакеты не творят магию — они делают ровно четыре вещи:

**1. Переключают соединение с БД.** Laravel кэширует соединения в `DatabaseManager` по имени. Поэтому недостаточно поменять конфиг — нужно сбросить старое PDO-соединение:

```php
config(['database.connections.tenant.database' => $tenant->db_name]);
DB::purge('tenant');        // иначе останется PDO прошлого тенанта!
DB::reconnect('tenant');
config(['database.default' => 'tenant']);
```

Забытый `purge()` в воркере очереди — утечка между тенантами. Именно это автоматизируют bootstrappers в stancl (`DatabaseTenancyBootstrapper`) и tasks в spatie (`SwitchTenantDatabaseTask`).

**2. Префиксят кэш и Redis.** Ключ `dashboard_stats` без тенантного префикса — один тенант видит кэш другого. Stancl: `CacheTenancyBootstrapper` добавляет префикс `tenant{id}_`. Spatie: `PrefixCacheTask`.

**3. Суффиксят файловую систему.** `storage/app/tenant{id}/...`, отдельный префикс в S3-бакете. Иначе публичные URL и сгенерированные пути текут между тенантами (`FilesystemTenancyBootstrapper`).

**4. Прокидывают контекст в очередь.** При диспатче job-а в payload пишется `tenant_id`; при обработке воркер *до* выполнения job-а инициализирует этот тенант (`QueueTenancyBootstrapper`). Без этого job выполнится в центральном контексте — в лучшем случае упадёт, в худшем запишет данные не туда.

В Postgres schema-модели вместо смены базы выставляется `search_path` на соединении — и та же проблема пулинга (PgBouncer в transaction mode) может вернуть соединение с чужим `search_path`.

## 5. Три практических пути в Laravel

### 5.1. Вручную (row-level) — недооценённый вариант

Для single-DB модели пакет часто не нужен. Ядро — трейт с global scope:

```php
trait BelongsToTenant
{
    protected static function booted(): void
    {
        static::addGlobalScope('tenant', function (Builder $q) {
            if ($tenantId = app('tenant_id')) {           // контекст из middleware
                $q->where($q->getModel()->getTable().'.tenant_id', $tenantId);
            }
        });

        static::creating(function ($model) {
            $model->tenant_id ??= app('tenant_id');
        });
    }

    public function tenant(): BelongsTo
    {
        return $this->belongsTo(Tenant::class);
    }
}
```

Нюансы, которые спросят на ревью:
- **Global scope работает только в Eloquent.** `DB::table('orders')`, raw-запросы, отчёты на query builder, Scout, Excel-экспорты — всё это scope обходит. Row-level — не граница безопасности, а дисциплина. Для defense-in-depth в Postgres добавляют **RLS (Row Level Security)**: политика `USING (tenant_id = current_setting('app.tenant_id')::bigint)` на уровне самой БД.
- Уникальность становится составной: не `unique('email')`, а `unique(['tenant_id', 'email'])`. Один email может быть пользователем у десяти тенантов.
- Композитные индексы всегда с `tenant_id` **первым**: `index(['tenant_id', 'created_at'])` — равенство по тенанту, дальше сортировки/диапазоны внутри него.
- Route model binding со scope автоматически отдаёт **404** на чужой ID. Это правильно: 403 подтверждает существование чужой записи, 404 — нет.

### 5.2. stancl/tenancy («Tenancy for Laravel») — стандарт для DB-per-tenant

Самый популярный пакет, фактически фреймворк внутри фреймворка. Даёт из коробки: идентификацию по домену/поддомену/пути, bootstrappers для DB/cache/FS/Redis/queue, provisioning через события и JobPipeline.

```php
class Tenant extends BaseTenant implements TenantWithDatabase
{
    use HasDatabase, HasDomains;
}

// Provisioning — одна строка, остальное делает pipeline событий:
// создать БД → прогнать тенантные миграции → seed
$tenant = Tenant::create(['id' => 'acme']);
$tenant->domains()->create(['domain' => 'acme.yourapp.com']);
```

Конвенции: центральные роуты — в `routes/web.php`, тенантные — в `routes/tenant.php` под middleware `InitializeTenancyByDomain` и `PreventAccessFromCentralDomains` (чтобы с центрального домена нельзя было попасть в тенантные роуты и наоборот). Миграции делятся: `database/migrations` (центральные) и `database/migrations/tenant`. Команды: `tenants:migrate`, `tenants:seed`, `tenants:run`. Ручное управление: `tenancy()->initialize($tenant)` / `tenancy()->end()`.

Сила stancl — полнота. Слабость — та же полнота: много магии, нужно реально понимать bootstrappers, а не верить им.

### 5.3. spatie/laravel-multitenancy — конструктор

Философия противоположная: нет готовой идентификации роутов и «волшебного» provisioning-а, зато есть модульный pipeline **Tasks**: `SwitchTenantDatabaseTask`, `PrefixCacheTask` и т.д., которые вы собираете и можете заменить своими. Текущий тенант: `$tenant->makeCurrent()`, `Tenant::current()`, `forgetCurrent()`. TenantFinder-ы (по домену и др.) тоже есть, но интеграцию с роутингом делаете сознательно сами.

**Как выбирать:** нужен готовый SaaS с поддоменами и базой на тенанта «вчера» — stancl. Нужен контроль, нестандартная идентификация (тенант из аутентифицированного юзера в API), single-DB или своя логика переключения — spatie или вообще вручную. Гнаться за stancl ради row-level модели — тащить лишнюю сложность.

## 6. Идентификация тенанта: где прячется источник истины

| Стратегия | Плюсы | Минусы / риски |
|---|---|---|
| Поддомен `acme.app.com` | Стандарт B2B SaaS, контекст виден до логина | Wildcard DNS + wildcard SSL, cookie-сессии между поддоменами |
| Кастомный домен `crm.acme.com` | White-label, enterprise-фича | Верификация домена (CNAME/TXT), выпуск сертификатов — отдельный provisioning |
| Путь `app.com/acme/...` | Просто, один домен | Конфликты роутов, все URL «грязные», легко ошибиться в генерации ссылок |
| По аутентифицированному пользователю | Идеально для API/мобильных | Тенант неизвестен до логина; юзер в нескольких тенантах — нужен выбор/переключение |
| Header `X-Tenant-ID` | Удобно для API | **Никогда не доверять без проверки membership** — иначе любой шлёт чужой ID и читает чужие данные |

Железное правило безопасности: идентификатор из запроса — это *заявка*, а не *право*. Если тенант определяется из header/параметра, вы обязаны проверить, что аутентифицированный пользователь — member этого тенанта. Поддомен сам по себе тоже не авторизация: авторизация всегда проверяется внутри контекста.

Отдельные случаи вне HTTP, где идентификации «по домену» нет в принципе: **вебхуки Stripe** (тенант резолвится из `metadata`/customer id в payload), **scheduler** (команда обходит всех тенантов циклом и инициализирует каждого), **CLI-команды** (`tenants:run "migrate"`). Senior всегда спрашивает: «А как этот код получит тенанта без запроса?»

## 7. Аутентификация и membership

Самая недооценённая тема. Две модели:

1. **Tenant-local users:** таблица `users` внутри каждой тенантной базы. Один человек в трёх компаниях — три несвязанные учётные записи. Просто, изолированно; в DB-per-tenant иначе почти никак.
2. **Central identity + membership:** пользователи центральные, связь `tenant_user` (membership) с ролью в каждом тенанте. Один логин, переключатель компаний как в Slack/Notion. Удобнее UX, сложнее всё остальное: при переключении тенанта меняется контекст, права берутся из membership, а не из юзера.

Центральный супер-админ, который «заходит посмотреть тенанта», — это **impersonation**: одноразовый подписанный токен, аудит в логах, явный баннер в UI. Имперсонация без аудита — дыра комплаенса.

## 8. Эксплуатация: где проекты умирают

- **Онбординг** должен быть идемпотентной транзакцией-воркфлоу: создали тенанта → базу → миграции → seed → админа. Упало на шаге 3 — нужна возможность повторить/откатить, а не полуживой тенант.
- **Деплой при DB-per-tenant:** `tenants:migrate` по 5 000 баз занимает минуты-часы и идёт *во время* работы старого и нового кода. Отсюда обязательные expand/contract миграции (сначала добавляем nullable-колонку, потом отдельным релизом делаем обязательной).
- **Наблюдаемость:** `tenant_id` — обязательное поле каждого лога (`Log::withContext`), тег в Sentry, метрика в Pulse/Telescope. Без этого дебаг «у клиента X сломалось» превращается в археологию.
- **Бэкапы и offboarding:** в DB-per-tenant бэкап/восстановление/экспорт/удаление тенанта — операции над одной базой, это сильный аргумент для enterprise-продаж. В row-level всё это — ручная хирургия по всем таблицам.
- **Статусы тенанта:** `suspended`/`past_due` проверяются middleware *после* инициализации: тенант найден, но доступ закрыт по биллингу.

**Тестирование.** Главная стратегия — тесты на изоляцию: создаём тенантов A и B, юзера A, объект B и проверяем, что каждый эндпоинт отдаёт 404/пустоту. Такие «cross-tenant leakage tests» должны покрывать API, экспорты, поиск, файлы. DB-per-tenant в тестах дорог (создание баз), поэтому часто тестируют на одном-двух тенантах + `RefreshDatabase` на тенантной схеме, а row-level покрывают массово.

## 9. Главные footguns

1. **Кэш без префикса** — `Cache::remember('stats', ...)` одинаков для всех. Утечка номер один в hand-made tenancy.
2. **Job без контекста** — сохранили `order_id` в job, воркер поднял его в центральной БД. Или хуже: в контексте *предыдущего* job-а другого тенанта.
3. **Забыт `DB::purge()` / teardown** в Octane и воркерах.
4. **Singleton-ы и статика**, закэшировавшие данные тенанта при инициализации приложения.
5. **Публичные файлы** через `Storage::url()` без тенантного префикса; чужие вложения по прямому URL.
6. **Broadcasting:** авторизация приватных каналов (`channels.php`) обязана проверять тенанта канала, а не только юзера.
7. **Scout/Meilisearch:** индекс `orders` общий для всех — нужен префикс индекса или `tenant_id` в фильтре *каждого* запроса.
8. **Raw-запросы и отчёты** мимо Eloquent scope (см. выше).
9. **Уникальный email глобально** в shared-БД — ломает легитимный сценарий «один человек в двух компаниях».
10. **Scheduler без цикла по тенантам**: ежедневный отчёт уходит только «центральному» никому.

Распространённое заблуждение: «поставим пакет — изоляция гарантирована». Пакет переключает инфраструктуру, но если вы в DB-per-tenant модели руками дёргаете центральную БД с объединением данных — вы сами построили мост. И обратное заблуждение: «row-level — это несерьёзно». На row-level живут огромные SaaS; серьёзность измеряется тестами на утечки и дисциплиной, а не количеством баз.

## 10. Спорные вопросы — как рассуждает senior

- **«DB per tenant — всегда лучше?»** Нет. Это покупка изоляции ценой эксплуатационной сложности. Покупать её надо за деньги: требования контракта, регуляторика, размер тенантов.
- **«Пакет или вручную?»** Пакет покупает bootstrappers и provisioning; вручную покупаете прозрачность. Для row-level ручной вариант часто чище; для DB-per-tenant писать свой stancl — безумие.
- **«Поддомены или один домен с выбором компании?»** Поддомен — контекст до логина и глубокие ссылки; выбор после логина — проще мобильным и API. Многие зрелые продукты имеют оба: идентификация по юзеру, а поддомен — косметика.
- **«RLS в Postgres вместо scope-ов?»** RLS — отличная вторая линия обороны, но усложняет пулинг, миграции и дебаг. Senior-ответ: scope для удобства + RLS, если цена утечки высока.

## 11. Current vs legacy

- **hyn/multi-tenant** и старый экосистемный зоопарк Laravel 5-й эры — abandonware. Встретили в проекте — это легаси на миграцию, новый проект на этом не начинают. Оттуда же термин `landlord` вместо `central` — жив в spatie, но в речи чаще «central».
- Актуальная картина: Laravel 11/12, **stancl/tenancy v3** (боевой стандарт; смотрите changelog вашей ветки — API bootstrappers между мажорами менялся) и **spatie/laravel-multitenancy v3/v4**. Концепции из этого урока стабильны между версиями, меняются конфиги.
- Современный контекст: Octane/FrankenPHP сделали teardown контекста обязательным навыком; раньше PHP-FPM многое прощал.

## 12. Вопросы, с которых senior начинает любой tenancy-дизайн

1. Какая гарантия изоляции нужна и кто её требует — мы, контракт или регулятор?
2. Сколько тенантов через год: 50, 5 000, 100 000? Насколько неравномерны их размеры?
3. Нужен ли cross-tenant репортинг и как часто?
4. Каковы SLA на бэкап/восстановление/удаление *одного* тенанта?
5. Как тенант идентифицируется в API, вебхуках, scheduler-е — не только в вебе?
6. Один человек в нескольких тенантах — нормальный сценарий?
7. Что делаем с тенантом, который вырос в 50 раз относительно остальных?

Если на эти вопросы нет ответов — код писать рано, независимо от пакета.

**Итоговый чек-лист перед «мы сделали мультитенантность»:** контекст инициализируется и *сбрасывается* везде (web, queue, scheduler, Octane); кэш/файлы/поиск/бродкаст префиксованы или отскоуплены; есть тесты на cross-tenant утечки; provisioning идемпотентен; миграции обратно-совместимы; в каждом логе есть `tenant_id`; offboarding тенанта — одна понятная процедура.

Освоив эту картину — контекст как ambient state, спектр изоляции, bootstrapping под капотом и цену каждого решения, — вы будете говорить с людьми, которые «в теме», на одном языке: не «какой пакет поставить», а «какая изоляция, какой источник истины для resolution и где teardown».
