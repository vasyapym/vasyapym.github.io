# Inside the If

signup: remove two assertions, add one check

This change deletes two assertions from `signup.ts` — the words `as string`, on lines 13 and 30 — and adds one line. The handler reads two fields out of a submitted form, `form.get('email')` and `form.get('name')`. The compiler has never seen the page. What it knows of `FormData` it reads from a declaration file, a description of the browser written out as types, and the description says `get` returns one of three things — a string, a `File`, or `null` — because a field of that name might be a text box, or a file picker, or not on the form at all.

The assertion on line 13, the email, was redundant. Line 12 reads `if (typeof email !== 'string') return;`. Deleting `as string` from the line below it produces no error, because the compiler already knew. Asked what `email` is on line 13, it does not read a label. It starts at line 13 and reads upward, along every route by which the program could have arrived there, and from the three possibilities strikes out whatever each `if` on the way has ruled out. There is one route to line 13: through line 12 with its test false, since every route on which the test was true left through the `return`. The test being false rules out everything but a string. The assertion was telling the compiler what it had worked out one line earlier.

Every check you write shrinks what a value could be, and inside the branch the type is exactly what you have proved — nothing more, nothing assumed. What is below an `if` that returns is inside its else, whether or not anyone wrote the word; the braces were never the boundary, the routes were. TypeScript has read `return` this way since 2.0, in September 2016. Before that a check was good between the braces of its own `if` and forgotten at the closing one, and a check that returned early proved nothing to the lines below it.

The assertion on line 30, the name, was not redundant. Deleting it produces two errors at once: `'name' is possibly 'null'`, and `Property 'trim' does not exist on type 'File'`. There is no `if` above line 30. The assertion was not repeating a check; it stood where one should have been, and the compiler, told the field was a string, believed it, because an assertion is not a test. It inspects no value. It is a sentence addressed to the compiler alone, and the compiler strips it out with the rest of the types before the program runs — the JavaScript it writes for line 30 is the same, byte for byte, with the assertion as without. On Tuesday a request arrived without a name field, `get` returned `null`, and the next line called `.trim()` on it: `TypeError: Cannot read properties of null (reading 'trim')`. The assertion that had called it a string was not in the file that crashed.

The first repair tried was `if (name === null) return;`, and it removed one error and left the other. The compiler struck `null` from the list — the one thing the check proved — and left `File` standing, which is correct: a file picker called `name` is unlikely, but the check had said nothing about it. The new line 31 is the test from line 12, for `name`. One test disposes of both, because a `File` is an object and `null`, as `typeof` reports it, is one too — the compiler knows what `typeof` says of `null` — and what remains below is a string.

The check could have been written the other way up, with the work inside `if (typeof name === 'string') { … }` and the `return` in an `else`, and the compiler would have read it the same. Inside those braces it knows a string, and no more: not that it is non-empty, not that it is anyone's name. In the `else` it knows `File | null`, the exact remainder. Handle `null` there and what is left is `File`; handle that too and nothing is left, a type the compiler calls `never` — and a line there that accepts only `never` is how a program finds out, before it runs, that a type it owns has grown a fourth possibility.

The `if` on line 31 is the one line in this change that will run. The next request without a name will reach it, and go no further.
