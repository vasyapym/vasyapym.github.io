# Деревья Меркла: послойное объяснение

*От интуиции на пальцах до тонкостей, о которых спорят на конференциях. Каждый слой самодостаточен — читайте до того уровня, который вам нужен.*

---

## Слой 0. Интуиция (для всех)

Представьте библиотеку из миллиона книг. Вы хотите быстро ответить на два вопроса:

1. **«Изменилось ли хоть что-то в библиотеке?»** — не перечитывая все книги.
2. **«Есть ли в библиотеке вот эта конкретная книга?»** — не пересылая собеседнику всю библиотеку.

Дерево Меркла решает обе задачи одним приёмом: у каждой книги берётся «отпечаток пальца» (хеш), отпечатки попарно склеиваются и снова «снимается отпечаток», и так далее, пока не останется один — **корень**. Этот корень размером 32 байта представляет всю библиотеку. Изменили одну букву в одной книге — корень стал другим. А чтобы доказать наличие книги, достаточно показать «тропинку» от неё к корню: log₂(миллион) ≈ 20 отпечатков вместо миллиона.

**Одна фраза:** дерево Меркла — это способ сжать целостность большого набора данных в одно короткое число так, чтобы можно было дёшево доказать, что любой фрагмент входит в этот набор.

## Слой 1. Основы (новичок → уверенный пользователь)

### 1.1. Строительные блоки

**Криптографическая хеш-функция** H (например, SHA-256): принимает данные любой длины, выдаёт фиксированные 256 бит. Ключевые свойства:
- *Детерминированность* — одинаковый вход → одинаковый выход.
- *Стойкость к коллизиям* — вычислительно невозможно найти два разных входа с одним хешем.
- *Стойкость к нахождению прообраза* — по хешу нельзя восстановить вход.
- *Лавинный эффект* — изменение одного бита меняет примерно половину выходных бит.

### 1.2. Конструкция

Есть данные D₁, D₂, …, Dₙ (транзакции, файлы, блоки диска — что угодно).

```
Шаг 1. Листья:        Lᵢ = H(Dᵢ)
Шаг 2. Внутренние узлы: N = H(левый_ребёнок ‖ правый_ребёнок)
Шаг 3. Повторяем, пока не останется один узел — корень (Merkle root).
```

Пример для 4 элементов:

```
                Root = H(N₀₁ ‖ N₂₃)
               /                    \
      N₀₁ = H(L₀‖L₁)            N₂₃ = H(L₂‖L₃)
      /          \               /          \
  L₀=H(D₀)   L₁=H(D₁)      L₂=H(D₂)    L₃=H(D₃)
```

`‖` — конкатенация байтов.

### 1.3. Доказательство включения (Merkle proof / inclusion proof)

Хочу доказать, что D₂ входит в набор с корнем Root. Отправляю:
- сам D₂ (или L₂);
- **путь аутентификации**: список «соседей» на пути к корню — [L₃, N₀₁] с указанием, слева или справа стоит каждый сосед.

Проверяющий вычисляет:
```
L₂ = H(D₂)
N₂₃ = H(L₂ ‖ L₃)       ← L₃ был справа
Root' = H(N₀₁ ‖ N₂₃)   ← N₀₁ был слева
Root' == Root ?  → доказательство принято
```

### 1.4. Почему это круто — цифры

| Операция | Наивно | Дерево Меркла |
|---|---|---|
| Размер «отпечатка» n элементов | n хешей | 1 хеш |
| Доказать включение одного элемента | O(n) данных | O(log n) хешей |
| Проверить включение | O(n) | O(log n) хешей |
| Найти отличающийся элемент между двумя копиями | O(n) сравнений | O(log n) запросов |
| Обновить один элемент и пересчитать корень | O(n) | O(log n) |

Для n = 1 000 000 и SHA-256: доказательство ≈ 20 × 32 байта = 640 байт вместо десятков мегабайт.

### 1.5. Минимальный рабочий код

```python
import hashlib

def H(b: bytes) -> bytes:
    return hashlib.sha256(b).digest()

def build_tree(leaves_data: list[bytes]) -> list[list[bytes]]:
    """Возвращает все уровни дерева, levels[0] — листья, levels[-1] — [root]."""
    level = [H(b"\x00" + d) for d in leaves_data]      # 0x00 — префикс листа (см. Слой 3)
    levels = [level]
    while len(level) > 1:
        if len(level) % 2 == 1:
            level = level + [level[-1]]                # нечётное число — дублируем последний (одна из стратегий)
        level = [H(b"\x01" + level[i] + level[i+1])    # 0x01 — префикс внутреннего узла
                 for i in range(0, len(level), 2)]
        levels.append(level)
    return levels

def get_proof(levels, index: int) -> list[tuple[bytes, str]]:
    proof = []
    for level in levels[:-1]:
        if len(level) % 2 == 1:
            level = level + [level[-1]]
        sibling = index ^ 1                            # сосед: флипаем младший бит
        side = "L" if sibling < index else "R"
        proof.append((level[sibling], side))
        index //= 2
    return proof

def verify(root: bytes, data: bytes, proof) -> bool:
    h = H(b"\x00" + data)
    for sibling, side in proof:
        h = H(b"\x01" + (sibling + h if side == "L" else h + sibling))
    return h == root

# Демо
data = [b"tx0", b"tx1", b"tx2", b"tx3", b"tx4"]
levels = build_tree(data)
root = levels[-1][0]
p = get_proof(levels, 2)
print(verify(root, b"tx2", p))        # True
print(verify(root, b"tx9", p))        # False
```

## Слой 2. Рабочий процесс: что должен знать практик

### 2.1. Где это живёт (и зачем именно там)

| Система | Роль дерева Меркла |
|---|---|
| **Bitcoin** | Merkle root транзакций в заголовке блока. SPV-клиенты (лёгкие кошельки) проверяют платёж по 80-байтовым заголовкам + proof, не качая блокчейн. |
| **Ethereum** | Modified Merkle Patricia Trie для состояния, транзакций, чеков. Даёт не только доказательства включения, но и **доказательства отсутствия** (ключа нет). |
| **Git** | Каждый коммит — хеш дерева объектов (tree → blob). Технически это Merkle DAG, а не дерево. Хеш коммита = целостность всей истории. |
| **IPFS / Docker layers** | Content addressing: адрес = хеш содержимого; структура — Merkle DAG. Дедупликация «бесплатно». |
| **Certificate Transparency (RFC 6962)** | Append-only лог сертификатов. Кроме inclusion proof есть **consistency proof** — доказательство, что новая версия лога содержит старую как префикс (никто не переписал историю). |
| **ZFS / Btrfs** | Каждый блок хранит хеш детей → self-validating дерево; обнаружение битрота и «фантомных записей». |
| **Cassandra, DynamoDB, Riak** | Anti-entropy repair: реплики сравнивают деревья Меркла своих диапазонов ключей и синхронизируют только расходящиеся поддеревья. |
| **BitTorrent v2, Dat/Hypercore** | Верификация кусков файла по мере скачивания без полного файла. |
| **SPHINCS+, XMSS** | Постквантовые подписи на хешах: дерево Меркла аутентифицирует тысячи одноразовых ключей одним публичным ключом. |
| **zk-STARK (FRI), Plonky2** | Прувер коммитит к полиному деревом Меркла; верификатор запрашивает случайные точки с proof'ами. |

### 2.2. Проектные решения, которые придётся принимать

**1. Хеш-функция.** SHA-256 — дефолт. Blake3 — быстрее и параллелится (сам внутри — дерево Меркла). Keccak — если EVM-совместимость. Poseidon/Rescue — если дерево доказывается внутри zk-схемы (арифметически дешёвые хеши).

**2. Нечётное число листьев.** Три школы:
- *Дублировать последний узел* (Bitcoin). Просто, но породило CVE-2012-2459 (см. Слой 3).
- *Поднимать одинокий узел на уровень выше без хеширования* (RFC 6962, CT). Дерево становится несбалансированным, но детерминированным и без дублей.
- *Дополнять до степени двойки пустыми листьями* с фиксированным значением (многие zk-системы, sparse trees).

Все три дают **разные корни** для одинаковых данных. Несовместимость реализаций — классический баг интеграции.

**3. Арность (k-арное дерево).** Бинарное — минимальный размер proof'а по числу хешей, но глубже. В zk-контексте часто берут арность 4–16: меньше уровней, а хеш широкого входа стоит немногим дороже.

**4. Упорядоченность листьев.**
- *По позиции* (Bitcoin, CT): нужен индекс, можно доказать порядок, нельзя доказать отсутствие.
- *По ключу / сортированные* (Merkle Patricia, Sparse Merkle Tree): можно доказать отсутствие, поддерживают map-семантику.

**5. Что именно вы храните.** Всё дерево (O(n) памяти, быстрые proof'ы) vs только корень + пересчёт vs только «граница» (frontier) для append-only структур (O(log n) памяти — как в Ethereum deposit contract).

### 2.3. Типичный жизненный цикл

```
Издатель:                             Проверяющий (лёгкий клиент):
1. Собрал данные D₁..Dₙ               1. Получил root по доверенному каналу
2. Построил дерево, опубликовал root     (заголовок блока, подпись сервера, on-chain)
3. Сохранил дерево (или frontier)     2. Запросил Dᵢ + proof у НЕдоверенного источника
4. По запросу выдаёт Dᵢ + proof       3. Пересчитал путь → сравнил с root
                                      4. Принял/отверг
```

**Ключевая модель доверия:** корень доставляется через доверенный (дорогой) канал; данные и proof — через недоверенный (дешёвый). Дерево переносит доверие с канала на криптографию.

### 2.4. Чек-лист перед продакшеном

- [ ] Домен-разделение листьев и внутренних узлов (префиксы `0x00`/`0x01` или разные хеш-функции).
- [ ] Зафиксирована и задокументирована стратегия нечётных уровней.
- [ ] Proof содержит или однозначно вычисляет направление (лево/право) для каждого шага. Индекс листа — часть публичного интерфейса.
- [ ] Ограничена максимальная глубина дерева при верификации (защита от DoS длинными proof'ами).
- [ ] Тестовые векторы совместимы с эталонной реализацией (если протокол чужой).
- [ ] Если нужны доказательства отсутствия — вы используете сортированную структуру, а не позиционное дерево.
- [ ] Листья хешируются от **канонической сериализации** данных (иначе одинаковые объекты дадут разные хеши).

## Слой 3. Подводные камни и атаки (профессионал)

### 3.1. Атака второго прообраза через смешение уровней

Если лист и внутренний узел хешируются одинаково — `H(x)` для листа и `H(a‖b)` для узла, — то злоумышленник может взять внутренний узел `N = H(a‖b)` и предъявить **64-байтовые данные `a‖b` как лист**. Проверяющий посчитает `H(a‖b) = N`, и путь от N к корню будет валидным. Итог: «доказано» включение элемента, которого в наборе не было.

**Защита:** доменное разделение. RFC 6962: лист = `H(0x00 ‖ data)`, узел = `H(0x01 ‖ left ‖ right)`. Альтернатива — фиксировать глубину дерева и проверять длину proof'а (так делает Bitcoin де-факто, поскольку транзакция не может быть ровно 64 байтами валидного формата… точнее, теперь не может — после специальных проверок).

### 3.2. CVE-2012-2459 (Bitcoin): дублирование последнего узла

При нечётном числе узлов Bitcoin дублирует последний: `[A, B, C] → [A, B, C, C]`. Но тогда набор транзакций `[A, B, C]` и `[A, B, C, C]` дают **одинаковый корень**. Атакующий рассылал блок с продублированной транзакцией; узлы помечали блок с этим хешем как невалидный и навсегда кешировали отказ — а потом отвергали и настоящий, валидный блок с тем же хешем. Denial of service на уровне консенсуса. Патч: явная проверка на дубли соседних транзакций.

**Урок:** конструкция должна быть **инъективной** относительно набора листьев. Дублирование нарушает инъективность; поднятие «сироты» наверх (RFC 6962) — нет.

### 3.3. Уязвимость к «проблеме нулевого листа» в sparse trees

Если пустой лист кодируется как `H(0)` или как нулевой байт, а пользователь может внести значение, чей хеш совпадает с пустым — коллизии семантики. Решение: пустой лист = отдельная константа с доменным префиксом, невыразимая как хеш пользовательских данных.

### 3.4. Гибкость направления (proof malleability)

Если направление сосед-слева/справа не закодировано и верификатор «пробует оба варианта» — вы удвоили пространство подделок на каждом уровне (2^depth вариантов). Направление должно вычисляться из индекса листа или явно передаваться и проверяться.

### 3.5. Что дерево НЕ доказывает

- **Не доказывает отсутствие** (в позиционном дереве). «У меня нет proof'а для X» ≠ «X нет в наборе».
- **Не доказывает уникальность** без дополнительных инвариантов (тот же CVE-2012-2459).
- **Не доказывает свежесть.** Старый корень — валидный корень. Нужна привязка ко времени/последовательности (номер блока, подписанная метка).
- **Не доказывает полноту выдачи.** Сервер может показать вам 3 валидных proof'а и скрыть 4-й элемент. Против этого — consistency proofs + gossip корней между клиентами (как в CT), либо сортированное дерево с range proofs.

### 3.6. Каналы утечки

Merkle proof раскрывает **позицию** элемента и хеши соседей. В приватных контекстах (например, доказательство членства в списке разрешённых адресов) это утечка: можно понять размер набора, соседство элементов. Решения: солёные листья (`H(data ‖ salt)`), zk-доказательства знания пути (Semaphore, Tornado Cash используют именно это).

## Слой 4. Теория и продвинутые варианты (гик / исследователь)

### 4.1. Формальная безопасность

**Утверждение.** Если H стойка к коллизиям, то дерево Меркла — **привязывающая (binding) векторная схема обязательств** (vector commitment): невозможно открыть одну позицию двумя разными значениями.

**Редукция (набросок).** Пусть противник предъявил `(i, v, π)` и `(i, v', π')` с `v ≠ v'`, оба верифицируются к одному root. Идём от корня вниз по обоим путям. В корне хеши равны. На первом уровне, где входы хешей различаются (а они где-то различаются, поскольку листья различны), мы нашли коллизию H. Если входы не различаются нигде — значит v = v', противоречие. Потеря в редукции — множитель, равный глубине (или единица при аккуратном анализе). Доменное разделение нужно как раз для того, чтобы «входы различаются» включало различие структурного типа узла.

Дерево Меркла **не является скрывающим (hiding)** обязательством без рандомизации листьев — root детерминированно зависит от данных, и при малой энтропии данных возможен перебор.

### 4.2. Связь с конструкцией Меркла–Дамгора

Ральф Меркл — автор обоих. Merkle–Damgård (SHA-1, SHA-2) — **цепочка**: `h_i = f(h_{i-1}, m_i)`. Дерево — **параллельная** структура. Цепочка страдает от length-extension и не параллелится; дерево лишено обеих проблем. Blake3 и ParallelHash (SP 800-185) — хеш-функции, внутри которых буквально дерево Меркла, что даёт линейное ускорение на многоядерных CPU/SIMD.

### 4.3. Sparse Merkle Tree (SMT)

Дерево глубины 256 (или λ), где индекс листа = хеш ключа. 2^256 листьев «виртуально» существуют, почти все пустые. Оптимизация: поддеревья, состоящие только из пустых узлов, имеют предвычислимые хеши `E_d = H(E_{d-1} ‖ E_{d-1})`, поэтому хранится только O(n · λ) реальных узлов. Свойства:
- **Доказательства отсутствия:** показать, что в позиции H(key) стоит пустой лист.
- Детерминированный корень независимо от порядка вставок (в отличие от позиционного дерева).
- Proof длиной 256 хешей сжимается битовой маской «здесь пустой сосед» (Compact SMT, Jellyfish Merkle Tree в Aptos/Diem).

### 4.4. Merkle Patricia Trie (Ethereum)

Гибрид radix-trie (сжатие путей по nibble'ам) и дерева Меркла. Узлы трёх типов: branch (16 детей + значение), extension (сжатый общий префикс), leaf. RLP-кодирование, узлы < 32 байт встраиваются в родителя. Даёт доказательства включения и отсутствия, но:
- арность 16 → proof тяжелее бинарного;
- глубина зависит от данных → сложность DoS-атак через специально подобранные ключи (Ethereum хеширует ключи через Keccak именно поэтому);
- дорогая запись на диск (каждое обновление трогает ~O(log₁₆ n) узлов, каждый — случайный доступ). Это одна из причин движения к Verkle trees.

### 4.5. Merkle Mountain Range (MMR)

Append-only лес идеальных бинарных деревьев («горы»), высоты которых соответствуют битам двоичной записи n. Добавление элемента — O(1) амортизированно, не требует перестройки. Корень = хеш «пиков» (bagging the peaks). Используется в Grin, Polkadot (BEEFY), OpenTimestamps. Идеально, когда данные только растут и историю нельзя переписывать.

### 4.6. Consistency proofs (RFC 6962 §2.1.2)

Доказательство, что дерево размера m — префикс дерева размера n > m. Состоит из O(log n) узлов, позволяющих одновременно восстановить старый и новый корни. Это то, что превращает дерево Меркла в **проверяемую append-only структуру** и лежит в основе transparency-логов (CT, Sigstore Rekor, Go checksum database, Key Transparency).

### 4.7. Verkle Trees

Заменяют хеш в узле на **векторное обязательство** (KZG или Pedersen на IPA). Узел арности 256 коммитит к 256 детям, а proof для одного ребёнка — константного размера (одна групповая точка), а не 255 соседних хешей. Все ветви proof'а для нескольких ключей агрегируются в один. Итог: proof для состояния Ethereum падает с ~ мегабайт до ~ сотен байт. Цена: полиномиальные обязательства требуют либо trusted setup (KZG), либо более тяжёлой арифметики (IPA), и они не постквантовые.

### 4.8. Merkle-деревья в zk-системах

- Хеши должны быть «арифметически дружелюбными»: Poseidon — ~250 constraints на хеш в R1CS против ~25 000 у SHA-256.
- Проверка пути внутри схемы — доминирующая стоимость в приложениях вроде Semaphore, zkSync, Tornado. Отсюда популярность арности 4–8 и глубины 20–32.
- В STARK/FRI дерево Меркла — это **сама схема обязательств** к вычислению; безопасность прувера сводится к стойкости хеша, что даёт постквантовость и прозрачность (без setup).

### 4.9. Инкрементальное построение и frontier

Для append-only дерева фиксированной глубины d достаточно хранить d «крайних правых» узлов + счётчик. Добавление: O(d) хешей, память O(d). Именно так работает Ethereum deposit contract (глубина 32, хранит 32 хеша) и большинство on-chain деревьев. Наблюдение: положение узлов frontier определяется битами n — по сути, это тот же MMR.

### 4.10. Открытые и полуоткрытые вопросы

- **Агрегация proof'ов** для произвольных подмножеств листьев без полиномиальных обязательств: multiproofs (Octopus, batched Merkle proofs) экономят до ~50%, но не константны.
- **Постквантовые векторные обязательства с короткими proof'ами** без Merkle-overhead — активная область (lattice-based VC).
- **Приватность структуры** (скрыть размер набора, позицию) при сохранении дешёвой верификации.
- **Дифференциальная синхронизация** больших SMT между репликами с минимальным трафиком — практически важный, но малоформализованный вопрос.

## Слой 5. Шпаргалка

**Что это:** дерево хешей, где корень — обязательство ко всему набору, а путь до листа — доказательство включения.

**Ключевые числа:** корень 32 байта; proof O(log n); верификация O(log n) хешей.

**Три вопроса при проектировании:**
1. Нужно ли доказывать отсутствие? → SMT / Patricia, иначе позиционное дерево.
2. Данные только добавляются? → MMR / frontier.
3. Проверка внутри zk или on-chain? → выбор хеша и арности определяется стоимостью constraint'ов/газа.

**Пять правил безопасности:**
1. Разделяй домены листьев и узлов.
2. Никогда не дублируй узлы — конструкция должна быть инъективной.
3. Направление в proof'е — из индекса, не из перебора.
4. Root доставляй по доверенному каналу; всё остальное — по любому.
5. Помни, что доказано: включение. Не отсутствие, не свежесть, не полнота.

**Родословная:** Merkle 1979 (патент 1982) → Bitcoin 2009 (SPV) → Certificate Transparency 2013 (consistency proofs) → Ethereum 2015 (Patricia trie, доказательства состояния) → Blake3 2020 (дерево как хеш-функция) → Verkle 2021+ (за пределы хешей).
