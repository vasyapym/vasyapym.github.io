# Serverless / Function-as-a-Service: продвинутые паттерны

## 0. Зачем этот урок и как его читать

Урок устроен как лестница: сначала — модель вычислений (что физически происходит, когда вы «запускаете функцию»), затем — ограничения, которые из неё следуют, затем — паттерны как *ответы на эти ограничения*, и в конце — сквозной пример и упражнения. Каждый англоязычный термин при первом появлении определён по-русски; новичок может читать подряд, а опытный инженер — сразу переходить к разделам 3–5, где обсуждаются семантика доставки, согласованность и стоимостная модель.

Главный тезис, к которому мы будем возвращаться: **все «продвинутые» паттерны serverless — это способы вернуть себе гарантии (порядок, состояние, ровно-однократное выполнение, предсказуемую задержку), которые платформа сознательно не даёт в обмен на упругое масштабирование и оплату по факту.**

## 1. Модель вычислений

**Serverless** («бессерверный») — модель, в которой разработчик не управляет серверами: не выбирает машины, не настраивает ОС, не следит за их количеством. Серверы, разумеется, существуют, но принадлежат провайдеру. **FaaS (Function-as-a-Service, «функция как сервис»)** — наиболее чистая форма serverless: единицей развёртывания является функция, то есть обработчик события. Примеры платформ: AWS Lambda, Google Cloud Functions, Azure Functions, Cloudflare Workers.

Жизненный цикл вызова:

1. Происходит **event** («событие»): HTTP-запрос, сообщение в очереди, запись в хранилище, тик таймера.
2. Платформа ищет свободный **execution environment** («среду выполнения» — изолированный контейнер или микро-виртуальную машину с вашим кодом). Если свободной нет — создаёт новую. Создание называется **cold start** («холодный старт»): загрузка кода, инициализация рантайма, выполнение вашего кода вне обработчика. Повторное использование уже «прогретой» среды — **warm start** («тёплый старт»).
3. Вызывается **handler** («обработчик») — ваша функция, получающая событие и контекст.
4. После завершения среда замораживается и может быть переиспользована или уничтожена — по усмотрению платформы.

Из этого вытекают **пять инвариантов**, формирующих все дальнейшие паттерны:

- **Statelessness** («отсутствие состояния»): между вызовами нельзя полагаться ни на память, ни на локальный диск. Состояние живёт снаружи — в базах, очередях, объектных хранилищах.
- **Ограниченное время жизни вызова** (обычно от секунд до ~15 минут). Длинные процессы нужно резать.
- **Одна среда — один вызов в единицу времени** (в большинстве платформ). Масштабирование происходит горизонтально: N одновременных событий → до N сред. Это число ограничено **concurrency limit** («лимитом одновременности»).
- **At-least-once delivery** («доставка как минимум один раз»): асинхронные источники событий могут доставить одно и то же событие дважды, а при ошибке платформа повторит вызов.
- **Нет контроля над размещением**: вы не знаете, на какой машине, рядом с кем и в какой момент среда будет убита.

Строгое следствие (его стоит запомнить как теорему): *в системе с at-least-once доставкой и возможными повторами «ровно один раз» (exactly-once) достижимо только как «как минимум один раз + идемпотентность получателя»*. Платформа может обещать «exactly-once» для узких случаев (например, в рамках одной очереди с дедупликацией), но сквозная гарантия через несколько систем всегда строится вами.

## 2. Что оптимизируем: три оси

Любой паттерн ниже двигает систему по трём осям, и почти всегда за счёт одной из них:

1. **Корректность** — отсутствие потерянных, задвоенных и неупорядоченных эффектов.
2. **Задержка (latency)** — время от события до результата, включая хвост распределения (p99, то есть 99-й перцентиль).
3. **Стоимость** — в FaaS она пропорциональна `число вызовов × длительность × выделенная память` плюс оплата сопутствующих сервисов (очередей, баз, оркестраторов).

Полезная эвристика из теории массового обслуживания — закон Литтла: среднее число одновременно работающих сред `L = λ · W`, где `λ` — интенсивность событий, `W` — средняя длительность вызова. Если `L` приближается к лимиту одновременности, система начнёт отбрасывать или задерживать события. Поэтому сокращение длительности вызова — не только экономия, но и запас прочности по масштабу.

## 3. Паттерны корректности

### 3.1 Идемпотентный обработчик (Idempotent consumer)

**Идемпотентность** — свойство операции, при котором её повторное выполнение с теми же входными данными не меняет результат. Это первый и обязательный паттерн: без него все остальные небезопасны.

Реализация:

- Каждому событию присваивается **идемпотентный ключ** — уникальный идентификатор бизнес-операции (не идентификатор доставки! он различается между повторами). Например, `order_id` или хеш содержимого.
- Перед выполнением побочного эффекта обработчик атомарно записывает ключ в хранилище с условием «если ещё не существует» (**conditional write**, «условная запись»). Если запись не удалась — событие уже обработано; выходим.
- Запись имеет **TTL (time-to-live, «время жизни»)**, чтобы таблица не росла бесконечно; TTL должен превышать максимальное окно повторов источника.

```python
# Псевдокод на Python для AWS Lambda; логика переносима на любую платформу.
import boto3, time, json
from botocore.exceptions import ClientError

table = boto3.resource("dynamodb").Table("idempotency")   # создаём вне handler: переживает тёплые старты

def handler(event, context):
    for record in event["Records"]:                       # пакет из очереди
        body = json.loads(record["body"])
        key = body["order_id"]                            # бизнес-ключ, не message_id
        try:
            table.put_item(
                Item={"pk": key, "status": "IN_PROGRESS", "ttl": int(time.time()) + 86400},
                ConditionExpression="attribute_not_exists(pk)",
            )
        except ClientError as e:
            if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
                continue                                  # дубликат — пропускаем
            raise
        charge_customer(body)                             # побочный эффект
        table.update_item(Key={"pk": key}, UpdateExpression="SET #s = :d",
                          ExpressionAttributeNames={"#s": "status"},
                          ExpressionAttributeValues={":d": "DONE"})
```

Тонкость для продвинутых: что, если функция упала *между* записью `IN_PROGRESS` и `DONE`? Повтор увидит ключ и пропустит операцию — эффект потерян. Правильные реализации хранят статус и по `IN_PROGRESS` старше порога либо повторяют операцию (если она сама идемпотентна по внешнему ключу), либо отправляют событие в очередь ручного разбора. Это иллюстрирует общее правило: **идемпотентность не отменяет необходимости думать о частичных отказах.**

### 3.2 Transactional outbox («транзакционный исходящий ящик»)

Проблема: функция записывает в базу и публикует событие. Если упасть между этими двумя действиями, системы разойдутся. Двухфазная фиксация (2PC) в serverless, как правило, недоступна.

Решение: записывать событие в ту же базу, в той же транзакции, в таблицу `outbox`. Отдельная функция, подписанная на поток изменений базы (**change data capture**, «захват изменений данных», например DynamoDB Streams или Postgres logical replication), читает `outbox` и публикует события. Поток изменений сам даёт at-least-once, поэтому потребители обязаны быть идемпотентны (3.1). Так атомарность «запись + публикация» сводится к атомарности одной транзакции.

### 3.3 Saga: распределённая транзакция через компенсации

Когда бизнес-процесс затрагивает несколько сервисов (списать деньги, зарезервировать товар, создать доставку), и любой шаг может отказать, применяется **saga** — последовательность локальных транзакций, каждая из которых имеет **компенсирующее действие** (возврат денег, снятие резерва). При отказе шага `k` выполняются компенсации шагов `k−1 … 1` в обратном порядке.

Две реализации:

- **Choreography («хореография»)**: сервисы обмениваются событиями через шину; каждый знает, на что реагировать. Слабая связность, но логика процесса размазана по системе, и её трудно увидеть целиком.
- **Orchestration («оркестрация»)**: центральный компонент (AWS Step Functions, Azure Durable Functions, Temporal) хранит состояние процесса и вызывает шаги. Явная модель процесса, встроенные повторы, таймауты и ветвление компенсаций; но появляется зависимость от оркестратора и его стоимость за переход состояния.

Правило выбора: до 3–4 шагов с простой компенсацией — хореография; процессы с ветвлениями, человеческими согласованиями или временем жизни больше нескольких минут — оркестрация. Оркестратор также снимает ограничение времени жизни вызова: сам процесс может длиться дни, а каждая функция — секунды.

Формальная оговорка: saga даёт **eventual consistency** («согласованность в конечном счёте»), не изоляцию. Между шагом и его компенсацией другие участники могут видеть промежуточное состояние (например, «деньги списаны»). Если это недопустимо, нужны семантические блокировки — помечать объект «в процессе» и запрещать конкурирующие операции.

## 4. Паттерны масштаба и потока

### 4.1 Очередь как буфер и back-pressure («обратное давление»)

Прямой вызов функции из источника с всплесками нагрузки упирается в лимит одновременности и начинает терять события. Вставьте очередь (SQS, Pub/Sub, Service Bus) между источником и функцией. Очередь поглощает всплеск, а функция вычерпывает его с темпом, ограниченным **reserved concurrency** («зарезервированной одновременностью» — верхней границей сред для конкретной функции). Это одновременно защищает нижестоящие системы (базу, внешний API), которые не умеют масштабироваться так же быстро.

Обязательные элементы: **DLQ (dead-letter queue, «очередь недоставленных»)** — куда попадают события после N неудачных попыток; метрика возраста самого старого сообщения как сигнал, что потребители не справляются; **частичный ответ по пакету** (partial batch response) — чтобы при ошибке на одном сообщении из десяти повторялось одно, а не десять.

Повторы — с **экспоненциальной задержкой и jitter** («случайным разбросом»): `delay = min(cap, base · 2^attempt) · random(0.5, 1.5)`. Без jitter тысячи сред, упавших одновременно, повторят запрос одновременно и снова уронят зависимость (эффект «громового стада»).

### 4.2 Fan-out / fan-in («разветвление / схождение»)

Задача: обработать большой объём данных параллельно и собрать результат. Схема:

1. **Координатор** разбивает работу на N независимых частей и публикует N сообщений (fan-out).
2. **Рабочие** функции обрабатывают части параллельно, каждая пишет результат во внешнее хранилище.
3. **Схождение (fan-in)**: нужно узнать, что все N завершены. Варианты:
   - атомарный счётчик в базе (`decrement`, когда дошёл до нуля — тот, кто довёл, запускает агрегацию); из-за at-least-once счётчик должен уменьшаться идемпотентно — по ключу части, а не вслепую;
   - оркестратор с состоянием `Map` (Step Functions Distributed Map, Durable Functions fan-out/fan-in), который берёт учёт на себя — проще, но дороже и с лимитами на размер состояния.

Для новичка: это map-reduce на функциях. Для специалиста: обратите внимание на **straggler problem** — одна медленная часть удерживает весь результат; лечится дроблением на части меньшего размера, чем хотелось бы интуитивно, и спекулятивным повтором отстающих.

### 4.3 Управление соединениями

Каждая среда выполнения — отдельный процесс с собственными соединениями к базе. Тысяча сред = тысяча соединений, а реляционная база обычно рассчитана на десятки или сотни. Решения:

- создавать клиентов вне `handler` (как в примере выше): соединение переживает тёплые старты;
- **connection proxy** («прокси соединений», например RDS Proxy, PgBouncer) — мультиплексирует множество клиентских соединений в небольшой пул к базе;
- ограничить одновременность функции до числа, которое база выдерживает, и буферизовать избыток очередью (4.1);
- для нагрузок с высоким параллелизмом предпочитать хранилища с HTTP-интерфейсом без состояния соединения (DynamoDB, Firestore).

## 5. Паттерны задержки и стоимости

### 5.1 Холодный старт: измерить, потом лечить

Холодный старт стоит от десятков миллисекунд (компилируемые языки, лёгкие рантаймы) до нескольких секунд (JVM с тяжёлыми фреймворками). Он проявляется в хвосте распределения задержки, и первая задача — измерить его долю: если 1 % вызовов холодные и это добавляет 300 мс к p99, возможно, лечить нечего.

Инструменты по возрастанию стоимости:

1. **Уменьшить артефакт**: меньше зависимостей, tree-shaking, нативная компиляция (GraalVM, Rust/Go).
2. **Ленивая инициализация**: тяжёлые клиенты создавать при первом использовании, а не при загрузке.
3. **Снимки среды** (AWS SnapStart, аналоги): платформа делает снимок проинициализированной среды и восстанавливает его вместо запуска с нуля. Внимание: всё, что зависит от уникальности при старте (случайные семена, временные токены), нужно переинициализировать после восстановления.
4. **Provisioned concurrency** («заранее подготовленная одновременность»): платформа держит N прогретых сред постоянно. Это уже возврат к оплате за простой — serverless в этом месте перестаёт быть serverless; оправдано для синхронных путей с жёстким SLA на задержку.

«Прогревающие» запросы по таймеру — распространённый, но слабый приём: они держат одну-две среды, а всплеск нагрузки всё равно породит холодные старты.

### 5.2 Стоимость как функция архитектуры

Стоимость вызова ≈ `память × длительность`. Контринтуитивный факт: увеличение памяти часто **снижает** цену, потому что вместе с памятью растёт выделенный CPU, и функция завершается быстрее, чем дорожает. Оптимум ищется измерением (есть автоматизированные инструменты перебора конфигураций).

На уровне архитектуры дорожают: оркестраторы с оплатой за переход состояния при миллионах мелких шагов; синхронные цепочки «функция вызывает функцию» (вы платите за время ожидания вызывающей); частое опрашивание (polling) вместо событийной подписки. Дешевеют: батчинг (один вызов на пакет из 10–100 событий), асинхронные вызовы вместо ожидания, вынос «горячего» постоянного трафика на контейнеры при превышении порога, где serverless становится дороже постоянно работающего инстанса (обычно это десятки миллионов вызовов в месяц при стабильной нагрузке — считайте для своего случая).

## 6. Сквозной пример: приём и обработка заказа

Соберём паттерны в одну систему.

1. **HTTP-функция** принимает заказ, валидирует, в одной транзакции пишет `orders` и строку в `outbox` (3.2), отвечает клиенту `202 Accepted` с `order_id`. Она синхронна и видна пользователю — для неё, при необходимости, включаем provisioned concurrency (5.1).
2. **Функция-публикатор** читает поток изменений базы и кладёт событие `OrderCreated` в шину событий.
3. **Оркестратор saga** (3.3) подписан на `OrderCreated`: шаги «списать деньги → зарезервировать товар → создать доставку», у каждого — компенсация. Каждый шаг — отдельная функция, идемпотентная по `order_id` (3.1). Оркестратор обеспечивает повторы с jitter и общий таймаут процесса в 24 часа.
4. **Отчёты**: ночной таймер запускает fan-out (4.2) по партициям заказов за день, рабочие пишут частичные агрегаты, счётчик в базе определяет завершение и запускает сборку итогового отчёта.
5. Все асинхронные функции получают события через очереди с DLQ и ограниченной одновременностью (4.1); база за прокси соединений (4.3).

Где здесь остались риски? Между шагом «списать деньги» и компенсацией клиент может увидеть списание; проверьте, допустимо ли это, иначе используйте предавторизацию вместо списания. `outbox` добавляет секунды задержки между записью и публикацией — для большинства заказов это приемлемо.

## 7. Анти-паттерны (коротко)

- **Монофункция («lambdalith»)** — одна функция со всем приложением: лишает гранулярного масштабирования и прав доступа, но *не всегда плоха* — для небольшого API это проще и дешевле холодных стартов множества функций. Выбор осознанный.
- **Синхронные цепочки функций** — платите дважды и умножаете хвост задержки.
- **Состояние в `/tmp` или глобальных переменных как источник истины** — оно пропадёт без предупреждения.
- **Отсутствие DLQ** — ошибки исчезают молча после исчерпания повторов.
- **Повторы без идемпотентности** — двойные списания.

## 8. Упражнения

1. Докажите (неформально), почему «ровно один раз» нельзя гарантировать на стороне доставщика, если получатель может упасть после обработки, но до подтверждения. Что именно должен хранить получатель?
2. В примере 3.1 функция упала после `charge_customer`, но до записи `DONE`. Повтор приходит через минуту. Предложите протокол, при котором ни одно списание не теряется и не дублируется, если платёжный провайдер принимает внешний идентификатор операции.
3. Функция обрабатывает событие 200 мс, пик — 5000 событий/с, лимит одновременности — 1000. Используя закон Литтла, определите, справится ли система, и какова будет глубина очереди через минуту пика.
4. Оцените, при какой стабильной нагрузке (вызовов/с, длительность 100 мс, 512 МБ) FaaS в вашем провайдере становится дороже одного постоянно работающего контейнера. Какие нестоимостные аргументы могут изменить решение?

## 9. Что запомнить

Serverless забирает у вас серверы и вместе с ними — гарантии порядка, состояния и однократности. Паттерны этого урока возвращают гарантии ровно в тех местах, где они нужны: идемпотентность и outbox — для корректности; очереди, лимиты и fan-out — для масштаба; снимки среды и подготовленная одновременность — для задержки. Каждый из них имеет цену, и профессионализм состоит не в том, чтобы применять все, а в том, чтобы измерить и выбрать минимально достаточный набор.
