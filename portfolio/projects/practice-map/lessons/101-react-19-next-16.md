# React 19 и Next.js 16: концептуальный разбор

Материал устроен в два слоя. Блоки **«Интуиция»** объясняют идею простым языком, без предварительных знаний. Блоки **«Глубже»** предназначены для профессионалов: там речь идёт о механизмах, компромиссах и теоретических основаниях. Начинающему достаточно первого слоя, опытному разработчику интереснее второй.

---

### 1. React 19 + Next.js 16: общая модель

## 1.0. Кто за что отвечает

**Интуиция.** React — это *язык описания интерфейса*. Вы объявляете, как должен выглядеть экран при данном состоянии, а React сам приводит реальность к описанию. Next.js — *фреймворк*, который берёт этот язык и добавляет всё необходимое для продакшена: маршрутизацию, сервер, сборку, кеширование, оптимизацию изображений.

**Глубже.** Начиная с React 18–19 граница между ними сместилась. React перестал быть «библиотекой для браузера» и стал спецификацией *распределённой* модели вычислений: часть дерева компонентов выполняется на сервере, часть на клиенте, и между ними работает потоковый протокол сериализации. Однако сам React не содержит ни бандлера, ни роутера, ни сервера, а без них эта архитектура не работает. Next.js App Router является де-факто референсной реализацией этой архитектуры. Поэтому App Router поставляется со встроенной canary-версией React, и Next.js 16 уже использует возможности React 19.2.

Отсюда практическое следствие: многие «фичи Next.js» на деле являются примитивами React, а Next.js даёт им конкретную семантику (кеш, маршруты, инвалидацию).

---

## 1.1. Фундамент: UI = f(state)

**Интуиция.** Компонент — функция: на вход данные, на выход описание интерфейса. Данные изменились, функция вызывается снова, React сравнивает старый и новый результат и точечно обновляет экран.

**Глубже.** За этой простотой стоят три идеи:

1. **Чистота рендера.** Рендер должен быть идемпотентным и свободным от побочных эффектов. Только при этом условии React может прерывать рендер, повторять его, выполнять «в фоне» или вообще на другой машине. Все продвинутые возможности, от concurrent rendering до Server Components и React Compiler, держатся на этом инварианте.
2. **Fiber и кооперативная многозадачность.** Дерево представлено связным списком «волокон», и обход можно приостановить, отдав управление браузеру. Обновления получают приоритеты (внутренняя модель *lanes*): ввод с клавиатуры срочнее, чем перерисовка тяжёлого списка.
3. **Suspense как алгебраический эффект.** Компонент, которому не хватает данных, «бросает» промис. Ближайшая граница `<Suspense>` перехватывает его, показывает fallback и возобновляет рендер, когда промис разрешится. Концептуально это близко к effect handlers из теории языков программирования: вычисление сигнализирует об эффекте, а обрабатывает его внешний контекст.

---

## 1.2. Server Components (RSC)

**Интуиция.** Обычный компонент отправляется в браузер как JavaScript-код и выполняется там. Серверный компонент выполняется на сервере, и в браузер уходит только *результат*. Он может напрямую читать базу данных или файлы, а его код и зависимости (скажем, тяжёлая библиотека разбора Markdown) не увеличивают размер бандла ни на байт.

В Next.js App Router **все компоненты по умолчанию серверные**. Клиентским компонент становится только по явной просьбе:

```tsx
// app/products/page.tsx — Server Component (по умолчанию)
import { AddToCart } from './AddToCart';

export default async function ProductsPage() {
  const products = await db.product.findMany(); // прямой доступ к БД
  return (
    <ul>
      {products.map(p => (
        <li key={p.id}>
          {p.name} <AddToCart productId={p.id} />
        </li>
      ))}
    </ul>
  );
}
```

```tsx
// app/products/AddToCart.tsx — Client Component
'use client';
import { useState } from 'react';

export function AddToCart({ productId }: { productId: string }) {
  const [added, setAdded] = useState(false);
  return <button onClick={() => setAdded(true)}>{added ? '✓' : 'В корзину'}</button>;
}
```

| | Server Component | Client Component |
|---|---|---|
| Где выполняется | Только на сервере (при сборке или запросе) | На сервере (SSR) **и** в браузере (гидратация) |
| `async`/`await` в теле | Да | Нет (вместо этого `use`) |
| `useState`, `useEffect`, обработчики событий | Нет | Да |
| Доступ к БД, секретам, ФС | Да | Нет |
| Попадает в JS-бандл | Нет | Да |

**Глубже.**

- **`'use client'` отмечает границу модульного графа, а не отдельного компонента.** Директива говорит бандлеру: «здесь начинается клиентский подграф». Всё, что импортирует этот файл, тоже уходит на клиент. Поэтому директиву стоит ставить как можно ниже по дереву, на «листьях интерактивности».
- **RSC Payload (протокол Flight).** Сервер сериализует дерево в потоковый формат. Серверные компоненты в нём уже «развёрнуты» в элементы, а клиентские представлены *ссылками на модули* плюс сериализованными пропсами. Отсюда главное ограничение: **пропсы через границу должны быть сериализуемыми**. Можно передавать примитивы, обычные объекты, `Date`, `Map`, промисы, JSX. Нельзя передавать произвольные функции, за исключением Server Functions (о них ниже).
- **Композиция вместо импорта.** Клиентский компонент не может *импортировать* серверный, но может получить его как `children` или проп. Так возникает «шахматная» структура: серверная обёртка → клиентский интерактивный слой → серверный контент внутри.
- **RSC не отменяют SSR.** Это ортогональные вещи. SSR превращает дерево в HTML для первого показа. RSC определяют, *где* выполняется код компонента. Next.js использует оба механизма: HTML для быстрого первого кадра и RSC Payload для гидратации и последующих навигаций без полной перезагрузки.

---

## 1.3. Server Functions и Server Actions (`'use server'`)

**Интуиция.** Функция объявляется на сервере, а вызывается из браузера как обычная функция, например из кнопки или формы. React и Next.js сами организуют сетевой запрос.

**Глубже.** По сути это RPC, сгенерированный компилятором. Функция с `'use server'` при сборке заменяется на клиенте стабильным идентификатором, а вызов превращается в POST-запрос к серверу. Server Function, переданная в `action` формы, называется **Server Action** и даёт *прогрессивное улучшение*: форма отправится даже до загрузки JavaScript.

Важно с точки зрения безопасности: каждая Server Function — **публичный HTTP-эндпоинт**. То, что она «спрятана» внутри компонента, ничего не гарантирует. Аутентификацию, авторизацию и валидацию входных данных нужно выполнять внутри самой функции. Next.js шифрует захваченные замыканием переменные и удаляет неиспользуемые экшены из сборки, но это меры гигиены, а не модель безопасности.

---

## 1.4. Actions: асинхронные переходы как примитив

**Интуиция.** Раньше для каждой формы приходилось вручную заводить `isLoading`, `error` и сбрасывать их. React 19 вводит понятие **Action** — асинхронной функции, внутри которой React сам отслеживает состояние ожидания, ошибки и оптимистичные обновления.

Ключевые API:

- **`useActionState`** — состояние, которое обновляется результатом экшена, плюс флаг `isPending`;
- **`useFormStatus`** (из `react-dom`) — дочерний компонент формы узнаёт, отправляется ли она, без прокидывания пропсов;
- **`useOptimistic`** — показывает предполагаемый результат мгновенно и откатывается, если сервер ответил ошибкой;
- **`useTransition`** теперь принимает асинхронные функции.

```ts
// app/posts/actions.ts
'use server';
import { updateTag } from 'next/cache';

export async function createPost(_prev: { error: string | null }, formData: FormData) {
  const session = await auth();                      // авторизация — внутри!
  if (!session) return { error: 'Нет доступа' };

  const title = formData.get('title');
  if (typeof title !== 'string' || !title.trim()) return { error: 'Пустой заголовок' };

  await db.post.create({ data: { title, authorId: session.userId } });
  updateTag('posts');                                // Next 16: read-your-writes
  return { error: null };
}
```

```tsx
// app/posts/PostForm.tsx
'use client';
import { useActionState } from 'react';
import { createPost } from './actions';

export function PostForm() {
  const [state, formAction, isPending] = useActionState(createPost, { error: null });
  return (
    <form action={formAction}>
      <input name="title" />
      <button disabled={isPending}>{isPending ? 'Сохраняем…' : 'Создать'}</button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}
```

**Глубже.** Actions встроены в модель переходов (transitions). Обновления внутри экшена получают низкий приоритет и не блокируют ввод, а несколько последовательных экшенов упорядочиваются. Сдвиг здесь концептуальный: асинхронность из «пользовательского» кода, который React не видел, становится частью планировщика. React знает, что идёт переход, и может согласованно управлять Suspense-границами и оптимистичным состоянием.

---

## 1.5. `use`: чтение ресурсов во время рендера

**Интуиция.** `use(promise)` «разворачивает» промис прямо в рендере: пока он не готов, показывается ближайший `<Suspense>`. `use(Context)` читает контекст. В отличие от хуков, `use` можно вызывать внутри `if` и циклов.

Самый полезный паттерн в связке с Next.js — **начать загрузку на сервере, а дождаться её на клиенте**:

```tsx
// page.tsx (Server Component)
export default function Page() {
  const commentsPromise = getComments();   // без await: запрос уже летит
  return (
    <Suspense fallback={<p>Загрузка комментариев…</p>}>
      <Comments commentsPromise={commentsPromise} />
    </Suspense>
  );
}
```

```tsx
// Comments.tsx
'use client';
import { use } from 'react';

export function Comments({ commentsPromise }: { commentsPromise: Promise<Comment[]> }) {
  const comments = use(commentsPromise);
  return <ul>{comments.map(c => <li key={c.id}>{c.text}</li>)}</ul>;
}
```

**Глубже.** Промис сериализуется протоколом Flight. Страница отдаётся сразу, а когда данные готовы, сервер дописывает их в тот же поток, и клиентская граница раскрывается. Так устраняются «водопады» запросов. Одно ограничение: промис должен быть *стабильным*. Если создавать новый промис на каждом клиентском рендере, получится бесконечная приостановка. Поэтому промисы создаются на сервере или в кеширующем слое.

---

## 1.6. Suspense и потоковый рендеринг

**Интуиция.** Вместо того чтобы ждать самую медленную часть страницы, сервер сразу отдаёт готовое, а на месте медленных блоков показывает заглушки. Затем он «досылает» их по мере готовности в том же HTTP-ответе. В Next.js для этого достаточно положить рядом со страницей файл `loading.tsx` или явно обернуть часть дерева в `<Suspense>`.

**Глубже.** Потоковая передача дополняется **выборочной гидратацией**: React гидратирует границы независимо и в первую очередь ту, с которой пользователь начал взаимодействовать. В React 19.2 серверный рендер **группирует раскрытие соседних Suspense-границ** в один кадр, чтобы контент не «прыгал» мелкими кусками, и поддерживает Web Streams в Node.js.

---

## 1.7. Эргономика React 19

Это небольшие, но заметные изменения:

- **`ref` как обычный проп.** `forwardRef` больше не нужен.
- **`<Context>` вместо `<Context.Provider>`.**
- **Функции очистки у ref-колбэков**, по аналогии с `useEffect`.
- **Метаданные документа.** `<title>`, `<meta>`, `<link>` можно рендерить в любом компоненте, и React поднимет их в `<head>`. В Next.js для этого всё же правильнее использовать Metadata API (`export const metadata` / `generateMetadata`).
- **Таблицы стилей с `precedence`** и дедупликация асинхронных `<script>`.
- **API предзагрузки ресурсов:** `preload`, `preinit`, `preconnect`, `prefetchDNS`.
- **Понятные ошибки гидратации** с диффом вместо загадочных сообщений.
- **Полная поддержка Custom Elements.**

---

## 1.8. React 19.2: новое, на что опирается Next.js 16

**`<Activity>`** — «пауза» для части интерфейса:

```tsx
<Activity mode={isOpen ? 'visible' : 'hidden'}>
  <Sidebar />
</Activity>
```

*Интуиция:* скрытый блок сохраняет своё состояние (введённый текст, позицию прокрутки), но не тратит ресурсы. *Глубже:* в режиме `hidden` React отключает эффекты и откладывает обновления на минимальный приоритет, при этом дерево остаётся смонтированным. Это промежуточное состояние между «смонтировано» и «размонтировано», которого раньше не существовало. Оно позволяет заранее готовить вероятные следующие экраны и мгновенно возвращаться к предыдущим.

**`useEffectEvent`** решает давнюю проблему зависимостей эффектов:

```tsx
function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification('Подключено', theme);   // всегда видит актуальную theme
  });

  useEffect(() => {
    const conn = createConnection(roomId);
    conn.on('connected', onConnected);
    conn.connect();
    return () => conn.disconnect();
  }, [roomId]);                               // смена theme НЕ переподключает чат
}
```

*Глубже:* эффект описывает *синхронизацию с внешней системой*, а Effect Event описывает *реакцию на событие*, которой нужны свежие значения, но которая не должна перезапускать синхронизацию. API формализует разделение «реактивного» и «нереактивного» кода, которое раньше обходили через `useRef` или отключение линтера.

**Другие нововведения:**

- **`cacheSignal`** (для RSC) — сигнал отмены, когда закешированная работа больше не нужна;
- **Performance Tracks** в Chrome DevTools — дорожки планировщика и компонентов прямо в профайлере;
- **API частичного пререндера** в `react-dom` (`prerender` / `resume`) — низкоуровневая основа Cache Components в Next.js 16;
- **View Transitions** (`<ViewTransition>`, canary) — анимации переходов на основе браузерного View Transitions API, доступные в Next.js 16 через встроенную canary-версию React.

## 1.9. React Compiler 1.0

**Интуиция.** Раньше для производительности приходилось вручную расставлять `useMemo`, `useCallback` и `memo`. Компилятор делает это сам на этапе сборки, и обычно точнее человека.

**Глубже.** Компилятор переводит компонент в промежуточное представление, анализирует потоки данных и мемоизирует значения с гранулярностью отдельных выражений, а не целых компонентов. Это возможно только при соблюдении **Правил React** (чистота, иммутабельность пропсов и состояния). Там, где правила нарушены, компилятор просто пропускает компонент. В Next.js 16 поддержка стабильна (`reactCompiler: true`), но **по умолчанию выключена**: компилятор работает через Babel и замедляет сборку.

### 2. Next.js 16: собственные концепции фреймворка

## 2.1. App Router: каркас

**Интуиция.** Структура папок в `app/` и есть карта сайта. Специальные файлы задают роли:

| Файл | Назначение |
|---|---|
| `page.tsx` | Содержимое маршрута |
| `layout.tsx` | Общая обёртка, сохраняется при навигации |
| `loading.tsx` | Fallback (автоматический `<Suspense>`) |
| `error.tsx` | Граница ошибок (клиентский компонент) |
| `not-found.tsx` | Страница 404 |
| `default.tsx` | Fallback для параллельных маршрутов (в v16 **обязателен**) |
| `route.ts` | API-обработчик (GET, POST…) |

Также доступны динамические сегменты (`[slug]`), группы маршрутов (`(marketing)`), параллельные (`@modal`) и перехватывающие (`(.)photo`) маршруты.

**Глубже.** Вложенные layouts образуют дерево, которое при навигации *не перемонтируется*: меняются только сегменты ниже точки расхождения. Это прямое следствие модели согласования React, перенесённой на уровень маршрутов.

---

## 2.2. Главный сдвиг: Cache Components и `'use cache'`

**Интуиция.** В прошлых версиях Next.js сам решал, что кешировать, и разработчики часто не понимали, почему данные «залипли». В Next.js 16 правило простое и честное: **всё динамично, пока вы явно не попросили кешировать**. Кешировать можно функцию, компонент или целую страницу одной директивой.

```ts
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  reactCompiler: true, // опционально
};
export default nextConfig;
```

```tsx
import { Suspense } from 'react';
import { cookies } from 'next/headers';
import { cacheLife, cacheTag } from 'next/cache';

async function getProducts() {
  'use cache';
  cacheLife('hours');       // профиль времени жизни
  cacheTag('products');     // метка для точечной инвалидации
  return db.product.findMany();
}

async function ProductList() {
  const products = await getProducts();
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

async function Cart() {
  const session = (await cookies()).get('session');  // персональные данные
  const items = await getCart(session?.value);
  return <CartView items={items} />;
}

export default function Page() {
  return (
    <>
      <Header />                                   {/* статическая оболочка */}
      <ProductList />                              {/* закешированный блок */}
      <Suspense fallback={<CartSkeleton />}>
        <Cart />                                   {/* динамическая «дыра» */}
      </Suspense>
    </>
  );
}
```

**Глубже.**

- **Partial Prerendering как модель по умолчанию.** Страница больше не делится на «статическую» и «динамическую». Каждая страница — это *статическая оболочка* (пререндерится при сборке и раздаётся с CDN мгновенно) с *динамическими дырами* на месте `<Suspense>`, которые дорендериваются и стримятся по запросу. Бинарный выбор SSG/SSR заменён непрерывным спектром на уровне отдельных поддеревьев.
- **Ключ кеша выводится компилятором.** В него входят аргументы функции и захваченные замыканием значения. Поэтому внутри `'use cache'` нельзя вызывать `cookies()` или `headers()`: это скрытые входы, которые сделали бы кеш некорректным. Персональные данные нужно передавать аргументом.
- **Явность принуждается сборкой.** Если некешированные данные или request-API используются вне `<Suspense>`, сборка завершится ошибкой. Фреймворк заставляет вас явно решить для каждого куска данных: «кешировать» или «стримить».
- **Профили `cacheLife`:** `'seconds'`, `'minutes'`, `'hours'`, `'days'`, `'weeks'`, `'max'` или собственные. Каждый задаёт три параметра: stale (сколько клиент использует без проверки), revalidate (когда фоново обновлять) и expire (когда считать недействительным).
- **Варианты директивы** вроде `'use cache: remote'` и `'use cache: private'` задают, где и для кого хранится кеш. Их точную семантику стоит сверять с актуальной документацией, она ещё развивается.
- Прежние `experimental.ppr` и `experimental.dynamicIO` удалены и заменены `cacheComponents`. `unstable_cacheLife` и `unstable_cacheTag` стабилизированы как `cacheLife` и `cacheTag`.

## 2.3. Инвалидация: три инструмента с разной семантикой

| API | Где вызывать | Семантика | Когда использовать |
|---|---|---|---|
| `revalidateTag(tag, profile)` | Server Actions, Route Handlers | **Stale-while-revalidate**: пользователь сразу видит старое, свежее подтягивается в фоне. Второй аргумент (профиль, например `'max'`) теперь **обязателен** | Контент, где допустима задержка: блог, каталог |
| `updateTag(tag)` | **Только** Server Actions | **Read-your-writes**: кеш истекает немедленно, и тот же запрос получает свежие данные | После действия пользователя, который ждёт увидеть результат: «сохранил настройки — вижу новые» |
| `refresh()` | Только Server Actions | Обновляет **некешированные** данные на странице, кеш не трогает | Счётчики уведомлений, статусы |

**Глубже.** Разделение отражает классическую дилемму согласованности. `revalidateTag` даёт *eventual consistency* с минимальной задержкой ответа, а `updateTag` даёт сильную согласованность для автора изменения ценой ожидания. Раньше оба сценария делили одну функцию, отсюда были неожиданные эффекты. `revalidatePath` по-прежнему доступен.

## 2.4. `proxy.ts` вместо `middleware.ts`

```ts
// proxy.ts (в корне проекта или в src/)
import { NextRequest, NextResponse } from 'next/server';

export function proxy(request: NextRequest) {
  if (!request.cookies.has('locale')) {
    return NextResponse.redirect(new URL('/ru' + request.nextUrl.pathname, request.url));
  }
}

export const config = { matcher: ['/((?!_next|api|favicon.ico).*)'] };
```

**Интуиция.** Это код, который выполняется *до* маршрута: редиректы, переписывание URL, заголовки, A/B-тесты.

**Глубже.** Переименование концептуальное. Слово «middleware» создавало ложное ожидание Express-подобной цепочки, куда можно положить всю бизнес-логику, включая авторизацию. «Proxy» честно описывает роль: лёгкий слой на сетевой границе перед приложением. `proxy.ts` работает в рантайме Node.js. `middleware.ts` пока поддерживается для Edge-сценариев, но объявлен устаревшим. Рекомендованная архитектура авторизации — проверка близко к данным (Data Access Layer, Server Actions), а не только в прокси.

## 2.5. Turbopack по умолчанию

**Интуиция.** Новый сборщик на Rust теперь используется и для разработки, и для продакшен-сборки. Сборки в 2–5 раз быстрее, Fast Refresh до 10 раз быстрее. Вернуться к webpack можно флагом `--webpack`.

**Глубже.** Turbopack построен на модели **инкрементальных вычислений**. Сборка описана как граф мемоизированных функций-задач с автоматическим отслеживанием зависимостей (идейные родственники — Salsa в rust-analyzer и Adapton). При изменении файла пересчитываются только задачи, транзитивно зависящие от него. В Next.js 16 появилось бета-кеширование этого графа на диск между перезапусками dev-сервера (`experimental.turbopackFileSystemCacheForDev`), что особенно заметно на больших монорепозиториях.

## 2.6. Навигация и предзагрузка

**Интуиция.** `<Link>` заранее подгружает страницы, на которые вы, вероятно, перейдёте. В v16 это стало заметно экономнее.

**Глубже.**

- **Дедупликация layouts.** Если на странице 50 ссылок на товары с общим layout, он загружается один раз, а не 50.
- **Инкрементальная предзагрузка.** Загружаются только недостающие в кеше сегменты. Запрос отменяется, когда ссылка уходит из viewport, повышается в приоритете при наведении и обновляется при инвалидации данных.

В итоге число запросов может вырасти, но суммарный объём передаваемых данных заметно падает. Это осознанный компромисс в пользу точности.

## 2.7. Асинхронные request-API

`params`, `searchParams`, `cookies()`, `headers()`, `draftMode()` теперь **только асинхронные**. Синхронный доступ, временно разрешённый в v15, удалён:

```tsx
export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  // ...
}
```

**Глубже.** Это не каприз API, а фундамент частичного пререндера. Пока компонент не прочитал данные запроса, фреймворк может считать его статическим и пререндерить. Момент `await` становится *точкой перехода* в динамический режим. Синхронный доступ скрыл бы эту точку и сделал бы автоматическое разделение на оболочку и дыры невозможным.

## 2.8. Прочие нововведения

- **Build Adapters API (alpha)** — официальный способ для хостинг-платформ встраиваться в процесс сборки. Это шаг к независимости Next.js от конкретного хостинга.
- **Next.js DevTools MCP** — сервер Model Context Protocol, через который ИИ-ассистенты получают доступ к маршрутам, логам и ошибкам приложения.
- **Улучшенное логирование** в dev-режиме и при сборке: видно, сколько времени заняли компиляция и рендер.

---

## 2.9. Критические изменения при миграции

- **Node.js 20.9+**, **TypeScript 5.1+**, обновлены минимальные версии браузеров.
- **`next lint` удалён.** ESLint (или Biome) нужно вызывать напрямую.
- **AMP удалён полностью.**
- **`serverRuntimeConfig` и `publicRuntimeConfig` удалены.** Вместо них используются переменные окружения.
- **Параллельные маршруты требуют явного `default.tsx`.**
- **Изменения в `next/image`:**
  - `minimumCacheTTL` по умолчанию 4 часа;
  - `qualities` по умолчанию `[75]`;
  - `images.domains` устарел в пользу `remotePatterns`;
  - локальные изображения с query-строкой требуют `localPatterns`.
- **Автоматическая миграция:** `npx @next/codemod@canary upgrade latest`.

## 2.10. Итоговая модель: путь одного запроса

```
Запрос
  │
  ▼
proxy.ts ──────────── редирект / rewrite / заголовки
  │
  ▼
Сопоставление маршрута (app/…/page.tsx + вложенные layouts)
  │
  ▼
Статическая оболочка ── уже пререндерена при сборке → отдаётся мгновенно
  │
  ├─ блоки 'use cache' ──── берутся из кеша (или вычисляются и сохраняются)
  │
  └─ <Suspense>-дыры ────── рендерятся по запросу (cookies, персональные данные)
                             и стримятся в тот же HTTP-ответ
  │
  ▼
Браузер: HTML (первый кадр) + RSC Payload
  │
  ▼
Гидратация только клиентских компонентов ('use client')
  │
  ▼
Дальнейшие навигации: RSC Payload без перезагрузки,
сохранённые layouts, инкрементальная предзагрузка
```

---

### Практические принципы

1. **Сервер по умолчанию, клиент по необходимости.** `'use client'` ставьте на листья интерактивности, а не на корень страницы.
2. **Кешируйте явно и осознанно.** Для каждого источника данных решите, что это: `'use cache'` с понятным `cacheLife` и `cacheTag` или динамика внутри `<Suspense>`.
3. **Выбирайте инвалидацию по ожиданиям пользователя.** Если пользователь должен сразу увидеть своё изменение, используйте `updateTag`. Если допустима короткая задержка, используйте `revalidateTag(tag, 'max')`.
4. **Считайте каждую Server Function публичным API.** Проверяйте авторизацию и валидируйте ввод внутри неё.
5. **Соблюдайте чистоту рендера.** На ней держатся concurrent rendering, RSC, React Compiler и частичный пререндер.

Если сжать всю эволюцию в одну мысль: React 19 дал *язык* для описания распределённого, асинхронного и потокового интерфейса, а Next.js 16 сделал *явной* стоимость каждого решения: где выполняется код, что кешируется, когда данные устаревают и кто ждёт их обновления.
