# GraphQL, from First Principles to Federation

## Part I — What GraphQL Actually Is

GraphQL is three things wearing one name: a **query language** that clients use to describe the data they want, a **type system** (the schema) that servers use to describe the data they can provide, and an **execution specification** that defines exactly how a request against that schema is turned into a response. It is *not* a database, *not* a storage engine, and *not* tied to graphs in the mathematical sense beyond the fact that your data is modeled as nodes (objects) connected by edges (fields). It was designed at Facebook around 2012 to solve a concrete problem: mobile clients were over-fetching (receiving huge REST payloads of which they used a sliver) and under-fetching (needing several round trips to assemble one screen). GraphQL inverts control: the client states the exact shape of the response, and the server fulfills it in one trip.

The foundational contract is the **schema**, written in the **Schema Definition Language (SDL)**. A schema declares **types**, each type declares **fields**, and each field has a return type. The root of all reading is the `Query` type, the root of all writing is the `Mutation` type, and the root of all real-time pushes is the `Subscription` type. A request is called a **document**; a document contains one or more **operations** (query, mutation, or subscription) and optionally **fragments**. The response is JSON whose shape mirrors the request almost one-to-one: a field you asked for appears as a key, nested selections appear as nested objects. This structural mirroring is the single most important intuition for beginners and is what makes GraphQL responses predictable enough to generate static types from.

## Part II — The Type System Vocabulary

**Scalars** are the leaves: `Int`, `Float`, `String`, `Boolean`, and `ID` are built in, and you can define **custom scalars** such as `DateTime`, `URL`, or `JSON` with your own serialization and validation logic. **Enums** are closed sets of named values. **Object types** are the heart of the schema—named collections of fields, like `User { id: ID!, name: String, posts: [Post!]! }`. **Input types** are object-like types permitted only as arguments; this separation exists because output objects may have circular references and interfaces that make no sense as input payloads. **Interfaces** declare a set of fields that multiple object types promise to implement, enabling polymorphic queries. **Unions** declare that a field may return one of several object types with no shared fields required. **Lists** wrap any type, and the **non-null modifier** (`!`) asserts that a value will never be `null`.

Nullability deserves its own paragraph because it is where GraphQL's semantics are most subtle and most often misunderstood. In GraphQL, *every field is nullable by default*, which is the opposite of most type systems. This is deliberate. Because a single response may be assembled from many backend calls, partial failure is the norm, not the exception. When a resolver for a nullable field throws, the field becomes `null`, an entry is added to the `errors` array, and the rest of the response survives. When a resolver for a **non-null** field throws, `null` is forbidden there, so the error *propagates upward* to the nearest nullable ancestor, nullifying that entire subtree. This is called **null bubbling** or **error propagation**. The practical design rule: mark a field non-null only when its absence would make the parent object meaningless. Overusing `!` turns small failures into large blast radii.

**Arguments** parameterize fields: `user(id: ID!)`, `posts(first: Int, after: String)`. **Variables** let documents be parameterized so the same query text can be reused with different values, which matters for caching and for persisted queries. **Aliases** let a client request the same field twice with different arguments (`small: avatar(size: 50) large: avatar(size: 400)`). **Fragments** are reusable selection sets, and **inline fragments** with type conditions (`... on Admin { permissions }`) are how you select type-specific fields on an interface or union. The special meta-field `__typename` returns the concrete type name and is essential for client-side normalization and union handling.

**Directives** annotate the document or the schema. Executable directives like `@include(if:)` and `@skip(if:)` conditionally shape the selection; `@deprecated(reason:)` marks schema elements for retirement; `@specifiedBy` points custom scalars at a specification URL. Custom schema directives are the extension mechanism everything advanced—authorization, caching, federation—is built upon.

**Introspection** is the schema querying itself. The `__schema` and `__type` meta-fields expose the entire type system at runtime, which is what powers GraphiQL, code generators, and IDE autocompletion. In production, introspection is often disabled or restricted because it is also a map for attackers.

## Part III — Execution: How a Request Becomes a Response

The execution pipeline has distinct phases, and knowing them turns debugging from guesswork into diagnosis. **Lexing and parsing** turn the document string into an **AST**. **Validation** checks the AST against the schema: do the fields exist, are the arguments the right types, are fragments spread on compatible types, is the document free of cycles, do overlapping fields merge cleanly. Only after validation does **execution** begin.

Execution is a depth-first traversal of the selection set. For each field, the engine invokes a **resolver**, a function with the canonical signature `(parent, args, context, info)`. `parent` is the value returned by the resolver of the enclosing field; `args` are the coerced arguments; `context` is a per-request bag (the authenticated user, database connections, loaders); `info` carries the AST and path, which advanced resolvers use for look-ahead optimizations. If no resolver is defined, the **default resolver** simply reads a property of the same name off the parent. Sibling fields are resolved in parallel for queries; **mutation root fields are resolved serially, in order**, which is the specification's only ordering guarantee and the reason you can safely put `deleteX` after `createX` in one mutation document.

The engine never knows or cares where data comes from. A resolver may hit SQL, Redis, a REST service, another GraphQL server, or return a constant. This indifference is GraphQL's power and also the source of its most famous performance pitfall, the **N+1 problem**: a query for a hundred posts and each post's author naively fires one query for the posts and then one hundred queries for the authors, because each author resolver executes independently and knows nothing of its siblings. The standard remedy is the **DataLoader pattern**: a per-request utility that batches all `load(id)` calls made within one tick of the event loop into a single `loadMany(ids)` and memoizes results. DataLoaders must be instantiated per request to avoid leaking data across users. A more aggressive alternative is **look-ahead** resolution, where the top-level resolver inspects `info` to see which child fields are requested and constructs one joined query up front.

## Part IV — Advanced Client and Server Patterns

**Pagination** in GraphQL has a de-facto standard: the **Relay Cursor Connections specification**. Instead of `posts: [Post]`, you expose `posts(first: Int, after: String, last: Int, before: String): PostConnection`, where a connection contains `edges` (each with a `node` and an opaque `cursor`) and `pageInfo` (`hasNextPage`, `hasPreviousPage`, `startCursor`, `endCursor`). Cursors are opaque strings—typically base64-encoded sort keys—so the server can change pagination strategy without breaking clients. The connection pattern also gives you a natural place for edge metadata (think "friendship since" on a friends edge) and a `totalCount`.

The **Global Object Identification** convention gives every object a globally unique `id` and a root `node(id: ID!): Node` field, letting any client refetch any object by ID alone. Combined with `__typename`, this enables **normalized client caches** (Apollo Client, Relay, urql's graphcache) that store every object once and automatically update every view when a mutation returns new data for a known ID.

**Mutation design** has matured conventions: one input object argument (`createPost(input: CreatePostInput!)`), one payload object return (`CreatePostPayload`) containing the mutated entity plus room for user-facing errors, and a `clientMutationId` passthrough for idempotency tracking. The modern approach to **errors-as-data** models expected business failures (validation, insufficient funds, not found) as union members in the payload—`CreatePostPayload = PostCreated | ValidationError | RateLimited`—while reserving the top-level `errors` array for genuinely exceptional failures. This makes error handling type-safe and introspectable rather than string-parsed.

**Subscriptions** deliver server-pushed events over a stateful transport, usually WebSockets via the `graphql-ws` protocol or Server-Sent Events. The server pairs each subscription field with an async iterator; each event is passed through the normal execution engine so clients receive exactly the shape they selected. At scale, subscription fan-out is backed by a pub/sub system (Redis, Kafka, NATS) and horizontal scaling requires that any node can serve any subscriber.

The **`@defer` and `@stream` directives**, now in the specification's later stages, allow incremental delivery: a client marks a slow fragment with `@defer` and receives the fast part of the response immediately, followed by patches as the slow part resolves. `@stream` does the same for list items. This brings the latency profile of multiple requests to the ergonomics of one document.

**Persisted queries** and **trusted documents** move the query text out of the request. The client sends a hash; the server looks the hash up in an allowlist and executes the stored document. Automatic Persisted Queries (APQ) reduce bandwidth; the stricter trusted-documents model turns the GraphQL endpoint into something closer to a set of pre-approved RPCs, eliminating arbitrary-query attack surface while preserving the developer experience of writing GraphQL during development.

**Security** is where GraphQL's flexibility demands discipline. Because clients compose queries, a malicious client can compose pathological ones: deeply nested cyclic selections (`friends { friends { friends ... } }`), alias amplification (the same expensive field requested thousands of times under different aliases), or batching floods. Defenses are layered: **depth limiting**, **query complexity analysis** (assigning static or argument-dependent costs to fields and rejecting documents exceeding a budget), **alias and directive count limits**, **rate limiting by cost rather than by request**, **timeouts**, disabling introspection in production, and ultimately trusted documents. Authorization belongs in the business layer or in resolver middleware, never in the schema shape alone—a field being present in the schema says nothing about who may read it.

**Caching** is harder than REST because everything is a POST to one endpoint. Approaches include GET requests with persisted-query hashes for CDN caching, response caching keyed on the normalized document and variables with per-field cache hints (`@cacheControl(maxAge:)`), and entity-level caching inside resolvers. Normalized client caches handle most of the client-side story.

**Schema evolution** follows one rule: never make a breaking change; add instead. Adding fields, types, and optional arguments is safe. Removing fields, changing types, making an argument required, or making a nullable field non-null breaks clients. Because clients declare exactly which fields they use, **field usage analytics** make it possible to know when a deprecated field has genuinely zero traffic and can finally be removed. This observability is why GraphQL APIs are typically unversioned.

## Part V — Federation: One Graph, Many Teams

A single GraphQL schema is a wonderful thing for clients and a political nightmare for organizations. If one monolithic GraphQL server fronts fifty backend services owned by fifteen teams, every schema change funnels through one codebase, one deploy pipeline, and one group of overworked gateway maintainers. **Federation** is the architectural answer: the schema is split into **subgraphs**, each owned and deployed independently by a team, and a **router** (also called a **gateway**) composes them into a single **supergraph** that clients query as if it were one server. The client never knows federation exists.

The crucial conceptual leap is that federation divides the graph *by type ownership and field ownership*, not merely by type. The `Users` subgraph may define `User { id name email }`. The `Reviews` subgraph may *extend* that same `User` with `reviews: [Review]`. The `Products` subgraph may add `recommendedProducts`. A single `User` object in a client response is stitched together from three services, and each team deploys its contribution without coordinating with the others. This is what distinguishes federation from the older **schema stitching** approach, where a central gateway programmatically merged schemas and hand-wrote the glue; federation pushes the declarations into the subgraphs themselves via directives and standardizes the glue.

### Entities and the Federation Directives

An **entity** is a type that can be referenced and extended across subgraphs. A type becomes an entity when a subgraph annotates it with `@key(fields: "id")`, declaring which fields uniquely identify an instance. Keys can be compound (`@key(fields: "sku region")`), nested (`@key(fields: "org { id } slug")`), and a type can declare multiple keys. The subgraph that declares a key must be able to **resolve a reference**: given only the key fields, it must return the full object. This is done by implementing a **reference resolver** (`__resolveReference` in most frameworks), which the router invokes through a special, automatically generated root field called `_entities(representations: [_Any!]!)`. A **representation** is a minimal object containing `__typename` and the key fields—essentially a pointer. The router sends batches of representations to a subgraph and gets back the hydrated entities.

`@external` marks a field that is defined in another subgraph but referenced here; it tells the composer "I know this field exists, I don't own it, but I need to talk about it." `@requires(fields: "...")` says that to compute this field, the subgraph needs the values of certain external fields first—the router will fetch those from the owning subgraph and include them in the representation. The canonical example is a shipping subgraph that defines `Product.shippingEstimate @requires(fields: "weight dimensions")`, where weight and dimensions live in the inventory subgraph. `@provides(fields: "...")` is the optimization twin: it declares that when this subgraph returns an entity through a particular field, it can also supply certain fields that normally belong elsewhere, saving the router a hop. `@shareable` (Federation 2) declares that a field may be resolved identically by multiple subgraphs, allowing redundancy and locality; without it, composition fails on the conflict. `@override(from: "subgraphName")` enables **field migration**: a new subgraph can take ownership of a field from an old one atomically, which is how teams gradually decompose monoliths without downtime. `@inaccessible` hides a field from the supergraph's public API while still allowing it to participate in internal `@requires` plumbing. `@interfaceObject` lets a subgraph contribute fields to an interface's implementations without knowing the concrete types. `@tag` attaches metadata used for contracts and tooling. `@authenticated`, `@requiresScopes`, and `@policy` push authorization declarations into the schema so the router can enforce them before any subgraph is called.

### Composition and the Supergraph Schema

**Composition** is the build-time process that takes all subgraph schemas, validates that they are mutually consistent, and emits the **supergraph schema**—an annotated SDL that contains the merged public **API schema** plus routing metadata encoded as `@join__*` directives describing which subgraph owns what and how to reach it. Composition is where conflicts are caught: two subgraphs defining the same non-shareable field, a `@requires` referencing a field that no subgraph provides, an entity with no reference resolver, an enum with inconsistent values, a type that is an input in one place and an output in another. Because composition fails fast, it acts as an integration test that runs before anything deploys. **Satisfiability** is the formal property composition checks: for every field in the API schema reachable through every possible path, can the router construct a plan that resolves it? If a type is extended with a field in subgraph B but the only `@key` for that type can't be resolved by B, the field is unsatisfiable, and composition rejects it with an explanation.

A **schema registry** (Apollo GraphOS, Hive, WunderGraph Cosmo, Grafbase, and others) stores every subgraph's schema, runs composition on each publish, performs **schema checks** against historical traffic (would this change break any operation seen in the last thirty days?), and distributes the resulting supergraph to routers via **managed federation**, so routers hot-reload the new graph without redeploying. This workflow—publish, compose, check, distribute—is the heart of federated governance.

### Query Planning

At runtime the router performs **query planning**: it takes the client's operation, walks the supergraph's routing metadata, and produces a **query plan**, a tree of **fetch nodes** (each a subgraph request), **flatten nodes** (that reshape intermediate results into representations), **sequence nodes** (fetches that depend on prior results), and **parallel nodes**. For `{ me { name reviews { body product { name price } } } }` with three subgraphs, the plan is roughly: fetch `me { id name }` from Users; then, using `me.id` as a representation, fetch `reviews { body product { id } }` from Reviews via `_entities`; then, using the product ids as representations, fetch `name price` from Products via `_entities`. Plans are cached per operation signature. The planner's quality—minimizing round trips, maximizing parallelism, exploiting `@provides` to skip hops—is a large part of the difference between federation implementations, and modern routers (Apollo Router in Rust, Cosmo Router in Go, Hive Gateway, Grafbase Gateway) treat planning as a serious optimization problem with heuristics and cost models.

The router also handles **entity caching** (caching `_entities` responses by key), **coprocessors and plugins** for authentication, header propagation, and request transformation, **subscriptions over federation** (the router manages the long-lived connection and fans out to the owning subgraph), `@defer` across subgraph boundaries, distributed tracing with per-subgraph spans, and **demand control**—cost-based rate limiting computed over the query plan rather than over the single incoming request.

### Contracts, Variants, and Multi-Tenancy

**Contracts** derive filtered supergraphs from one source graph using `@tag`: tag internal-only fields `@tag(name: "internal")` and generate a partner-facing contract that excludes them. One supergraph, many public faces, no code duplication. **Variants** are named environments (staging, production, canary) of the same graph, each with its own composed supergraph and its own routers.

### Federation Versus the Alternatives

**Schema stitching** merges schemas imperatively at the gateway and remains useful for wrapping third-party or legacy GraphQL APIs you don't control, since it requires no subgraph cooperation. **A BFF (backend-for-frontend)** is one GraphQL server per client type that calls downstream REST services; simple, but reintroduces duplication when many clients exist. **GraphQL over gRPC/REST without federation** (a single monolithic gateway) works fine until Conway's law makes it a bottleneck. Federation's trade-offs are real: it introduces a new infrastructure component that must be highly available and performant; it requires every team to learn the entity and key model; cross-subgraph joins add latency compared to a well-indexed monolith; and debugging a query that fans across six services demands distributed tracing from day one. The payoff is organizational: teams ship independently against a schema that remains, from the client's perspective, one coherent graph with one set of types, one introspection endpoint, and one URL.

## Part VI — The Deeper View

For those inclined to theory: a GraphQL schema is a directed, typed graph where object types are nodes and fields are labeled edges with arity (scalar, object, list) and nullability modality. A query is a *finite tree unfolding* of that graph rooted at `Query`; validation ensures the tree is a valid projection, and execution is a *catamorphism* over the tree, folding resolver results upward. Nullability with error propagation is a monadic error model where `!` tightens the failure boundary. Federation decomposes the global graph into a set of local graphs that share nodes (entities) identified by keys—essentially a *pushout* of schemas along their shared entity types—and query planning is a search over the possible join paths of that shared structure. Understanding it this way explains why keys must be resolvable (the join needs a lookup), why `@requires` induces sequential plan nodes (data dependency edges), and why composition is decidable and checkable at build time (the graph is finite and the satisfiability problem is a reachability question).

## A Compact Glossary

**Schema / SDL** — the type contract and its textual syntax. **Document / Operation / Selection set** — the client request, its named unit, and the braces of requested fields. **Resolver** — the function that produces a field's value; **reference resolver** — the one that hydrates an entity from its key. **Context** — per-request shared state. **DataLoader** — batching and memoization to defeat N+1. **Non-null / null bubbling** — the `!` modifier and the upward propagation of errors through it. **Fragment / inline fragment / type condition** — reusable selections and polymorphic branches. **Interface / Union / Input type / Enum / Custom scalar** — the compound and leaf type kinds. **Connection / Edge / Cursor / PageInfo** — the Relay pagination vocabulary. **Node / Global Object Identification** — universal refetch by ID. **Introspection** — the schema describing itself. **Directive** — annotation for behavior. **Persisted query / Trusted document** — hash-referenced, pre-registered operations. **Query complexity / Depth limit / Demand control** — cost-based protection. **Subscription / graphql-ws** — real-time push and its transport. **`@defer` / `@stream`** — incremental delivery. **Subgraph / Supergraph / Router (Gateway)** — the parts of a federated system. **Entity / `@key` / Representation / `_entities`** — the cross-service join mechanism. **`@external` / `@requires` / `@provides` / `@shareable` / `@override` / `@inaccessible` / `@interfaceObject` / `@tag`** — the federation directives. **Composition / Satisfiability / API schema** — build-time merging and its validation. **Query plan / Fetch node / Flatten** — runtime routing. **Schema registry / Schema checks / Managed federation / Contracts / Variants** — the governance layer.

If you remember only three things: the client owns the shape, the server owns the types, and federation lets many teams own the types without the client ever noticing the seams.
