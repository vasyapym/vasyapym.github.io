## Часть 0. Зачем вообще существует Go

### История и мотивация

Go придумали в Google в 2007 году Роб Пайк, Кен Томпсон (соавтор Unix
и C) и Роберт Гризмер. Проблема, которую они решали, была очень
конкретной:

- Огромные кодовые базы на C++ компилировались **часами**.
- Многопоточное программирование на C++/Java было болезненным и
подверженным ошибкам.
- Языки стали сложными: чтобы читать чужой код, нужно было знать десятки фич.
- Многоядерные процессоры стали нормой, а языки были спроектированы
для одноядерного мира.

Go — это **реакция на сложность**. Его философия: *меньше — значит
больше*. Язык сознательно НЕ имеет многих вещей: классов и
наследования, исключений, перегрузки операторов, тернарного оператора,
неявных преобразований типов. Это не недоработка, а дизайн.

### Ключевые свойства (запомните, они объясняют всё остальное)

1. **Компилируемый** — исходник превращается в машинный код одного
бинарного файла. Нет виртуальной машины, нет интерпретатора.
2. **Статически типизированный** — типы известны на этапе компиляции.
3. **Со сборщиком мусора** — вы не освобождаете память вручную, как в C.
4. **Конкурентность встроена в язык** — горутины и каналы, а не библиотека.
5. **Простой** — спецификация языка читается за вечер (~100 страниц).
6. **Ортогональный** — фичи не пересекаются; обычно есть один
очевидный способ сделать вещь.

### Ментальная модель №1: «Go — это C для XXI века с GC и горутинами»

Если вы знаете, как работает C (указатели, структуры, память), Go
будет очень знаком. Если не знаете — Go отличное место это выучить,
потому что он не прячет от вас машину, но и не даёт выстрелить себе в
ногу так легко.

## Часть 1. Первые принципы: что происходит, когда вы запускаете программу

Прежде чем писать код, нужно понять, **что такое программа
физически**. Многие опытные программисты, пришедшие из Python/JS,
здесь имеют пробелы.

### 1.1. От исходника к процессу

```
main.go  --[компилятор go]-->  бинарный файл (ELF/Mach-O/PE)
--[ОС]-->  процесс в памяти
```

- **Компилятор** читает текст, проверяет типы, генерирует машинные
инструкции для конкретного процессора (amd64, arm64...) и операционной
системы.
- **Линковщик** склеивает ваш код, стандартную библиотеку и **рантайм
Go** в один файл. Поэтому бинарник Go «толстый» (2–10 МБ для hello
world) — но он **не зависит ни от чего** на целевой машине.
Скопировали файл — работает.
- **Рантайм Go** — это код, который живёт внутри каждого бинарника и
делает: сборку мусора, планирование горутин, управление памятью,
обработку паник. Это не виртуальная машина, а просто библиотека,
вкомпилированная в программу.

### 1.2. Память процесса: стек и куча

Это фундаментально. Разберём честно.

Когда программа работает, у неё есть несколько областей памяти:

- **Код** (text) — инструкции, только чтение.
- **Глобальные данные** — переменные уровня пакета.
- **Стек** (stack) — память для локальных переменных функций. Работает
как стопка тарелок: вызвали функцию — положили «кадр» (frame) с её
переменными; вернулись — сняли. Очень быстро (просто сдвиг указателя),
освобождается автоматически.
- **Куча** (heap) — память для данных, время жизни которых не
привязано к вызову функции. Управляется сборщиком мусора. Медленнее,
потому что нужно искать свободное место и потом чистить.

**Почему это важно в Go:** компилятор сам решает, где разместить
переменную — на стеке или в куче. Это называется **escape analysis**
(«анализ утечки»). Если компилятор может доказать, что переменная не
переживёт функцию, она живёт на стеке. Если переменная «убегает»
(например, вы возвращаете указатель на неё) — она отправляется в кучу.

```go
func makeInt() *int {
    x := 42      // x «убегает» через возвращаемый указатель →
размещается в куче
    return &x    // в C это была бы ошибка (висячий указатель), в Go — нормально
}
```

Вы можете это увидеть: `go build -gcflags="-m" .` покажет `moved to heap: x`.

**Мысль великих программистов:** в Go можно вернуть адрес локальной
переменной, и это безопасно. Не потому, что стек «магический», а
потому что компилятор переместил переменную в кучу. Понимание этого
объясняет, почему одни программы аллоцируют много, а другие — нет, и
почему это влияет на производительность.

### 1.3. Каждая горутина имеет свой стек

В Go у каждой горутины (лёгкого потока) свой стек, который начинается
с ~2–8 КБ и **растёт по мере необходимости** (рантайм копирует стек в
большую область). Поэтому горутин можно создать миллион, а потоков ОС
(со стеком в 1–8 МБ) — тысячи. Вернёмся к этому в разделе про
конкурентность.

### 1.4. Сборщик мусора (GC)

GC в Go — **конкурентный, трёхцветный, mark-and-sweep**. Простыми словами:

1. **Mark** (пометка): начиная с «корней» (глобальные переменные,
стеки горутин), GC обходит все указатели и помечает достижимые
объекты.
2. **Sweep** (очистка): всё, что не помечено, — мусор, память
возвращается в пул.

Ключевая особенность — GC работает **параллельно** с вашей программой,
паузы обычно меньше миллисекунды. Но GC не бесплатен: он тратит CPU и
пробегает по памяти. Поэтому в Go-сообществе так много внимания
уделяют «снижению аллокаций» — меньше объектов в куче → меньше работы
GC.

**Следствие для мышления:** Go — не Java, где «аллоцируй что хочешь».
И не C, где ты всё контролируешь. Это середина: аллоцируй свободно, но
знай, где это происходит, и умей мерить.

## Часть 2. Установка, инструменты, первая программа

### 2.1. Установка

Скачайте с https://go.dev/dl/. Проверьте:

```bash
go version
# go version go1.22.x linux/amd64
```

Важные переменные окружения (посмотреть `go env`):
- `GOPATH` — где хранится кэш модулей (`~/go` по умолчанию). Раньше
был обязателен, сейчас — почти нет.
- `GOROOT` — где установлен сам Go.
- `GOOS`, `GOARCH` — целевая ОС и архитектура. Кросс-компиляция
тривиальна: `GOOS=linux GOARCH=arm64 go build`.

### 2.2. Модули: единица проекта

В Go проект = **модуль**. Модуль описывается файлом `go.mod`.

```bash
mkdir hello && cd hello
go mod init example.com/hello
```

Появится `go.mod`:
```
module example.com/hello

go 1.22
```

`example.com/hello` — **путь модуля**. Это одновременно и имя, и (по
соглашению) URL, откуда его можно скачать. Для локальных экспериментов
подойдёт любое имя.

### 2.3. Hello, world — построчно

Файл `main.go`:

```go
package main // 1

import "fmt" // 2

func main() { // 3
    fmt.Println("Привет, мир") // 4
}
```

1. `package main` — каждый файл принадлежит пакету. Пакет `main`
особенный: это исполняемая программа (в отличие от библиотеки).
2. `import "fmt"` — подключаем пакет `fmt` (format) из стандартной библиотеки.
3. `func main()` — точка входа. Не принимает аргументов, ничего не возвращает.
4. `fmt.Println` — функция `Println` из пакета `fmt`. Заглавная буква
`P` — не случайность (см. ниже про экспорт).

```bash
go run main.go     # скомпилировать во временный файл и запустить
go build           # создать бинарник ./hello
./hello
```

### 2.4. Правило заглавной буквы (экспорт)

В Go нет ключевых слов `public`/`private`. Вместо них — **первая буква
идентификатора**:

- `Println`, `User`, `MaxSize` — с заглавной → **экспортируются**
(видны из других пакетов).
- `println`, `user`, `maxSize` — со строчной → приватны для пакета.

Это одно из решений «убрать лишнее»: видимость видна сразу в месте
использования.

### 2.5. Инструменты, которые вы будете использовать каждый день

```bash
go fmt ./...      # форматирование (единый стиль — не обсуждается!)
go vet ./...      # статический анализ подозрительных конструкций
go test ./...     # тесты
go build ./...    # компиляция всего
go mod tidy       # синхронизировать go.mod с реальными импортами
go doc fmt.Println   # документация
go get github.com/x/y@v1.2.3  # добавить зависимость
```

`./...` означает «этот каталог и все вложенные рекурсивно».

**gofmt — это культурный феномен.** В Go нет споров о стиле. Табы,
расстановка скобок — всё решено. Настройте редактор форматировать при
сохранении и забудьте.

## Часть 3. Основы синтаксиса: переменные, типы, значения

### 3.1. Объявление переменных

```go
var x int          // объявление с явным типом; x = 0
var y int = 10     // с инициализацией
var z = 10         // тип выводится: int
w := 10            // короткое объявление — только внутри функций

var (              // блочное объявление
    name string
    age  int
)
```

**Почему тип пишется после имени?** `var x int` читается как «x имеет
тип int». Для сложных типов это читается слева направо: `var f
func(int) string` — «f — функция из int в string». В C `char
(*(*x())[])()` — нечитаемо. Это осознанный выбор.

### 3.2. Нулевые значения (zero values) — фундаментальная идея

В Go **нет неинициализированных переменных**. Любая объявленная
переменная получает нулевое значение своего типа:

| Тип | Нулевое значение |
|---|---|
| числа | `0` |
| `bool` | `false` |
| `string` | `""` (пустая строка) |
| указатели, слайсы, map, каналы, функции, интерфейсы | `nil` |
| структуры | все поля нулевые |

**Почему это важно:** Go поощряет проектировать типы так, чтобы
**нулевое значение было полезным**. Например, `var buf bytes.Buffer` —
уже готовый к работе буфер. `var mu sync.Mutex` — готовый мьютекс. Не
нужен конструктор. Это принцип «make the zero value useful».

### 3.3. Базовые типы

```go
// Целые со знаком
int8, int16, int32, int64
int      // размер зависит от платформы (64 бита на 64-битных системах)

// Беззнаковые
uint8, uint16, uint32, uint64, uint, uintptr
byte  // псевдоним uint8
rune  // псевдоним int32 — символ Юникода

// Плавающая точка
float32, float64

// Комплексные
complex64, complex128

bool
string
```

**Правило:** используйте `int` для целых, `float64` для дробных, если
нет причин иначе. `int32`/`int64` — когда важен точный размер (сетевые
протоколы, файлы, БД).

### 3.4. Нет неявных преобразований

```go
var a int32 = 10
var b int64 = a       // ОШИБКА КОМПИЛЯЦИИ
var b int64 = int64(a) // правильно

var f float64 = 3.7
var i int = int(f)     // 3 (отбрасывание дробной части, не округление)
```

Это раздражает поначалу, но убирает целый класс багов (переполнения,
потеря точности), которые в C/JS находят в проде.

### 3.5. Константы и iota

```go
const Pi = 3.14159
const MaxUsers int = 100

const (
    Sunday = iota // 0
    Monday        // 1
    Tuesday       // 2
)

// Флаги-битмаски — классический приём
const (
    Read  = 1 << iota // 1 (0b001)
    Write             // 2 (0b010)
    Exec              // 4 (0b100)
)
```

`iota` — счётчик внутри блока `const`, начинается с 0, увеличивается
на каждой строке.

**Тонкость:** нетипизированные константы (`const Pi = 3.14`) имеют
произвольную точность и приобретают тип в месте использования. `var f
float32 = Pi` работает; `Pi * 2` — тоже.

### 3.6. Управляющие конструкции

В Go **один** цикл — `for`:

```go
for i := 0; i < 10; i++ { }   // классический

for cond { }                   // как while

for { }                        // бесконечный, выход через break

for i, v := range slice { }    // по коллекции: индекс и значение
for k, v := range mapa { }
for i := range 10 { }          // Go 1.22+: 0..9
```

`if` с инициализатором — идиома:

```go
if err := doSomething(); err != nil {
    return err
}
// err здесь уже не виден — область видимости ограничена if
```

`switch` без «проваливания» (fallthrough по умолчанию НЕТ):

```go
switch x {
case 1, 2:
    fmt.Println("один или два")
case 3:
    fmt.Println("три")
default:
    fmt.Println("другое")
}

// switch без выражения = цепочка if-else
switch {
case x < 0:
    ...
case x == 0:
    ...
}
```

### 3.7. Строки, байты, руны — здесь у многих пробел

Строка в Go — это **неизменяемая последовательность байтов**, а не
символов. Обычно это UTF-8, но язык этого не требует.

```go
s := "привет"
fmt.Println(len(s))       // 12, а не 6! Каждая кириллическая буква —
2 байта в UTF-8
fmt.Println(s[0])         // 208 — первый БАЙТ, не буква
fmt.Println(string(s[0])) // "Ð" — мусор

// Правильный обход по символам (рунам):
for i, r := range s {
    fmt.Printf("%d: %c\n", i, r) // i — байтовый индекс, r — rune
}
// 0: п, 2: р, 4: и, 6: в, 8: е, 10: т

runes := []rune(s)
fmt.Println(len(runes))   // 6
```

**Внутреннее устройство строки:** это структура из двух слов —
указатель на байты и длина. Передавать строку в функцию дёшево (16
байт копируются, сами данные — нет). Строки неизменяемы, поэтому их
безопасно разделять между горутинами.

**Конкатенация в цикле — антипаттерн:**

```go
// Плохо: каждая += создаёт новую строку — O(n²)
s := ""
for i := 0; i < 1000; i++ {
    s += "x"
}

// Хорошо:
var sb strings.Builder
for i := 0; i < 1000; i++ {
    sb.WriteString("x")
}
s := sb.String()
```

## Часть 4. Функции

### 4.1. Основы

```go
func add(a int, b int) int {
    return a + b
}

func add(a, b int) int { ... }  // сокращённая запись одинаковых типов

// Несколько возвращаемых значений — ОСНОВА идиоматики Go
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("деление на ноль")
    }
    return a / b, nil
}

result, err := divide(10, 2)
```

### 4.2. Именованные возвращаемые значения

```go
func split(sum int) (x, y int) {
    x = sum * 4 / 9
    y = sum - x
    return // «голый» return — возвращает x и y
}
```

Используйте с осторожностью: полезно для документирования и для
`defer`, изменяющего результат, но голый `return` в длинных функциях
ухудшает читаемость.

### 4.3. Вариативные функции

```go
func sum(nums ...int) int {   // nums — это []int
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}

sum(1, 2, 3)
s := []int{1, 2, 3}
sum(s...)  // распаковка слайса
```

### 4.4. Функции — значения первого класса

```go
func apply(f func(int) int, v int) int {
    return f(v)
}

double := func(x int) int { return x * 2 }
apply(double, 5) // 10

// Замыкания захватывают переменные ПО ССЫЛКЕ
func counter() func() int {
    count := 0
    return func() int {
        count++
        return count
    }
}
c := counter()
c() // 1
c() // 2
```

**Классическая ловушка с замыканиями (до Go 1.22):**

```go
for i := 0; i < 3; i++ {
    go func() { fmt.Println(i) }() // до 1.22: печатало 3 3 3, т.к. i
— одна переменная
}
```

С Go 1.22 каждая итерация создаёт свою `i`, и это печатает 0 1 2 (в
некотором порядке). Но понимать механизм всё равно нужно: **замыкание
захватывает переменную, а не её значение**.

### 4.5. `defer` — отложенное выполнение

`defer` откладывает вызов до **выхода из функции** (любым способом —
return, паника).

```go
func readFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close() // выполнится при выходе, что бы ни случилось дальше

    // ... работа с f ...
    return nil
}
```

Правила:
1. Отложенные вызовы выполняются в порядке **LIFO** (последний defer — первым).
2. **Аргументы вычисляются в момент `defer`**, а не выполнения:

```go
x := 1
defer fmt.Println(x) // напечатает 1
x = 2
```

3. `defer` внутри цикла накапливается до конца функции — потенциальная
утечка ресурсов:

```go
// Плохо: 1000 файлов открыты одновременно до конца функции
for _, p := range paths {
    f, _ := os.Open(p)
    defer f.Close()
}

// Хорошо: вынести в функцию
for _, p := range paths {
    func() {
        f, _ := os.Open(p)
        defer f.Close()
        // ...
    }()
}
```

**Почему defer, а не try/finally?** Потому что освобождение ресурса
пишется рядом с его захватом. Читая код, вы видите `Open` и сразу
`defer Close` — не нужно листать вниз.

## Часть 5. Составные типы: массивы, слайсы, map

Это раздел, где **больше всего пробелов у опытных программистов**.
Читайте внимательно.

### 5.1. Массивы — значения фиксированной длины

```go
var a [3]int          // [0 0 0]
b := [3]int{1, 2, 3}
c := [...]int{1, 2, 3} // компилятор посчитает длину

fmt.Println(len(a))
```

**Ключевое:** длина — часть типа. `[3]int` и `[4]int` — разные типы. И
массивы **копируются при присваивании и передаче в функцию**:

```go
x := [3]int{1, 2, 3}
y := x        // полная копия
y[0] = 99
fmt.Println(x[0]) // 1 — x не изменился
```

Из-за этого массивы в Go используют редко напрямую. Их главная роль —
быть основой для слайсов.

### 5.2. Слайсы — самый важный тип в Go

**Слайс — это не массив.** Слайс — это маленькая структура-заголовок
из трёх полей, которая указывает на участок массива:

```go
type sliceHeader struct {
    ptr *T   // указатель на первый элемент в базовом массиве
    len int  // длина — сколько элементов доступно
    cap int  // ёмкость — сколько места от ptr до конца базового массива
}
```

Рисунок:

```
базовый массив:  [ 10 | 20 | 30 | 40 | 50 ]
                        ^
s := arr[1:3]           |
s.ptr ─────────────────┘
s.len = 2  (20, 30)
s.cap = 4  (20, 30, 40, 50 — до конца массива)
```

Создание:

```go
s := []int{1, 2, 3}         // литерал: len=3, cap=3
s := make([]int, 5)         // len=5, cap=5, все нули
s := make([]int, 0, 10)     // len=0, cap=10 — «пустой, но с местом»
var s []int                 // nil-слайс: ptr=nil, len=0, cap=0
```

### 5.3. Почему передача слайса в функцию — «полуссылка»

Заголовок копируется (24 байта), но `ptr` указывает на **тот же массив**:

```go
func modify(s []int) {
    s[0] = 100 // изменяет базовый массив → видно снаружи
}

func appendOne(s []int) {
    s = append(s, 1) // изменяет ЛОКАЛЬНУЮ копию заголовка → НЕ видно снаружи
}

a := []int{1, 2, 3}
modify(a)     // a == [100 2 3]
appendOne(a)  // a по-прежнему [100 2 3]
```

Это — **самая частая ошибка новичков в Go**. Запомните: изменение
элементов видно, изменение длины — нет (если не вернуть слайс).

### 5.4. `append` и рост ёмкости

```go
s := make([]int, 0, 2)
s = append(s, 1)  // len=1, cap=2, тот же массив
s = append(s, 2)  // len=2, cap=2, тот же массив
s = append(s, 3)  // cap исчерпан! → аллоцируется НОВЫЙ массив (обычно
вдвое больше),
                  // элементы копируются, s.ptr теперь указывает на новый массив
```

**Всегда пишите `s = append(s, ...)`.** append может вернуть слайс с
новым `ptr`.

### 5.5. Коварная ловушка: общий базовый массив

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]           // b = [2 3], len=2, cap=4 — делит массив с a
b = append(b, 99)     // cap хватает → пишет в базовый массив!
fmt.Println(a)        // [1 2 3 99 5] — a изменился, хотя мы трогали только b!
```

Защита — **полное выражение слайса** `a[low:high:max]`, ограничивающее cap:

```go
b := a[1:3:3]         // len=2, cap=2
b = append(b, 99)     // cap исчерпан → новый массив, a не тронут
```

Или явное копирование:

```go
b := make([]int, len(a[1:3]))
copy(b, a[1:3])
// или в Go 1.21+: b := slices.Clone(a[1:3])
```

**Как думают опытные гоферы:** «Кто владеет этим слайсом? Могу ли я
его мутировать, или кто-то ещё держит заголовок на тот же массив?»
Если функция получает слайс и собирается его менять — либо
документировать это, либо копировать.

### 5.6. nil-слайс vs пустой слайс

```go
var a []int          // nil
b := []int{}         // не nil, но len=0
c := make([]int, 0)  // не nil, len=0

a == nil // true
b == nil // false

// Для практики почти всегда неважно: len, range, append работают одинаково.
// Разница проявляется в JSON: nil → null, пустой → []
```

Идиоматично проверять `len(s) == 0`, а не `s == nil`.

### 5.7. Полезные операции

```go
copy(dst, src)                    // копирует min(len(dst), len(src)) элементов
s = append(s[:i], s[i+1:]...)     // удаление i-го элемента (сдвиг)
s = slices.Delete(s, i, i+1)      // Go 1.21+
slices.Sort(s)
slices.Contains(s, x)
slices.Index(s, x)
```

Пакет `slices` (Go 1.21+) — обязательно изучите, он избавляет от кучи
ручного кода.

### 5.8. Map — хеш-таблица

```go
m := make(map[string]int)
m := map[string]int{"a": 1, "b": 2}
var m map[string]int  // nil-map: ЧИТАТЬ можно, ПИСАТЬ — паника!

m["c"] = 3
v := m["a"]         // 1
v := m["zzz"]       // 0 — нулевое значение, НЕ ошибка!
v, ok := m["zzz"]   // ok == false — «идиома запятая-ok»
delete(m, "a")
len(m)

for k, v := range m { }  // порядок обхода СЛУЧАЙНЫЙ — специально!
```

**Почему порядок случайный?** Разработчики Go намеренно
рандомизировали его, чтобы никто не зависел от порядка (который и так
был не гарантирован). Нужен порядок — соберите ключи в слайс и
отсортируйте.

**Map — ссылочный тип.** Переменная map — это указатель на внутреннюю
структуру. Передача в функцию не копирует данные; изменения видны
везде.

**Map не потокобезопасен.** Одновременная запись из двух горутин →
fatal error (рантайм это детектирует). Нужна синхронизация (мьютекс)
или `sync.Map` для специфических случаев.

**Ключом может быть только сравнимый тип:** числа, строки, bool,
указатели, структуры из сравнимых полей, массивы. Слайсы, map, функции
— не могут.

**Нельзя взять адрес элемента map:** `&m["a"]` — ошибка компиляции,
потому что при росте таблицы элементы переезжают. Следствие — нельзя
менять поле структуры в map напрямую:

```go
type P struct{ X int }
m := map[string]P{"a": {1}}
m["a"].X = 2      // ОШИБКА
p := m["a"]; p.X = 2; m["a"] = p  // так
// или храните указатели: map[string]*P
```

## Часть 6. Структуры, указатели, методы

### 6.1. Указатели — без страха

Указатель — это переменная, содержащая **адрес** другой переменной в памяти.

```go
x := 10
p := &x        // & — «взять адрес». p имеет тип *int
fmt.Println(*p) // * — «разыменовать»: получить значение по адресу → 10
*p = 20
fmt.Println(x)  // 20
```

В Go нет арифметики указателей (нельзя `p++`), поэтому они безопасны.
`nil`-указатель при разыменовании вызывает панику (а не неопределённое
поведение, как в C).

**Зачем указатели, если есть GC?** Две причины:
1. **Изменяемость (mutability):** передать функции возможность
изменить исходную переменную.
2. **Избежать копирования** больших структур.

### 6.2. Структуры

```go
type User struct {
    Name  string
    Email string
    Age   int
}

u := User{Name: "Анна", Email: "a@x.ru", Age: 30} // именованные поля
— предпочтительно
u := User{"Анна", "a@x.ru", 30}                    // позиционно —
хрупко, избегайте
var u User                                          // все поля нулевые

u.Age = 31
p := &u
p.Age = 32     // Go автоматически разыменовывает: (*p).Age

// Анонимные структуры — для одноразовых вещей
point := struct{ X, Y int }{1, 2}
```

**Структуры — значения.** Присваивание копирует все поля:

```go
a := User{Name: "A"}
b := a
b.Name = "B"
// a.Name по-прежнему "A"
```

### 6.3. Встраивание (embedding) — композиция вместо наследования

```go
type Animal struct {
    Name string
}
func (a Animal) Speak() string { return "..." }

type Dog struct {
    Animal     // встроенное поле — без имени
    Breed string
}

d := Dog{Animal: Animal{Name: "Шарик"}, Breed: "дворняга"}
fmt.Println(d.Name)    // поля Animal «поднимаются» → d.Animal.Name
fmt.Println(d.Speak()) // методы тоже
```

**Это НЕ наследование.** `Dog` не является `Animal`. Нельзя передать
`Dog` туда, где ждут `Animal`. Это просто синтаксический сахар для
делегирования: `d.Speak()` = `d.Animal.Speak()`. Нет виртуальных
методов: если `Animal.Speak` вызывает другой метод, он вызовет версию
`Animal`, а не `Dog`.

### 6.4. Методы

Метод — это функция с **получателем** (receiver):

```go
type Rect struct{ W, H float64 }

// Value receiver — работает с КОПИЕЙ
func (r Rect) Area() float64 {
    return r.W * r.H
}

// Pointer receiver — работает с ОРИГИНАЛОМ
func (r *Rect) Scale(k float64) {
    r.W *= k
    r.H *= k
}

r := Rect{2, 3}
r.Area()    // 6
r.Scale(2)  // Go сам возьмёт &r
r.Area()    // 24
```

Методы можно определять на **любом именованном типе** (не только
структурах), объявленном в этом же пакете:

```go
type Celsius float64
func (c Celsius) ToF() float64 { return float64(c)*9/5 + 32 }

type IntList []int
func (l IntList) Sum() int { ... }
```

### 6.5. Value vs pointer receiver: правила выбора

1. **Метод изменяет получателя** → pointer.
2. **Структура большая** (условно > 64 байт) → pointer, чтобы не копировать.
3. **Есть хоть один pointer-метод** → делайте все pointer для консистентности.
4. **Тип содержит мьютекс или иное некопируемое** → pointer
обязательно (копирование мьютекса — баг; `go vet` это ловит).
5. Маленькие неизменяемые типы (`time.Time`, координаты) → value.

**Почему это важно для интерфейсов:** метод с pointer receiver входит
в **набор методов** только `*T`, но не `T`. Значит, `T` не будет
удовлетворять интерфейсу с этим методом. Об этом — дальше.

### 6.6. Конструкторы — просто соглашение

```go
func NewUser(name string) *User {
    return &User{Name: name, CreatedAt: time.Now()}
}
```

Нет специального синтаксиса. Функция `NewXxx` — просто конвенция.
Возвращать указатель или значение — зависит от типа (см. правила
выше).

## Часть 7. Интерфейсы — сердце дизайна в Go

### 7.1. Что это

Интерфейс — это **набор сигнатур методов**. Тип удовлетворяет
интерфейсу, если у него есть все эти методы. **Неявно** — никакого
`implements`.

```go
type Shape interface {
    Area() float64
}

type Circle struct{ R float64 }
func (c Circle) Area() float64 { return math.Pi * c.R * c.R }

type Square struct{ S float64 }
func (s Square) Area() float64 { return s.S * s.S }

func PrintArea(s Shape) {
    fmt.Println(s.Area())
}

PrintArea(Circle{1})  // работает — Circle имеет Area()
PrintArea(Square{2})  // работает
```

### 7.2. Почему неявная реализация — гениально

1. **Развязка пакетов.** Пакет `io` определяет `Reader`. Ваш тип его
реализует, ничего не импортируя из `io`. Пакет с типом не знает об
интерфейсе; пакет с интерфейсом не знает о типе.
2. **Интерфейс определяет потребитель, а не производитель.** Вместо
«вот мой класс с интерфейсом на все случаи жизни» — «моей функции
нужно только `Read`, определю интерфейс с одним методом».
3. **Ретроактивность.** Можно описать интерфейс для уже существующего
чужого типа.

### 7.3. Идиома: маленькие интерфейсы

Самые важные интерфейсы стандартной библиотеки — из одного метода:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
type Writer interface {
    Write(p []byte) (n int, err error)
}
type Stringer interface {
    String() string
}
type error interface {   // да, error — просто интерфейс
    Error() string
}
```

`io.Reader` реализуют файлы, сетевые соединения, HTTP-тела, буферы,
gzip-декодеры, строки... И любая функция, принимающая `io.Reader`,
работает со всем этим. Это **композиция через интерфейсы**.

**Правило Роба Пайка:** *«Чем больше интерфейс, тем слабее
абстракция»*. Интерфейсы из 1–3 методов. Комбинируйте встраиванием:

```go
type ReadWriter interface {
    Reader
    Writer
}
```

### 7.4. Как интерфейс устроен внутри (важно для понимания nil-ловушки)

Значение интерфейса — это пара из двух слов:

```
interface value = (тип, указатель на данные)
                  (itab/type, data)
```

```go
var s Shape          // (nil, nil) → s == nil
s = Circle{1}        // (Circle, ptr→Circle{1}) → s != nil
```

### 7.5. Ловушка №1 в Go: «nil-интерфейс, который не nil»

```go
type MyErr struct{}
func (e *MyErr) Error() string { return "ошибка" }

func doSomething() error {
    var e *MyErr = nil
    return e   // возвращаем nil-указатель, обёрнутый в интерфейс error
}

err := doSomething()
fmt.Println(err == nil) // FALSE!!!
```

Почему: `err` — это `(*MyErr, nil)`. Тип не nil → интерфейс не nil.
Хотя указатель внутри nil.

**Правило:** если функция возвращает `error` и ошибки нет —
возвращайте **литеральный `nil`**, а не nil-указатель конкретного
типа.

### 7.6. Пустой интерфейс и `any`

```go
var x interface{}  // любой тип
var x any          // то же самое, Go 1.18+
```

Используется, когда тип действительно неизвестен (`json.Unmarshal`,
`fmt.Println`). Злоупотребление — антипаттерн: вы теряете
типобезопасность. С появлением дженериков нужда в `any` сильно упала.

### 7.7. Утверждение типа (type assertion) и type switch

```go
var i any = "hello"

s := i.(string)       // паника, если не string
s, ok := i.(string)   // безопасно: ok == false, если не string

switch v := i.(type) {
case string:
    fmt.Println("строка", v)
case int:
    fmt.Println("число", v)
case nil:
    fmt.Println("nil")
default:
    fmt.Printf("неизвестный %T\n", v)
}
```

### 7.8. Набор методов и указатели

```go
type Counter struct{ n int }
func (c *Counter) Inc() { c.n++ }

type Incrementer interface{ Inc() }

var i Incrementer
i = &Counter{}  // OK
i = Counter{}   // ОШИБКА: Counter (значение) не имеет метода Inc — он
есть только у *Counter
```

Почему: значение в интерфейсе — копия; если бы `Inc` вызывался на
копии, изменение потерялось бы. Компилятор запрещает это.

### 7.9. Как опытные гоферы используют интерфейсы

- **Принимай интерфейсы, возвращай структуры.** Функция принимает
`io.Reader` (гибко для вызывающего), возвращает `*bytes.Buffer`
(конкретно, вызывающий знает, что получил).
- **Не создавай интерфейс заранее.** Сначала конкретный тип. Интерфейс
— когда появилась вторая реализация или нужен мок в тесте.
- **Интерфейс определяется там, где используется**, а не там, где реализуется.
- Проверка реализации на этапе компиляции:

```go
var _ Shape = (*Circle)(nil) // если Circle перестанет реализовывать
Shape — не скомпилируется
```

## Часть 8. Обработка ошибок — «почему нет исключений»

### 8.1. Философия

В Go ошибка — это **обычное значение**, которое функция возвращает. Не
механизм прерывания потока управления.

```go
f, err := os.Open("file.txt")
if err != nil {
    return err
}
```

Почему так:
1. **Явность.** Читая код, вы видите каждую точку, где что-то может
пойти не так. С исключениями любая строка может «выбросить», и это
невидимо.
2. **Ошибка — часть контракта функции.** Она в сигнатуре.
3. **Нет скрытого потока управления.** Исключения — это `goto` через
много уровней стека.

Да, `if err != nil` пишется много. Это цена явности. Гоферы её принимают.

### 8.2. Создание ошибок

```go
errors.New("что-то пошло не так")
fmt.Errorf("не удалось открыть %s: %w", path, err)  // %w — обёртывание!
```

### 8.3. Обёртывание и цепочки ошибок (Go 1.13+)

Проблема: ошибка поднимается через 5 уровней. На каждом хочется
добавить контекст, но сохранить исходную ошибку для проверки.

```go
func readConfig() error {
    _, err := os.Open("cfg.yaml")
    if err != nil {
        return fmt.Errorf("readConfig: %w", err) // %w сохраняет err внутри
    }
    return nil
}

err := readConfig()
// err.Error() == "readConfig: open cfg.yaml: no such file or directory"

// Проверка на конкретную ошибку в цепочке:
if errors.Is(err, os.ErrNotExist) {
    // файла нет — можно создать дефолтный
}

// Извлечение конкретного типа из цепочки:
var pathErr *os.PathError
if errors.As(err, &pathErr) {
    fmt.Println(pathErr.Path)
}
```

**Правила:**
- `errors.Is(err, target)` — «есть ли в цепочке ошибка, равная target»
(для sentinel-ошибок).
- `errors.As(err, &target)` — «есть ли в цепочке ошибка типа target»
(для типизированных ошибок).
- **Никогда не сравнивайте `err == ErrX`** — после обёртывания это
сломается. Только `errors.Is`.
- Оборачивайте с контекстом: «что делали», а не «произошла ошибка». Не
дублируйте: `fmt.Errorf("error: %w", err)` — бесполезно.

### 8.4. Sentinel-ошибки и типы ошибок

```go
// Sentinel — заранее объявленная ошибка для сравнения
var ErrNotFound = errors.New("not found")

// Тип — когда нужны данные
type ValidationError struct {
    Field string
    Msg   string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("поле %s: %s", e.Field, e.Msg)
}
```

### 8.5. Паника и recover

`panic` — для **непоправимых** ситуаций: баг программиста (индекс за
границей, nil-разыменование), невозможное состояние. Не для «файл не
найден».

```go
func safeDivide(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("паника: %v", r)
        }
    }()
    return a / b, nil // деление на 0 → паника → recover
}
```

`recover` работает **только внутри defer**. Используется на границах:
HTTP-сервер восстанавливается после паники в обработчике, чтобы не
уронить весь процесс.

**Антипаттерн:** использовать panic/recover как исключения. Не делайте так.

### 8.6. Как думают опытные

- Обрабатывай ошибку **один раз**: либо логируй, либо возвращай. Не
оба. Иначе одна ошибка в логах 5 раз.
- Ошибка — часть API. Документируй, какие sentinel-ошибки функция может вернуть.
- `_ = f.Close()` — явное игнорирование ошибки лучше молчаливого. Но
лучше не игнорировать.

## Часть 9. Дженерики (Go 1.18+)

### 9.1. Зачем

До 1.18 универсальную функцию `Max` для `int` и `float64` нельзя было
написать без дублирования или `any` с потерей типов.

```go
func Max[T constraints.Ordered](a, b T) T {
    if a > b {
        return a
    }
    return b
}

Max(1, 2)       // T выводится как int
Max(1.5, 2.5)   // float64
Max[int](1, 2)  // явно
```

### 9.2. Ограничения (constraints)

Ограничение — это интерфейс, описывающий, какие типы допустимы:

```go
type Number interface {
    ~int | ~int64 | ~float64  // ~ означает «любой тип с таким базовым типом»
}

func Sum[T Number](xs []T) T {
    var total T
    for _, x := range xs {
        total += x
    }
    return total
}

// comparable — встроенное ограничение: типы, поддерживающие ==
func Contains[T comparable](xs []T, x T) bool { ... }

// any — без ограничений
func Map[T, U any](xs []T, f func(T) U) []U {
    out := make([]U, 0, len(xs))
    for _, x := range xs {
        out = append(out, f(x))
    }
    return out
}
```

Полезные готовые ограничения: `cmp.Ordered` (Go 1.21), пакет
`golang.org/x/exp/constraints`.

### 9.3. Обобщённые типы

```go
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 {
        return zero, false
    }
    v := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return v, true
}

s := &Stack[int]{}
s.Push(1)
```

### 9.4. Когда НЕ использовать дженерики

- Когда достаточно интерфейса (поведение важнее типа: `io.Reader`).
- Когда функция работает с одним типом.
- «Потому что могу». Go-сообщество консервативно: дженерики — для
контейнеров, алгоритмов над слайсами/map, утилит. Не для
бизнес-логики.

**Правило:** пишите конкретный код, пока не скопируете его в третий
раз. Тогда думайте о дженериках.

## Часть 10. Конкурентность — главная сила Go

### 10.1. Конкурентность ≠ параллелизм

- **Конкурентность** — структура программы: множество независимо
выполняющихся задач. Это про **дизайн**.
- **Параллелизм** — одновременное выполнение на нескольких ядрах. Это
про **исполнение**.

Конкурентная программа может работать на одном ядре (задачи
чередуются). Go даёт инструменты для конкурентного дизайна;
параллелизм получается бесплатно, если ядер много.

### 10.2. Горутины

Горутина — функция, выполняемая независимо от вызвавшей её.

```go
go doWork()       // запустить и не ждать
go func() {
    fmt.Println("в горутине")
}()
```

**Что такое горутина физически?** Это НЕ поток ОС. Это структура
рантайма (~2 КБ стека + метаданные), которую **планировщик Go**
размещает на потоках ОС.

### 10.3. Планировщик: модель G-M-P

- **G** (goroutine) — горутина.
- **M** (machine) — поток ОС.
- **P** (processor) — логический процессор, контекст планирования. Их
количество = `GOMAXPROCS` (по умолчанию = число ядер).

```
   P0          P1          P2         (по числу ядер)
   |           |           |
  M0          M1          M2          (потоки ОС)
   |           |           |
 [G G G]     [G G]       [G G G G]    (очереди горутин)
```

Каждый P имеет локальную очередь горутин. M берёт P и выполняет его
горутины. Когда горутина блокируется (канал, мьютекс, сеть) —
планировщик снимает её и ставит другую. **Переключение горутин —
дёшево** (сотни наносекунд, в user space, без участия ядра ОС).
Переключение потоков ОС — микросекунды.

**Work stealing:** если очередь P опустела, он крадёт горутины у соседей.

**Системные вызовы:** если горутина ушла в блокирующий syscall (чтение
файла), M блокируется вместе с ней; рантайм отдаёт P другому M.
Сетевой ввод-вывод — особый: через **netpoller** (epoll/kqueue) без
блокировки M. Поэтому Go-сервер держит 100k соединений на нескольких
потоках.

**Вытеснение:** с Go 1.14 планировщик может снять горутину
принудительно (по сигналу каждые ~10 мс), даже если она крутится в
цикле без вызовов функций.

**Зачем это знать:** чтобы понимать, что `go f()` почти бесплатно, что
горутины блокируются без вреда, и что миллион горутин — нормально, а
миллион потоков — нет.

### 10.4. Главная проблема: `main` не ждёт

```go
func main() {
    go fmt.Println("привет")
    // main завершается → программа завершается → горутина могла не успеть
}
```

Нужна синхронизация. Инструменты: `sync.WaitGroup`, каналы.

### 10.5. WaitGroup

```go
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)          // ДО запуска горутины!
    go func(id int) {
        defer wg.Done()
        fmt.Println("worker", id)
    }(i)
}
wg.Wait()              // блокируется, пока счётчик не станет 0
```

`Add` — вне горутины, иначе гонка: `Wait` может выполниться до `Add`.

### 10.6. Гонки данных (data race) — что это на самом деле

Гонка — когда две горутины обращаются к одной памяти, хотя бы одна
пишет, и нет синхронизации. Результат — **неопределённое поведение**,
не «иногда неправильное число», а буквально что угодно (порванные
структуры, крах).

```go
counter := 0
for i := 0; i < 1000; i++ {
    go func() { counter++ }()  // ГОНКА: counter++ — это чтение, +1,
запись; не атомарно
}
```

**Детектор гонок:** `go test -race`, `go run -race`. Замедляет в 5–10
раз, но находит реальные гонки. **Всегда гоняйте тесты с `-race`.**

### 10.7. Мьютексы

```go
type SafeCounter struct {
    mu sync.Mutex
    n  int
}

func (c *SafeCounter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}
```

`sync.RWMutex` — много читателей ИЛИ один писатель. Полезно, когда
чтений на порядки больше.

Правила:
- Мьютекс защищает **данные**, а не код. Документируйте, какие поля
под каким мьютексом (кладите mu рядом с полями).
- Не копируйте структуры с мьютексом (pointer receiver!).
- Держите блокировку минимально: не делайте I/O под мьютексом.

### 10.8. Каналы — коммуникация вместо разделяемой памяти

> *«Не общайтесь через разделяемую память; разделяйте память через общение.»* — пословица Go

Канал — типизированная очередь для передачи значений между горутинами
с встроенной синхронизацией.

```go
ch := make(chan int)      // небуферизованный
ch := make(chan int, 10)  // буферизованный, ёмкость 10

ch <- 42       // отправить (блокируется, пока никто не примет / буфер полон)
v := <-ch      // принять (блокируется, пока нечего принимать)
v, ok := <-ch  // ok == false, если канал закрыт и пуст
close(ch)      // закрыть — сигнал «больше не будет»

for v := range ch { }  // читать до закрытия
```

**Небуферизованный канал = точка встречи (rendezvous).** Отправитель и
получатель должны быть готовы одновременно. Это и синхронизация, и
передача данных за раз. После `ch <- v` вы **знаете**, что получатель
забрал v.

**Буферизованный** — отправка не блокируется, пока есть место.
Развязывает производителя и потребителя по времени, но **не решает
проблему, если потребитель медленнее в среднем** — буфер всё равно
заполнится.

**Направленные каналы** в сигнатурах — документация и защита:

```go
func producer(out chan<- int) { ... }  // только отправка
func consumer(in <-chan int)  { ... }  // только приём
```

### 10.9. Аксиомы каналов (выучите наизусть)

| Операция | nil-канал | закрытый канал | обычный |
|---|---|---|---|
| отправка | блокируется навсегда | **паника** | блок/успех |
| приём | блокируется навсегда | нулевое значение, ok=false | блок/успех |
| close | паника | **паника** | закрывает |

Следствия:
- **Закрывает только отправитель**, и только один. Никогда не
закрывайте канал со стороны получателя.
- Закрывать не обязательно (GC уберёт). Закрывайте, чтобы
сигнализировать «конец» получателям через `range`.
- nil-канал в `select` = «отключить этот case». Это осознанный приём.

### 10.10. `select` — мультиплексор каналов

```go
select {
case v := <-ch1:
    fmt.Println("из ch1", v)
case ch2 <- 10:
    fmt.Println("отправили в ch2")
case <-time.After(time.Second):
    fmt.Println("таймаут")
default:
    fmt.Println("ничего не готово")  // делает select неблокирующим
}
```

Если готово несколько case — выбирается **случайный**. `select {}` без
case — вечная блокировка.

### 10.11. Context — отмена и дедлайны

`context.Context` — стандартный способ сказать горутине «пора
заканчивать». Передаётся **первым аргументом** во все функции, которые
могут работать долго.

```go
func worker(ctx context.Context) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()  // context.Canceled или DeadlineExceeded
        default:
            // делать работу маленькими порциями
        }
    }
}

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()   // ВСЕГДА вызывайте cancel — иначе утечка
err := worker(ctx)
```

Контексты образуют дерево: отмена родителя отменяет всех детей.
HTTP-сервер даёт `r.Context()`, который отменяется при отключении
клиента — и вся цепочка (БД-запросы, HTTP к другим сервисам)
прерывается.

`context.WithValue` — для сквозных данных (trace ID, пользователь).
**Не для передачи параметров функции.**

### 10.12. Классические паттерны

**Worker pool:**

```go
func workerPool(jobs <-chan Job, results chan<- Result, n int) {
    var wg sync.WaitGroup
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range jobs {
                results <- process(j)
            }
        }()
    }
    go func() {
        wg.Wait()
        close(results)  // закрываем, когда ВСЕ воркеры закончили
    }()
}
```

**Pipeline:**

```go
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            out <- n
        }
    }()
    return out
}

func sq(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            out <- n * n
        }
    }()
    return out
}

for v := range sq(sq(gen(1, 2, 3))) {
    fmt.Println(v)
}
```

**errgroup** (`golang.org/x/sync/errgroup`) — WaitGroup + первая
ошибка + отмена контекста:

```go
g, ctx := errgroup.WithContext(ctx)
for _, url := range urls {
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
if err := g.Wait(); err != nil { ... }
```

Это то, что вы будете использовать в 80% случаев «запустить N задач
параллельно».

### 10.13. Утечки горутин

Горутина, которая заблокирована навсегда (ждёт канал, который никто не
заполнит), — утечка памяти. Типичный случай:

```go
func fetch() <-chan Result {
    ch := make(chan Result)
    go func() {
        ch <- slowCall()  // если вызывающий ушёл по таймауту и не
читает — горутина висит вечно
    }()
    return ch
}
```

Решения: буфер размером 1 (`make(chan Result, 1)`) — горутина отправит
и завершится; или `select` с `ctx.Done()` внутри.

**Правило:** запуская горутину, знайте, **как и когда она
завершится**. Каждый `go` — это обязательство.

### 10.14. `sync` и `atomic` — когда что

- `sync.Mutex` — защита состояния.
- `sync.Once` — инициализация ровно один раз (ленивые синглтоны).
- `sync.WaitGroup` — ожидание группы.
- `sync/atomic` — атомарные операции над числами. `atomic.Int64` (Go
1.19+): `counter.Add(1)`. Быстрее мьютекса для простых счётчиков.
- `sync.Pool` — пул переиспользуемых объектов для снижения аллокаций (буферы).
- `sync.Map` — только для специфических случаев (ключи пишутся один
раз, читаются много; разные горутины работают с разными ключами).
Обычный map + RWMutex обычно лучше и понятнее.

### 10.15. Как думают опытные гоферы о конкурентности

1. **Начинай с последовательного кода.** Конкурентность — оптимизация,
у которой есть цена (сложность, баги).
2. **Каналы — для передачи владения данными. Мьютексы — для защиты
состояния.** Не пытайтесь всё делать через каналы.
3. **Владение:** в каждый момент времени одна горутина владеет
данными. Передача через канал = передача владения.
4. **Ограничивайте параллелизм.** «Запустить горутину на каждый
элемент» для миллиона элементов — плохо. Семафор через буферизованный
канал или worker pool.
5. **Структурируйте время жизни.** Горутины, запущенные функцией,
должны завершиться до её возврата (или иметь явное управление
жизненным циклом). Это «structured concurrency».

## Часть 11. Пакеты, модули, организация кода

### 11.1. Пакет

- Пакет = каталог. Все `.go` файлы в каталоге принадлежат одному пакету.
- Имя пакета — короткое, строчными, без подчёркиваний: `http`, `json`,
`user`. Не `utils`, не `common`, не `helpers` — это «свалки».
- Имя пакета — часть имени при использовании: `http.Client`, а не
`http.HTTPClient` (заикание).
- Циклические импорты запрещены. Это заставляет думать о слоях.

### 11.2. `init()` и порядок инициализации

```go
func init() {
    // выполняется при загрузке пакета, до main
}
```

Порядок: сначала инициализируются импорты, затем переменные пакета,
затем `init()`. Используйте редко (регистрация драйверов,
`database/sql`). Скрытая магия — плохо.

### 11.3. Структура проекта

Для маленького проекта — всё в корне, плоско. Не делайте 10 каталогов
для 500 строк.

Для среднего/большого:

```
myapp/
  go.mod
  cmd/
    server/main.go       # исполняемые файлы — тонкие
    cli/main.go
  internal/              # код, недоступный для импорта извне модуля
(компилятор гарантирует)
    user/                # доменный пакет
      user.go
      repository.go
      service.go
    order/
    httpapi/
  pkg/                   # публичные библиотеки (спорно; многие не используют)
```

`internal/` — единственное магическое имя: пакеты внутри могут
импортировать только пакеты из того же корня.

**Организуйте по домену, а не по слою.** Не `models/`, `controllers/`,
`services/`, а `user/`, `order/`, `payment/`. Пакет `models` со всеми
структурами — типичный источник циклических зависимостей.

### 11.4. Модули и версионирование

- Semantic Versioning: `v1.2.3`.
- Мажорная версия ≥ 2 — часть пути импорта: `github.com/x/lib/v2`. Это
позволяет использовать v1 и v2 одновременно.
- `go.sum` — хеши зависимостей, коммитьте.
- `go mod tidy` — регулярно.
- `go mod vendor` — скопировать зависимости в `vendor/` (для оффлайн-сборок).

## Часть 12. Тестирование, бенчмарки, профилирование

### 12.1. Тесты — встроены в язык

Файл `math_test.go` в том же пакете:

```go
package math

import "testing"

func TestAdd(t *testing.T) {
    got := Add(2, 3)
    if got != 5 {
        t.Errorf("Add(2,3) = %d; want 5", got)
    }
}
```

```bash
go test ./...
go test -v -run TestAdd ./...
go test -race -cover ./...
```

### 12.2. Табличные тесты — главная идиома

```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {"положительные", 2, 3, 5},
        {"с нулём", 0, 5, 5},
        {"отрицательные", -1, -1, -2},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := Add(tt.a, tt.b); got != tt.want {
                t.Errorf("got %d, want %d", got, tt.want)
            }
        })
    }
}
```

`t.Run` создаёт подтесты — можно запускать по отдельности: `-run
TestAdd/с_нулём`.

### 12.3. Полезное

- `t.Helper()` — в вспомогательных функциях, чтобы ошибка указывала на
строку теста.
- `t.Cleanup(func())` — аналог defer для теста.
- `t.Parallel()` — параллельные тесты.
- `testing.Short()` и `-short` — пропуск долгих тестов.
- `package foo_test` — внешний тестовый пакет; тестирует только публичный API.
- `testdata/` — каталог для файлов-фикстур, Go его игнорирует при сборке.
- Библиотеки: `github.com/stretchr/testify` (assert/require) —
популярна; `github.com/google/go-cmp` — для сравнения структур.

### 12.4. Бенчмарки

```go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(2, 3)
    }
}
```

```bash
go test -bench=. -benchmem
# BenchmarkAdd-8   1000000000   0.25 ns/op   0 B/op   0 allocs/op
```

`b.N` подбирается автоматически. `-benchmem` показывает аллокации —
это часто важнее наносекунд.

### 12.5. Профилирование

```bash
go test -cpuprofile cpu.out -memprofile mem.out -bench=.
go tool pprof cpu.out
(pprof) top
(pprof) web   # граф в браузере
```

В сервере: `import _ "net/http/pprof"` и
`http://localhost:6060/debug/pprof/`. Профилировать в проде — норма
для Go.

**Мышление:** не оптимизируйте вслепую. Измерь → профилируй → найди
горячее место → исправь → измерь снова.

## Часть 13. Стандартная библиотека — то, что делает Go продуктивным

### 13.1. `io` — универсальные абстракции

```go
io.Reader, io.Writer, io.Closer, io.ReadWriter, io.ReadCloser
io.Copy(dst Writer, src Reader)   // копирует поток, буферизуя
io.ReadAll(r)                      // прочитать всё в []byte
io.MultiWriter(w1, w2)             // писать в оба
io.TeeReader(r, w)                 // читать из r и одновременно писать в w
bufio.NewReader / NewWriter / NewScanner  // буферизация
```

Мышление через потоки, а не через «загрузить всё в память»:
`io.Copy(file, resp.Body)` скачает гигабайт, не съев гигабайт ОЗУ.

### 13.2. `net/http` — production-ready сервер

```go
func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r
*http.Request) {
        id := r.PathValue("id")  // Go 1.22+
        fmt.Fprintf(w, "user %s", id)
    })

    srv := &http.Server{
        Addr:         ":8080",
        Handler:      mux,
        ReadTimeout:  5 * time.Second,
        WriteTimeout: 10 * time.Second,
    }
    log.Fatal(srv.ListenAndServe())
}
```

Каждый запрос — своя горутина. **Никогда не используйте
`http.DefaultClient` / `http.Get` в проде без таймаутов** — они не
имеют таймаутов по умолчанию.

```go
client := &http.Client{Timeout: 10 * time.Second}
resp, err := client.Get(url)
if err != nil { return err }
defer resp.Body.Close()  // ОБЯЗАТЕЛЬНО, иначе утечка соединений
```

Middleware — просто функции `func(http.Handler) http.Handler`.

### 13.3. `encoding/json`

```go
type User struct {
    Name  string `json:"name"`
    Email string `json:"email,omitempty"`  // пропустить, если пусто
    pass  string                            // неэкспортируемое — игнорируется
    Age   int    `json:"-"`                 // явно игнорировать
}

data, err := json.Marshal(u)
err = json.Unmarshal(data, &u)  // указатель!

// Потоковый:
json.NewEncoder(w).Encode(u)
json.NewDecoder(r.Body).Decode(&u)
```

Теги структур — строки с метаданными, читаемые через рефлексию.

### 13.4. Остальное, что нужно знать

`strings`, `strconv` (конвертация строк ↔ чисел: `strconv.Itoa`,
`strconv.Atoi`), `time` (`time.Duration`, `time.Now()`, форматирование
через эталонную дату `2006-01-02 15:04:05`), `os`, `path/filepath`,
`sort`/`slices`/`maps`, `log/slog` (структурированные логи, Go 1.21+),
`flag` (аргументы командной строки), `regexp`, `crypto/*`,
`database/sql`, `embed` (встраивание файлов в бинарник).

## Часть 14. Заблуждения, ловушки, антипаттерны — сводка

### Заблуждения

| Заблуждение | Реальность |
|---|---|
| «Слайс — это массив/список» | Слайс — заголовок (ptr, len, cap)
поверх массива. Отсюда все сюрпризы. |
| «Строка — массив символов» | Строка — байты. `len` — байты. Символы — руны. |
| «Встраивание — это наследование» | Это композиция с делегированием.
Нет полиморфизма. |
| «nil-указатель в интерфейсе == nil» | Нет. Интерфейс nil, только
если и тип, и значение nil. |
| «Горутина — поток» | Горутина — структура рантайма; планировщик
мультиплексирует их на потоки. |
| «Буферизованный канал решает проблему медленного потребителя» |
Только сглаживает пики. |
| «GC значит не думать о памяти» | GC — цена. Аллокации в горячем пути
— то, что оптимизируют. |
| «`defer` медленный» | С Go 1.14 почти бесплатен. Используйте. |
| «Дженерики заменят интерфейсы» | Разные инструменты: дженерики —
параметризация типов, интерфейсы — поведение. |

### Ловушки

- `s = append(s, ...)` без присваивания.
- Общий базовый массив у слайсов.
- Запись в nil-map.
- Переменная `err` затеняется (`:=` внутри `if` создаёт новую). `go
vet` / линтер `shadow`.
- `for range` копирует элемент: `for _, v := range items { v.X = 1 }`
не меняет items. Нужен `items[i].X = 1` или range по индексам.
- Закрытие канала дважды / отправка в закрытый.
- `time.After` в цикле — утечка таймеров до Go 1.23. Используйте
`time.NewTimer` + `Stop`.
- `resp.Body.Close()` забыт.
- `cancel()` от контекста забыт.
- Копирование `sync.Mutex` / `sync.WaitGroup` по значению.
- Сравнение ошибок через `==` вместо `errors.Is`.
- `int` разного размера на разных платформах — для сериализации
используйте `int64`.
- Формат времени `"2006-01-02"` — не опечатка, а эталонное время Go (1
2 3 4 5 6 7 = месяц день час минута секунда год зона).

### Антипаттерны

- Пакет `utils`/`common`/`helpers`.
- Интерфейсы «на всякий случай» с одной реализацией.
- Большие интерфейсы.
- `panic` вместо ошибок.
- `interface{}` где можно конкретный тип или дженерик.
- Геттеры/сеттеры для всего (`GetName()` — не идиоматично; просто
`Name()` или публичное поле).
- Глобальное состояние (глобальный `db`, глобальный логгер без
инъекции) — мешает тестам.
- Излишняя абстракция: репозиторий → сервис → юзкейс → контроллер для
CRUD из 3 полей.
- Игнорирование `go vet` и линтеров (`golangci-lint`).

## Часть 15. Как думают великие гоферы (ментальные модели)

1. **Простота — это фича.** Простой, «скучный» код, который понятен
через год без автора, — цель. Умный код — это долг.
2. **Явное лучше неявного.** Ошибки видны. Аллокации видны.
Конкурентность видна (`go`). Зависимости видны (инъекция через
конструктор).
3. **Читай Go Proverbs (Роб Пайк):** «A little copying is better than
a little dependency», «Clear is better than clever», «Don't
communicate by sharing memory, share memory by communicating», «The
bigger the interface, the weaker the abstraction», «Make the zero
value useful», «Errors are values», «Don't panic».
4. **Думай о владении.** Кто владеет слайсом, map, горутиной,
соединением? Кто закрывает? Кто отменяет?
5. **Думай о памяти.** Где аллокация? Убегает ли в кучу? Можно ли
переиспользовать буфер? Но — сначала измерь.
6. **Читай стандартную библиотеку.** Это лучший учебник по
идиоматичному Go. `net/http`, `io`, `bufio`, `sort`, `context` —
читайте исходники.
7. **Пиши код для читателя.** Комментарии к экспортируемым сущностям
начинаются с их имени: `// NewUser создаёт...`. `go doc` их покажет.
8. **Инструменты — часть языка.** gofmt, vet, race detector, pprof, go
test — используйте всё.

## Часть 16. Упражнения и проекты

### Уровень 1 — базовый (закрепить синтаксис и коллекции)

1. **Частотный словарь.** Прочитать текст из stdin, посчитать частоту
слов, вывести топ-10. Обратите внимание на руны и `strings.Fields`,
сортировку map через слайс ключей.
2. **Слайс-лаборатория.** Напишите программу, которая демонстрирует:
(а) append с ростом cap — печатайте `len/cap` на каждом шаге; (б)
общий базовый массив у двух слайсов; (в) защиту через `s[a:b:b]`.
Объясните каждый вывод себе вслух.
3. **Стек и очередь** на слайсах. Затем — обобщённые версии через дженерики.
4. **Reverse строки** корректно для Юникода («привет🙂» → «🙂тевирп»).

### Уровень 2 — средний (интерфейсы, ошибки, тесты)

5. **Собственный `io.Reader`.** Реализуйте `rot13Reader`,
оборачивающий другой `Reader`. Проверьте с `io.Copy(os.Stdout,
rot13Reader{strings.NewReader("Hello")})`.
6. **Библиотека ошибок.** Напишите пакет с sentinel-ошибкой
`ErrNotFound` и типизированной `*ValidationError`. Функция, которая
оборачивает их через 3 уровня. Тесты с `errors.Is`/`errors.As`. Затем
воспроизведите ловушку «nil-указатель в интерфейсе» и исправьте.
7. **Фигуры.** Интерфейс `Shape` с `Area()`, `Perimeter()`. Три
реализации. Функция, сортирующая `[]Shape` по площади
(`slices.SortFunc`). Табличные тесты на всё.
8. **CLI-утилита `wc`** (word count) с флагами `-l -w -c` через пакет
`flag`. Работает и с файлами, и со stdin — через `io.Reader`.

### Уровень 3 — конкурентность

9. **Параллельный краулер.** Дан список URL. Скачать все с
ограничением в N одновременных запросов (семафор через буферизованный
канал или errgroup.SetLimit). Таймаут через context. Собрать
результаты. Запустить с `-race`.
10. **Pipeline.** Три стадии: генератор чисел → фильтр простых →
вывод. Каждая — горутина, соединены каналами. Добавьте отмену через
context на любой стадии. Убедитесь, что нет утечки горутин
(`runtime.NumGoroutine()` до и после).
11. **Потокобезопасный кэш** с TTL: `Get/Set`, фоновая горутина для
очистки просроченных. `RWMutex`. Тесты с `t.Parallel()` и `-race`.
Бенчмарк: сравните `Mutex` vs `RWMutex` vs `sync.Map` при 90% чтений.
12. **Rate limiter** (token bucket) на `time.Ticker` и канале.

### Уровень 4 — проекты

13. **URL-shortener** (HTTP-сервис). `POST /shorten`, `GET /{code}`.
In-memory хранилище за интерфейсом `Store`; вторая реализация на
SQLite. Graceful shutdown (`signal.NotifyContext` +
`srv.Shutdown(ctx)`). Middleware логирования и recover. Тесты через
`httptest`. Структура `cmd/` + `internal/`.
14. **Key-value база на диске** (мини-Bitcask): append-only лог,
in-memory индекс `map[string]offset`, компактификация. Работа с
`os.File`, `bufio`, `encoding/binary`. Это заставит понять байты,
буферы и `io` глубоко.
15. **Чат-сервер на TCP** (`net.Listen`). Каждый клиент — горутина.
Хаб с `broadcast` через каналы. Корректное отключение клиентов без
утечек.
16. **Мини-планировщик задач / worker queue** с приоритетами,
повторными попытками с экспоненциальной задержкой, graceful
остановкой. Метрики через `expvar` или `prometheus`.

### Вызовы на понимание

- Объясните без заглядывания: что напечатает
`fmt.Println(len("日本語"))`, и почему.
- Напишите функцию, которая безопасно удаляет элемент из слайса,
**не** влияя на другие слайсы, ссылающиеся на тот же массив.
- Прочитайте исходник `sync.Once` и объясните, зачем там и atomic, и mutex.
- Прочитайте `context.WithCancel` и нарисуйте дерево отмены.
- Запустите `go build -gcflags=-m` на своём коде и объясните каждую
строку про «escapes to heap».
