# bytecheck — the byte-check part of orchestrate

Your report is a claim; the filesystem is the evidence. This part produces that evidence — bytecheck exists so an agent can check itself and show the work is exactly what it says it is; it is a discipline of self-verification, not a guard the user posts against you. Byte-exact checking runs `bytecheck.py` as shipped — no git substitute, no replacement verifier, no flag the tool lacks. The capture plugin and reply extractor transport received text; neither supplies the tool's verdict or changes its internals. Read Harvest when a reply arrives, independently of the byte-check setting. Snapshot before the first edit and verify after the last only when byte-exact checking was settled on. Asked for the byte-check alone, run its full protocol.

## The tool

`bytecheck.py` is vendored beside this file — bytecheck v0.2.0, sha256 `03742ad77c6038ed6cdebc60855656df69b8245f72700171ca11854615c88606`, from github.com/vasyapym/bytecheck. Run the copy beside this file by default; a `bytecheck:` line in `~/.config/orchestrate/declarations.md` may name a different clone the user keeps current — use it when present, and say which copy you ran. Two more optional lines: `byte-check:` a standing answer (always, never) that spares the opening question; `rounds:` where round folders go (default: the brief folder). Interpreter `python3`; on Windows `py -3` where `python` is the Store stub, with `PYTHONIOENCODING=utf-8` (or run the vendored `bytecheck.cmd`).

You never modify, update or replace the tool — what judges your work is not yours to touch — but you report what judged it: `--version` and `hash bytecheck.py` go into every byte-checked round record. This file holds none of the tool's reference: flags, rules, exit codes and the policy guide come from `--help` and the clone's SKILL.md when needed, not from memory. Where this file and the tool disagree, the tool is right, this file is stale, and you say so.

## Snapshot — before the first edit

A round is one snapshot, any number of edits, one verdict. Nothing in the tree changes before the snapshot; none is taken once the round's first edit has happened — the next round opens with its own.

1. Make `round-<k>/` in the rounds folder (next `round-` number present; 1 in a fresh folder). It lies outside every tree a gate or this check covers; if the user put it inside the root, exclude it.
2. Snapshot with the store:

       python3 bytecheck.py snapshot <root> -o round-<k>/.bytecheck/before.json --store --exclude <g> ...

   Exclude dependency and build trees (`node_modules/`, `.venv/`, `dist/`) and nothing the task could touch — an excluded path is unchecked. The store keeps every before-byte: on a large tree exclude generously or tell the user the size first.
3. Derive the policy from the task as stated: allow what it names, narrowly; expect what must change; deny what it must not touch; allow deletion only where asked; `--within` where lines were named. No flags asserts an untouched tree; `--allow '**'` is a report, not a check, and is used only when asked for. Write the complete verify command — manifest, root, excludes, policy — into `round-<k>/.bytecheck/cmd.txt`. From here it narrows freely and widens only on the user's word in this conversation; the same excludes serve snapshot, verify and hash, since differing excludes make false verdicts.
4. Report in chat: `tree_hash_before`, excludes, the policy in one line, and how replies will travel (next section). The hash in the user's chat is the one piece of evidence you cannot later edit.

## Harvest — when a reply arrives

Acquire received text once; work from its file thereafter. Harvest applies with byte-checking on or off. A capture proves the receiving application's stored text, not the specialist's original bytes: rendered copying may already have removed markup before the plugin or database saw it. Prefer the specialist's raw text or copy-as-Markdown when available; never describe a repaired or retyped reply as received byte-exactly.

An explicit reply-file path is already acquired input; use it without searching other sources. Otherwise use this ladder, stopping at the first unambiguous usable source. Check acquisition availability once per session and revisit only after a failure or a configuration change; do not reinstall a plugin or rediscover a schema for every reply.

1. **Existing plugin capture**: when opencode-capture.ts is installed and captured this message, locate its file in BYTECHECK_INBOX, the project's .bytecheck/inbox/, or the home fallback. Match the message and part, not merely the newest filename; verify the .sha256 sidecar. A missing part or mismatching digest is an acquisition failure, never something to repair in place. Do not invent separators to assemble multiple parts; use a complete stored representation or ask for a raw file when their exact assembly is unknown.
2. **Session database**: when no usable capture exists, use extract-reply.py beside this file; read extract-reply.md on first use. Supply the identifying phrase, the expected marker profile, the receiving session and the reply-file destination. Prefer an exact message id when the relay event provides it. The helper reads the supported stored text, decodes its JSON and writes UTF-8 without retyping. Do not exclude the receiving session as a self-hit; it contains the wanted human paste. Reject assistant messages and known worker/spawn sessions; require the full profile, not a promising phrase or a large candidate. Ambiguity returns a candidate report, not a guessed file. For an identified cut-off or damaged reply, explicit capture-only mode may preserve that message with its failed markers recorded; it does not accept the reply.
3. **User-saved file**: when stored capture is unavailable or cannot be resolved, ask the user to save the raw reply as a separate file, preferably one reply per file. An existing inbox with separators is usable when the exact range is unambiguous; retain its source hash and cut mechanically. Say that this adds a save step. Saving a rendered copy does not undo its losses.
4. **Degraded transcription**: only when no usable source remains and the user declines the file step, treat text reconstructed from chat as your own edit. Mark it typed from chat, unverified in the record and report; never file it as an acquired raw reply or claim fidelity to the specialist. Scope verification may still run when enabled; reply fidelity remains unverified.

Put each acquired raw reply at round-<k>/replies/<n>-<slug>.md, using the brief's number and slug. Use the existing round folder; if none exists, allocate the next round number in the declared rounds folder, defaulting to the brief folder. With byte-checking off, this does not create a snapshot or enable a byte-check round. Keep acquisition and repair files outside checked trees or under exclusions already agreed; do not widen a policy to house them.

Keep one compact receipt: source kind and locator, receiving session/message/part or file range where applicable, byte length, SHA-256, marker results, completeness and any known transport loss. Reuse the helper's receipt rather than duplicating it. Hash the received bytes without normalizing line endings, Unicode or the terminal newline; a hash establishes identity from acquisition onward, not an independent provenance guarantee. A reply with nothing to place still gets a receipt. Preserve the raw file unchanged.

Transport checklist: look for missing headings, bold markers, list markers, inline-code backticks and blockquote markers where the brief actually required them. Their absence elsewhere is not evidence of damage. Collapsed line breaks are the same class: copies from a specialist chat sometimes arrive with every newline gone and sometimes intact; accept what lands without re-diagnosing storage — prose tolerates the collapse, byte-exact artifacts never travel by paste. DB extraction and plugin capture avoid agent transcription; neither restores these markers.

For a bounded restoration, use a separate working copy. Take the permitted line forms and exact literals from this brief's templates or its byte-authoritative sources; match whole lines or explicitly bounded fields, with their block context. Require one unambiguous template match and the expected match count. Change only the named missing delimiters; assert that removing the inserted delimiters reproduces the acquired text. Do not change words, numbers, whitespace, line breaks, ordering or undeclared lines; never globally prettify markdown. A non-unique match, a damaged fence boundary or missing substantive content stops the affected artifact for clarification or a continuation. Record the rule, affected ranges and derived-file hash; restoration is your integration edit, not proof of the original reply. When exact original markup is required but cannot be established, report it unverified rather than guessing.

With byte-checking on, scan the acquired file and any derived artifact; findings are facts about their contents. In prose they may be noise; inside an artifact to place, a placeholder or elision is an unresolved gap, never filled from memory. Cut accepted artifacts mechanically from the acquired file or the explicitly labelled derived copy into round-<k>/harvest/<n>-<slug>/<name>; record the source range or stable block label and hash. Use blocks CAPTURE --extract LABEL --to TARGET when path-labelled fenced blocks support it; otherwise use a byte-preserving file slice. Never route the cut through a model's rewritten text.

Stale-buffer law: disk is authoritative after an external write. Before placement, establish one writer per target and record its current hash or absence; compare again immediately before replacing or splicing it. Unexpected change stops the write for a fresh read and reconciliation. Reload or discard an editor's old buffer after a command, sub-agent or another editor changes the file; never save the old buffer to synchronize it. Read the placed result from disk. These checks do not make competing writes atomic; where exclusive ownership cannot be established, stop rather than claim protection against the race.

Place by command from the cut: copy a whole file, or splice a fragment by reading its bytes from disk. With byte-checking on, prove a whole-file placement with same; for a fragment, cut the placed range back out and compare it with the harvest cut; blocks CAPTURE --same may prove path-labelled blocks together. Prove an acquired cut against the acquired source and a repaired cut against its labelled derived source; do not conflate those claims. Corrections follow the placement proof as your own edits; keep the acquired and derived evidence so the differences remain inspectable.

With byte-checking off, retain acquisition, mechanical placement and ordinary task checks; do not invoke bytecheck.py or manufacture its snapshot, verdict, report book or repeated equality checks. Use standard file hashing for the acquisition receipt and existing capture-sidecar check. The minimal record is the receipt and any repair note, not a byte-check round in disguise.

When cleanup-after-yourself is yes, remove processed briefs and disposable scratch only after integration, required checks and any delivery are complete. Do not delete a pending continuation's inputs, user-owned source files, a manifest or store, or replies and harvests still cited by a retained ledger or report. Retained evidence is machinery, not scratch; keep it in ignored storage or the agreed external record folder. Do not sweep an entire inbox to clean up one processed reply.

## Verify — after the last edit

Read the final state from disk, not an editor buffer. Any later save, external write or integration edit invalidates the affected placement proofs, task-check results, verdict and delivery copies; repeat the affected checks and rebuild the record before claiming completion. Follow Harvest's stale-buffer law at every hand-off.

Run `cmd.txt` as written, twice, both read-only: as text into `round-<k>/.bytecheck/verify.txt`, whose last line is the verdict line you quote, and once more with `--json` added, into `verify.json`, from which the round folder is built. A sub-agent may run both and return the verdict line and the paths. Read nothing else into your context; on FAIL read `violations` and `findings` — paths and lines — not the document. The exit code decides: 0 PASS; 1 FAIL; 2 ERROR — the check did not complete, report that and claim nothing.

On FAIL act by the violation: a path you were never to touch is restored from the store's before-bytes; an error finding is fixed in the tree; a change you cannot account for goes to the user verbatim, unexplained. Then rerun against the same manifest. A FAIL never disappears by re-snapshotting; the manifest and store are never edited, moved or deleted; `--strict` only when asked, warnings quoted for the user to weigh. Verify is repeatable: between sub-agent lanes, a run against the same manifest localizes a violation to its lane. A path PASS is not content proof: where the task implies a count — every occurrence of X replaced, nothing else names Y — count over the after-tree and record expected against actual.

## The round folder

`round-<k>/` is the round's record for three readers: the user, who reads it or carries the changes by hand into a tree you may not touch; the reviewer, whose brief quotes it; anyone recomputing the hashes.

    round-<k>/
      .bytecheck/   before.json, before.objects/, cmd.txt, verify.txt, verify.json
      replies/      each reply as received
      harvest/      artifacts cut from replies, by brief
      files/        after-state copy of every added, modified or renamed file, at its root-relative path
      CHANGES.md    the diff book

Build `files/` after the verdict — rebuilt after any further edit — from disk and the store, with a script written once and kept beside the round folders (`tools/`); nothing in the book is typed by you. Render `CHANGES.md` from the same verdict: `python3 bytecheck.py verify <manifest> <policy as already written> --format md --report <round folder>/CHANGES.md` — bytecheck's review book: title with the verdict line, baseline line, one `##` per changed file with its fenced diff and findings, Violations, Findings, verdict line last. The round script copies it, with `files/`, into the round folder; it renders no diffs itself. `verify.json` names each changed path with its before and after hash; the store holds the before-bytes under the before hash — locate, `hash --expect` confirms; the store objects are plain bytes named by their sha256, flat under `<manifest stem>.objects/` (checked on bytecheck 0.2.0; if the tool changes, this line is stale — say so).

CHANGES.md is compact. Header: root, date, tool version and hash, `tree_hash_before -> tree_hash_after`, the verdict line verbatim, excludes, policy, the reply files with hashes, every item marked unverified. One section per changed file: path, kind, before -> after hash, lines added and removed. Deleted: that line. Added: content inline when short, else `see files/<path>`. Modified: one old/new pair per hunk with two or three lines of context — the old block with its old-file line range, then the new block, both fenced, both verbatim, so the reader finds the old text and pastes the new over it; a file mostly rewritten gets `replaced whole, see files/<path>` instead. Before you cite the book, check it: the new blocks applied over the old in the before-bytes reproduce the after-file (`same`), and each `files/` copy is `same` as the tree.

## Report

Close the round's report with the verdict line and both tree hashes, verbatim, and how to recompute: `python3 bytecheck.py hash <root> --exclude <g> ...` must print `tree_hash_after`. Name the tool version and hash, the round folder, every item marked unverified, every check you could not run — a check the protocol cannot give is said, not improvised. Violations and findings appear as the tool printed them; "minor issues" is not a quote.
